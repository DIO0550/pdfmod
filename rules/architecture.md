# アーキテクチャ規約

## パッケージ構成

pnpm モノレポの2パッケージ構成。**役割の境界がそのまま依存の境界**になる。

```
packages/
  core/   @pdfmod/core  — PDF処理エンジン。React にもDOMにも依存しない純粋なTypeScript
  react/  @pdfmod/react — Reactコンポーネント / フック。core を使う薄い層
```

```
packages/core/src/
  index.ts          # パッケージの公開API(再export のみ)
  lexer/            # バイト列 → トークン
  objects/          # トークン → PDFオブジェクト(パーサ・オブジェクトストア)
  xref/             # クロスリファレンス(table / stream / trailer / startxref)
  document/         # カタログ・ページツリー・メタデータ
  content-stream/   # コンテンツストリーム(トークナイザ・オペレータ・グラフィックス状態)
  pdf/              # PDF共通の型とエラー(上のどの層からも参照される語彙)
  ext/              # 組み込み型への汎用操作(<型名>Ex)
  utils/            # Brand / Option / Result / ValueOf など汎用ヘルパー

packages/react/src/
  index.ts          # パッケージの公開API
  components/       # Reactコンポーネント
  hooks/            # Reactフック
```

## モジュールの公開API

**モジュールフォルダの基本形は「`index.ts` + `__tests__/`」で、実装は `index.ts` に直接書く。**

- フォルダ名はケバブケース(`object-parser` / `graphics-state` / `string-array`)
- フォルダ外部からの import は必ず `index.ts` 経由とし、**内部ファイルへの deep import は禁止**
- import 先は `"../../utils/option/index"` のように **`index` まで明示**する
- `index.ts` から export するのは外部に公開する必要があるものだけに絞る
- 複数ファイルへの分割が必要になったら、実装ファイルを1つだけ切り出すのではなく、その時点で**サブフォルダに分割**する(サブフォルダも同じ形を保つ)
- モジュール内で共有する**コンパニオンオブジェクトを持たない型**(注入するインタフェース・オプション型)は、そのモジュール直下の `types.ts` に置いてよい。型 + 同名コンパニオンオブジェクトが揃ったものは分離せず同一ファイルに置く(→ `rules/coding.md`)

## ロジックの帰属先

**判断の起点は「その規則は誰の性質か」。** 値を組み立てる・判定する・変換するコードは、その値を表す型のコンパニオンオブジェクトに置く。迷ったら、そのコードが第1引数に取っている型を見る。

- ある型 `T` を受け取って `T` の性質を答える関数、`T` から別の表現を作る関数は、`T` のコンパニオンオブジェクトのメソッドにする。呼び出し側にヘルパー関数として置かない
- 2つの値が**常に対で意味を持つ**(片方だけでは答えが決まらない)なら、対を表す型を作ってそちらに帰属させる
- **汎用の型に個別の知識を集めない。** 「この辞書キーが無いときは既定値」のような規則はその辞書を持つ側の性質なので、そちら側に置く。汎用の `PdfObject` 側に `xxxFromPdfObject()` を生やすと、他の関心事もすべてそこに集まって肥大化する
- 帰属先の型がまだ無いなら、**そのときが型を作るタイミング**。引数を4つも5つも取る中間ヘルパーや `readonly [number, number]` のようなタプルは、「名前の付いていない型がここにある」というサイン
- **入口の事情を型へ持ち込まない。** 「この呼び出し元は 0 を未指定として渡す」のような規則は**その呼び出し元の事情**であって値の性質ではない。型に持たせるとその値にとっての意味が固定され、別の経路から使えなくなる(`0` はそれ自体が正当なオフセットになりうる)。解釈は呼び出し側に置き、型には**解釈済みの値**を渡す(不在なら `Option`)
- **出口も同じ: 表示のための綴りを型へ持ち込まない。** 型が持つのは**値の種別**(直和・列挙)までで、それを人が読む1行にどう綴るかは表示側の関心事

## ext / utils の責務

`ext/` はドメイン知識を持たない**組み込み型への汎用操作**の置き場。`<型名>Ex` という名前空間オブジェクトに集約する(`MathEx` / `NumberEx` / `StringEx` / `StringArrayEx`)。

- 数値の性質判定・文字種の判定・配列の範囲判定などを、パーサや各モジュールのローカル関数として書かない
- **用途ではなく操作で名付ける。** 名前が呼び出し側での用途を指していると、処理自体は汎用でも PDF の語彙が `ext/` に入り込む。操作そのもので名付けられるなら `ext/` に置いてよく、用途を外すと名前が付けられないなら、それは呼び出し側の関心事なので呼び出し側へ置く
- PDF の概念になった時点で `ext/` から各層のモジュールへ移す。判断軸は「その値に生成・判定・変換の規則が付いてくるか」

`utils/` は `Brand` / `Option` / `Result` / `Interop` / `ValueOf` など、**型の取り回しそのもの**を提供する。PDF の語彙も組み込み型の操作も持たない。

## 依存方向のルール(必須要件)

```
@pdfmod/react → @pdfmod/core
```

- **`@pdfmod/core` は `@pdfmod/react` を import しない。** React・DOM・ファイルシステム・ネットワークへの依存も禁止。core が使ってよい外部 API は、環境を問わず使える Web 標準(`DecompressionStream` / `TextDecoder` 等)までとする
- **I/O は `@pdfmod/react` 側に置く。** PDF バイト列の取得(fetch・File 読み込み)は react 層の責務で、core は受け取ったバイト列だけを扱う
- **`utils/` と `ext/` は PDF の語彙を知らない。** ここから他の層への import は禁止(語彙が下から上へ流れるのを防ぐ)
- core 内部の向きは処理パイプラインの順に下る。`content-stream` / `document` → `xref` → `objects` → `lexer` → `pdf`(共通の型とエラー) → `utils` `ext`。**新しい import を足すときはこの向きを保つ**。上へ向かう import が要るときは、まず帰属先を間違えていないかを疑い、手段を引数で受け取る形(デコード関数を注入する等)にできないか検討する
- **循環依存は全面禁止**(biome の `noImportCycles` で強制)。ファイル単位では通っていても、フォルダ同士が互いを import している状態は帰属先を見直すサイン
