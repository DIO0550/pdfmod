# 命名規約

## 名前と実体を一致させる

**名前が約束することと、実際にやること・返すものを一致させる。** 名前を読んで想像した挙動と実装がずれていたら、名前が間違っている。

- **戻り値を名前に出す。** エラーの配列を返すだけの関数を `validate*` と名付けない(「検証して成否を返す」「不正なら例外を投げる」と読める)。集めて返すなら `collect*Errors`
- 探索していない関数に `find*` / `scan*` を使わない。位置情報を付与するだけの関数は `withLocation`
- **`try*` は「失敗しても正常」を意味する接頭辞として使う。** `Option` を返し、不一致が異常ではない読み取りに限る(`tryReadIndirectRef`)。`Result` でエラーを返すものに付けない
- 公開APIも同じ基準で名付ける。「ISO 32000 の語彙だから」を理由に、戻り値と食い違う名前を入口だけ残さない
- 1つのモジュール内で語彙を混在させない(内部だけ直して公開APIを残すと混在が復活する)

## その名前が既に別の意味を持っていないか確認する

**新しく付ける識別子名は、書く前にこのリポジトリの他の場所を探す。** 命名規約に沿っていても、既存の接頭辞・仕様書が既にその語を別の意味で使っていることがある。

1. **接頭辞・語幹を grep する。** 同じ接頭辞を持つ既存モジュールが指している対象と一致するか
2. **`docs/specs/` を `grep -i` で数える。** PDF 仕様は `Object` / `Stream` / `Filter` / `Reference` のような一般語に固有の意味を与えている。**仕様が既にその語を使っているなら、仕様の意味に合わせる**
3. **他ライブラリから借りた慣習名は、このリポジトリの文脈で何を指すかを言えるか**

## `And` を含む名前を作らない

`doAAndB` のような名前は、その関数が2つの振る舞いを持っている証拠。**名前を工夫して押し込めるのではなく、処理を分ける。** 分けられないなら、2つをまとめて表す1つの概念名を見つける(見つからないなら、やはり分けるべき処理)。

## 条件を組んだ式に名前を付ける

`&&` / `||` で2つ以上の条件を組んだ式を、`if` の中へそのまま置かない。**何を判定しているのかを表す名前の変数に入れてから使う。** 読み手は式を目で分解するまで、その分岐が何のためのものかを知れない。**バイト値の範囲判定が並ぶ箇所は特にそうなりやすい**(`isWhitespace` / `isDelimiter` のように名前を付ける。汎用なら `ext/` へ)。

- **条件が2つ以上要る理由がコードから読み取れないなら、変数のそばにコメントで残す**
- 名前が付けられないのは、その分岐で何をしたいのかが決まっていないサイン。条件を組み直す
- 単独の条件(`isEmpty` / `list.length === 0` など)はそのまま置いてよい。名前を増やすことが目的ではない

## 内容を表さない汎用語を使わない

`Entry` / `Info` / `Data` / `Detail` / `Manager` / `Helper` のような語は、何を指すのかを伝えない。PDF の語彙で名付ける。

**名前が思いつかないのは、その型が2つの役割を抱き合わせているサイン**であることが多い。改名で解決しようとする前に役割を分けられないか確認する(分けた結果その型自体が不要になることもある)。

> 例外: **仕様がその語を使っている場合は仕様に従う**(`XRefEntry` の "entry" は ISO 32000 の語彙)。判断軸は「`docs/specs/` にその名前で載っているか」。

## 定数の綴りは「公開APIに並ぶか」で決める

**コンパニオンオブジェクトと、そのメンバー・`ValueOf` 用の定数オブジェクトは PascalCase。**
`Hoge.method()` と `Hoge.Member` が同じ公開APIに並ぶので、`.` の左右で綴りの流儀を割らないため。
キーも PascalCase にする（`const Mode = { Fill: 0, Stroke: 1 } as const`）。

**モジュール内に閉じたスカラー定数は SCREAMING_SNAKE_CASE のままでよい。**
バイト値・ビット幅・仕様上の上限など、公開APIに現れず `.` の右側にも来ない値がこれにあたる
（`BITS_PER_BYTE` / `ADLER32_MODULO`）。

判断軸は**その名前が `.` の右側に出るか**。出るなら PascalCase、出ないなら据え置き。

### 対応表のキーを PascalCase にするのは「キーが値の別名」のときだけ

**キーが値の別名になっている定数**は、キーも PascalCase にする。値を名前で指すためだけの定数なので、キーは値の綴り違いでしかない。

**それ以外はキーを据え置く。** キーが「何かを引くための見出し」になっているものは、キーの綴りが別の都合（union の値・PDF の名前オブジェクト・型のフィールド名）で決まっている。**`/Type` や `/Filter` の値を見出しにした対応表のキーは、仕様どおりの綴りのまま**にする。

判断の仕方: **その値は語彙そのものか、別のものか。** 値が union の値そのものならキーは値の別名なので PascalCase。値がハンドラ関数・オブジェクトなど**別のもの**なら、たまたま綴りが一致していても見出しなので据え置く。

## ファイル名

- **ファイル名を関数名にしない。** ファイルはモジュールであり、その中の1関数の名前ではない。分割するときはモジュールとして意味のある名前を付ける
- モジュールフォルダは**ケバブケース + `index.ts`**(`object-parser/index.ts` / `graphics-state/index.ts`)
- `ext/` も同じ形だが、export する名前空間オブジェクトは `<型名>Ex`(`string-array/index.ts` → `StringArrayEx`)
- テストファイル名は関数名ではなく**観点のラベル**にする(`rules/testing.md` の命名規則に従う)

## メソッド名を既存の語彙に揃える

コンパニオンオブジェクトのメソッド名は、既にある型の語彙に合わせる。同じ意味の操作に別の名前を与えない。

- **値を組み立てるのは `create`。** 引数から新しい値を作る入口はこれに揃える
- **バイト列・トークン列から読み取るのは `parse*` / `read*`。** 入力が「まだ解釈されていない外部の綴り」であることを名前に出す
- **別の内部表現から作り直すのは `from*`。** 変換元を名前に出す。`create` と使い分ける基準は「引数がその値の材料か(`create`)、別の形で同じものを表しているか(`from*`)」
- **`of*` は使わない。** `create` / `from*` のどちらかに寄せる
- 判定は `is*` / `has*`、変換は `to*` / `*Of`、収集は `collect*`

## `ext/` のメソッドは動詞で始める

`ext/` の `<型名>Ex` は**組み込み型への操作**を集めた場所。メソッド名は**動詞、または結果そのものを表す語**で始め、`with*` の過去分詞にしない。

- **`with*` は値側の語彙。** 「その値を持つ新しい値」を返すコンパニオンオブジェクトのメソッドに使う。`ext/` へ持ち込むと、同じ層の中で語形が 2 通りに割れる
- 条件付きの操作は、条件を名前に出す(`prependIfAbsent`)。**結果の性質**で名付けると、その性質を保証していない実装と食い違う
