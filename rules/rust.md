# Rust 規約

対象は `rust/crates/`（`pdfmod-core`）。TypeScript 実装とは別の再実装であり、**判断の基準は同じでも書き方は Rust の流儀に従う**。

## 前提

- **外部 crate 依存ゼロ。** `std` のみを使う。zlib / inflate などのフィルタ処理も自前で実装する。依存を足さないこと自体が設計制約なので、追加したくなったら実装前に相談する
- **`Result` / `Option` は std のものをそのまま使う。** 汎用のクローンを自作しない
- lint は workspace の `[workspace.lints]` で一元管理する。CI は `cargo fmt --all -- --check` と `cargo clippy --workspace --all-targets -- -D warnings` を通す。**警告は残さない**
- 新しいメンバ crate を足したら、その `Cargo.toml` に `[lints] workspace = true` を書く（書かないと lint 設定が効かない）

## ロジックは impl に置く

**その型の性質を答える処理・その型から別の表現を作る処理は、その型の `impl` に置く。** 自由関数として書かない。判断の起点は「その規則は誰の性質か」で、迷ったら第1引数の型を見る。

- 自由関数として書いてよいのは次の2つだけ。それ以外は `impl` に入れる
  1. **どの型にも属さないアルゴリズムの入口**（`flate::decode_zlib` のような、入力バイト列を受けて出力バイト列を返す変換）
  2. **crate 内に閉じたバイト操作ヘルパー**（`pub(crate)` / `pub(in crate::...)` に限る。公開しない）
- 引数を4つも5つも取る自由関数は、「名前の付いていない型がここにある」というサイン。**その型を作るのが先**
- `impl` ブロック内の自己型参照は必ず `Self` に統一する（`use_self = deny`）。型名のべた書きと混在させない
- `const fn` は const 文脈で実際に必要になった時点で付ける。予防的な一括 `const` 化はしない（`missing_const_for_fn = allow`）

## 不正な値を作れなくする

**「おかしい struct を作れてしまう」状態を残さない。** 検証は呼び出し側の規律ではなく、型の構築経路に閉じ込める。

- **フィールドは私有にする。** `pub struct` のフィールドを `pub` にすると、不変条件を保ったまま値を作る意味がなくなる。外へ出す必要があるものは `pub(crate)` / `pub(in crate::module)` まで絞り、読み取りはアクセサで出す
- **制約のある値は newtype にする。** 裸の `u64` / `usize` / `String` を持ち回らない。取り違えても型エラーにならない値（オフセットと長さ、オブジェクト番号と世代番号）は特に必須
- **制約は型で表現できるならそちらを優先する。** 「1 以上」は実行時チェックではなく `NonZeroU64` を内部表現にする（`ObjectNumber`）。範囲・非空・排他は、まず標準の型で表せないかを見る
- **構築経路は数えられる数に絞る。** 構築関数が増えるほど検証の抜け道が増える。既存の `new` / `try_from_*` / `From` のどれに当たるかを決めてから足す
- **不変条件は doc に書き、その型のすべての API で維持する。** `Lexer` の `0 ≦ pos ≦ input.len()` のように、構造体の doc に不変条件を1行で書き、範囲外の入力はクランプまたは失敗で吸収する

### 検証しない型は「検証しない」と書く

すべての newtype が検証を持つわけではない。**定義域が内部表現の全域と一致する値は無検証で構築してよい**（`ByteOffset` は 0 も `u64::MAX` も受理する）。その場合は doc に**無検証であること**と**妥当性検証を誰が持つか**を書く。書かないと、呼び出し側が「型が付いているから検証済み」と誤読する。

### 状態は判別可能 enum で表す

boolean とフィールドの組み合わせで矛盾した状態が作れてしまうなら、**状態ごとに持つフィールドを変えた enum** にする（`XRefEntry` / `LexOutcome`）。「この状態のときこのフィールドは無効」をコメントで補うのは、型で表せていないということ。

- `match` に `_ =>` の受け皿を安易に置かない。バリアントを足したときに黙って落ちる先を作らない
- **エラーに「実際に来た型」を載せる用途も、文字列ラベルではなくデータを持たない判別 enum で表す**（`ObjectKind` / `TokenKind`）。網羅 `match` が書け、実在しないラベルを混入させられない

## コピーを持ち込まない

**所有はコストなので、必要になる場所まで遅らせる。** 解析器は入力を所有せず借用する。

- **入力は借用で受ける。** 引数は `&[u8]` / `&str` で受け取り、`Vec<u8>` / `String` を要求しない。所有を要求すると呼び出し側にコピーを強いる
- **入力を持つ構造体はライフタイムで借用する。** `Lexer<'a>` / `Parser<'a>` / `BitReader<'a>` のように `&'a [u8]` を保持し、割り当てゼロで走査する。入力を `Vec<u8>` として抱え込まない
- **部分列を返すときはスライスを返す。** 呼び出し側が所有を必要とするかは呼び出し側が決める
- **`clone()` / `to_vec()` は、所有が本当に必要な出口だけ**（展開結果のように新しいバイト列を生むところ）。借用で済ませられないかを先に確かめる。**借用検査を通すためだけの `clone()` は、設計が間違っているサイン**
- **`to_string()` で文字列を作らない。** 表示は `Display` の実装に委譲する。`write!(f, "{}", self.0)` ではなく `fmt::Display::fmt(&self.0, f)` と書く（前者は呼び出し側の書式指定（幅・ゼロ埋め）を捨てる）
- **`Copy` を derive してよいのは小さな値ラッパだけ**（内部が整数1つ程度）。所有データを含む型に `Copy` は付かないし、`Clone` を「とりあえず」付けない
- 走査は `iter()` で回す。要素を複製してから詰め替えない

## panic しない

**production コードに `unwrap()` / `expect()` / `panic!` / `unsafe` を書かない。** 失敗しうる操作はすべて型で返す。

- 範囲外アクセスは添字ではなく `slice::get` の `Option` で吸収する
- 整数演算は `checked_*` / `saturating_*` を使い、暗黙のオーバーフローに頼らない
- `as` によるキャストで値を切り捨てない。幅が変わる変換は `try_from` で失敗を受ける
- テストコードでは `unwrap` / `expect` / `panic!` を使ってよい（失敗したらテストを落としたいため）

## エラーと不在

- **失敗理由が1つしか無く、追加情報が無いなら `Option`。** 「0 だった」「パターンに一致しなかった」はこれにあたる。専用エラー型や `TryFrom` を作らない
- **失敗理由が複数あるか、位置・文脈を載せたいなら `Result` と専用エラー型。** 分類タグ（`PdfErrorCode`）と文脈付きの値（`PdfError`）を分け、呼び出し側が分類で分岐できるようにする
- **失敗の扱いを呼び出し側の文脈ごとに変えたい場合も `Option`。** エラー型を固定すると、呼び出し側が「パースエラー」と「null オブジェクト」を選べなくなる
- 失敗を握りつぶして既定値へフォールバックしない。呼び出し側が分岐できるよう伝播させる

## モジュールとテストの配置

- モジュールは `foo.rs` + 同名ディレクトリ `foo/` の形にする（`mod.rs` は使わない）
- テストは実装ファイル末尾の `#[cfg(test)] mod tests;` から `foo/tests.rs` を指し、`foo/tests.rs` は観点ごとのファイルを `mod <観点>;` で並べる（`parse_version` / `malformed_signature` / `boundary` など）。**小さければ実装ファイル内の `mod tests { .. }` に直接書いてよい**
- 観点の分け方は TypeScript 側と同じで、**ネストした `mod` でグルーピングせずファイルで分ける**
- テストケースの根拠は `docs/specs/` と ISO 32000 に求める。仕様にない振る舞いをテストで固定しない
- **テスト入力は実バイト列（`b"..."` / `&[u8]`）で組み立てる。** 中間表現を手で作ったものだけで通すと、実ファイルで落ちる経路が残る

## doc コメント

- 公開項目には `///`、モジュールには `//!` を書く。**何をするかを 1〜2 文**で書いて終わり
- **不在・失敗を返すなら、どんなときにそうなるかを書く**（`None` を返す条件、エラーの種類）
- **仕様の参照は残す。** `docs/specs/` の節番号・ISO 32000 の節番号は拠り所なので書いてよい
- 型・テスト・lint が守っているものを理由としてコメントに写さない。書くのは**消したら次に読む人が同じ間違いをする事情**だけ（「この委譲を `write!` に戻すと書式指定が捨てられる」など）
- doc 中のコード例は実際にコンパイルされる。例に書いた API を変えたら例も直す

## 禁止事項

- 外部 crate の追加（相談なしに）
- production での `unwrap()` / `expect()` / `panic!` / `unsafe`
- `pub` フィールドによる不変条件の素通し
- 借用で済む場所での `clone()` / `to_vec()`
- 汎用 `Result` / `Option` の自作
- clippy 警告を残したままのコミット
