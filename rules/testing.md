# テスト規約

**基本方針: 古典学派(Classicist / Detroit School)でテストを書く。**

## 配置と命名

モジュールフォルダは `index.ts` を公開APIとし、テストは同フォルダ内の `__tests__/` に置く。

```
<モジュールフォルダ>/
  index.ts                        # 公開API(外部はここからのみ import する)。実装もここに書く
  __tests__/
    <対象モジュール名>.<カテゴリ>.test.ts
```

命名規則: `{テスト対象}.{カテゴリ}.test.ts`(型テストは `.test-d.ts`)

- カテゴリはテストの観点を表すラベル。既に使われているもの(`basic` / `error` / `validation` / `boundary` / `edge` / `integration` / `behavior` / `type`)に合うならそれを使い、**合わないときだけ仕様領域の名前を足す**(`xref-stream` / `inline-image` など)
- **describe のネストの代わりにカテゴリ(=ファイル)で分割する。** 1ファイルが肥大化したらカテゴリを分けること
- 複数ファイルへの分割が必要になったらサブフォルダに分割し、各サブフォルダでも同じ形を保つ

## 古典学派のテスト

2本柱は「**何をテストするか = 振る舞い**」と「**依存をどう扱うか = 実物を使う**」。

### 1. 振る舞い(仕様)をテストする

テストは**外から観測できる振る舞い**に対して書く。実装の内部構造に対して書かない。

- テスト対象は公開API(`index.ts` の export)の「入力 → 出力/最終状態」のみ。内部のヘルパー関数・中間データ構造・処理順序はテストしない
- テスト名は**仕様の文として**書く(「○○のとき□□になる」)。関数名・実装語彙ではなく PDF の語彙を使う
- 1テスト1振る舞い。複数の仕様を1つのテストで検証しない
- **リファクタリング耐性を判断基準にする**: 振る舞いを変えずに実装を書き換えたときに壊れるテストは、実装詳細をテストしている証拠なので書き直す
- **テストケースの根拠は `docs/specs/` と ISO 32000 に求める。** 仕様にない振る舞いをテストで固定しない。仕様が「未定義」としている入力に対する挙動を固定したいなら、まず仕様書側に決定を書く
- **API を作り替えるときは、既存テストの観点を先に数える。** 型名やメソッド名を変えると既存のテストファイルが丸ごと動かなくなるが、そこにある観点(不正なオフセット・循環参照・欠損キー・空入力など)は仕様であって、書き換えの都合で消えてよいものではない。**新しく思いついたケースだけを並べた一覧は、たいてい元より薄い**

### assert は「落ちうるか」と「1つの仕様か」で見る

テスト名が仕様の文になっていても、assert がその仕様を捉えていないことがある。書いたあとに次の2つを確かめる。

**1. その assert は落ちうるか。** 入力にその情報が存在しない状態で「出ない」ことを確かめても、実装が何をしても通る。

判断の仕方: **その assert を通すために実装をどう壊せるかを考える。** 壊し方が思いつかないなら、そのテストは何も守っていない。

- **既定値・フォールバックがある処理では、既定値と違う答えになる入力を選ぶ。** ページ属性の継承のように「規則で決まる答え」と「既定値」が同じ入力を使うと、継承を丸ごと壊しても既定値のほうで通ってしまう
- **「空になる」を確かめるテストには、同じ入力の中に集まる側を1件置く。** 対照を1件置き、期待値を「その1件だけの並び」にすると、集める側を壊しても集めすぎる側を壊しても落ちる
- **`Result` / `Option` は、タグだけでなく中身まで見る。** `result.ok === false` だけの assert は、どんなエラーでも通る。**どのエラーか**まで固定する
- **落ちるか迷ったら、その1件だけ実装を壊して走らせる。** 疑わしい assert 1 つのために分岐を消して 1 ファイル回すだけなら数秒で済む。頭で判断せず確かめる

**2. 1つの assert が複数の仕様を固定していないか。** 解析結果のオブジェクト全体を一括比較すると、テスト名が指していない仕様まで巻き込む。関係のない変更で落ちるため、リファクタリング耐性が下がる。

### 2. モックは原則使わない

依存は実物を使い、相互作用(呼び出し回数・引数)ではなく**結果の状態・戻り値を検証**する。

- **`@pdfmod/core` のテストでモック・スタブ・スパイの使用は全面禁止。** core は純粋なので実物で検証できるはず。モックが必要に感じたら設計を見直す
- `@pdfmod/react` のテストでも、`@pdfmod/core` は必ず実物を使う
- 例外として代替してよいのは**プロセス外・制御不能な境界のみ**(`fetch`・時刻・乱数)。この場合もモックライブラリによる自動モックより、テスト用の単純な実装(フェイク)を優先する
- `vi.mock` によるモジュール丸ごと差し替えは禁止
- 内部実装の呼び出し検証(`toHaveBeenCalledWith` 等)は外部境界の検証以外で使用しない

### テスト入力は実バイト列で組み立てる

PDF の解析は**バイト列が入力**なので、テストもバイト列で書く。中間表現を手で組み立てたオブジェクトだけで通すと、実ファイルで落ちる経路が残る。

- 最小の PDF 断片を `Uint8Array` で組み立て、公開APIに通す。組み立てが2つ以上のテストファイルに現れたら共通のファクトリへ出す
- **仕様が挙げている異常系(壊れた xref・不正な長さ・打ち切られたストリーム)は、実際にその形のバイト列を作って通す**

## テストの書き方: ネスト禁止

Kent C. Dodds の "Avoid Nesting when you're Testing" に従う。

- `describe` のネストは禁止(ファイル直下に `test` / `it` をフラットに並べる。グルーピングが必要ならカテゴリファイルを分ける)
- `beforeEach` での変数共有・ミューテーションは禁止。テストに必要なセットアップは**各テスト内に書く**か、セットアップ関数(`setup()`, ファクトリ)を呼び出す
- テストは1つだけ読めば前提がすべて分かる状態にする
- クリーンアップが必要な場合のみ `afterEach` を許可(リソース解放など、テストの理解に影響しないもの)

## テスト用ヘルパーの置き場所

**テストに書こうとしているヘルパーが汎用の操作なら、それは実装側に足りていない機能。** テストファイルにその場しのぎで書かず、`ext/` やコンパニオンオブジェクトへ実装する。

- 判断軸: そのヘルパーは**テストであることに依存しているか**。`expect` を含む表明はテスト固有だが、「`Ok` から値を取り出す」「バイト列を組み立てる」は汎用操作なので実装側に置く
- **移す前に、その assert がそのヘルパーを必要としていること自体を疑う。** 多くの場合テストが見たいのは整形された綴りではなく**構造**で、構造のまま比べればヘルパーごと要らなくなる
- 同じヘルパーを2つ以上のテストファイルに書いたら、その時点で共通化する(実装側へ移せるならそちらを優先)
- テスト固有のセットアップ(ファクトリ・`setup()`)は各テストから呼ぶ形で共有してよい
