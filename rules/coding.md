# コーディング規約

## コンパニオンオブジェクトパターン

値のロジックは**その値の型自身に閉じ込める**。型と同名の const オブジェクトを定義し、生成・判定・変換ロジックをそこに集約する。

```typescript
export type Color = GrayColor | RgbColor | CmykColor;

export const Color = {
  gray(g: number): GrayColor { /* ... */ },
  defaultBlack(): GrayColor { /* ... */ },
  colorSpaceOf(color: Color): ColorSpace { /* ... */ },
} as const;
```

- 型とコンパニオンオブジェクトは**同一ファイル**で定義する
- ロジック(判定・計算・変換)はコンパニオンオブジェクトのメソッドとして実装する。「複数のモジュールに跨るから」を理由に呼び出し側のヘルパーへ逃がさない

### class は可変な機構にだけ使う

**値を表す型に class を使わない**(type + コンパニオンオブジェクトで統一)。class が正当なのは、**呼び出しをまたいで可変状態を持つ機構**だけ(トークナイザのカーソル、オブジェクトストア、LRU キャッシュ、ドキュメントハンドル)。値なのか機構なのか迷ったら、「2つ作って等値比較したくなるか」で見る。なるなら値なので type にする。

## イミュータブル

**引数で受け取った値を変更しないことは全レイヤー共通の規約。**

- 引数で受け取った配列・オブジェクトを破壊的に変更しない(`push` / `splice` / `sort` / プロパティへの再代入など)。走査中のカーソルやエラー蓄積用の配列も同様で、「内部で使う可変オブジェクト」を引数で引き回さない
- 更新が必要な場合はコピーを作って新しい値を返す(スプレッド構文、`map` / `filter` / `toSorted` など)
- 値を表す型のフィールドはすべて `readonly`
- `let` による再代入も可能な限り避ける。ただしバイト列を1パスで走査するパーサなど、**可変カーソルが処理の本体そのもの**である箇所は class の内部に閉じ込めたうえで使ってよい

## エラーと不在の表現(Result / Option)

**例外を投げない。** 失敗しうる処理は `Result<T, E>` を、値が無いことがありうる処理は `Option<T>` を返す(`packages/core/src/utils/result` / `packages/core/src/utils/option`)。

- **`Result<T, E>`** — 値を生成するか、**エラー情報付きで**失敗する操作に使う
- **`Option<T>`** — 値の有無を表す。エラー情報が要らない場合(検索結果がない、パターン不一致など)
- **`null` / `undefined` を不在の表現に使わない。** 戻り値の `T | undefined` / `T | null` は `Option` に置き換える(`tryReadIndirectRef` の「パターン不一致」は `None`)
- **`Result<void, E>` は避ける。** 成功時に値がない検証系は `Option<E>`(エラーがあれば `Some(error)`、なければ `None`)の方が自然
- `throw` / `try-catch` は使わない。「見つからない」「不正な入力」「循環参照」はすべて `Result.err` / `Option.none` で表現する
- 失敗を握りつぶして既定値へフォールバックしない。呼び出し側が分岐できるよう、そのまま伝播させる(`Result.map` / `Result.flatMap` で連鎖する)
- **同じモジュール内で throw ベースと Result ベースを混在させない。** 公開APIの一部だけを `Result` 化して残りを throw のままにしない

### try-catch は外部 API の境界1箇所だけ

`try-catch` を書いてよいのは、**投げてくる外部 API を包む最小の関数**(`DecompressionStream`・`TextDecoder` など)と、失敗したらテストを落としたいテストコードだけ。包んだ関数は**その場で `Result` / `Option` に詰め替えて返す**。catch した例外を再 throw したり、呼び出し側へ素通ししたりしない。

## 関数のシグネチャ

- **引数は最大3つまで。** 4つ以上になったら、常に一緒に渡る値をまとめた型を作って名前を付ける
- 引数が増える原因が「1件ずつ受け取って呼び出し側でループしている」ことなら、**反復を関数の内側へ移す**(1エントリではなく、まとまり全体を受け取る)
- 同じ型の位置引数が2つ以上並び、取り違えても型エラーにならない場合はオブジェクト引数にする。**オフセットと長さ、オブジェクト番号と世代番号のように `number` が並ぶ箇所は特に危険**
- **意味のないジェネリクスを付けない。** 型引数は、実際に2種類以上の具体型で使われるときだけ導入する

## 値の語彙を型で閉じる

**取りうる値が仕様上決まっているものを `string` / `number` のままにしない。** union 型・テンプレートリテラル型で語彙を閉じ、タイポや単位違いをコンパイルエラーにする。

```typescript
// NG: 任意の文字列が通る
function setFilter(name: string): void { /* ... */ }

// OK: 語彙が型に出る
export type FilterName = "FlateDecode" | "LZWDecode" | "ASCII85Decode" /* ... */;
```

- **`docs/specs/` が列挙している語彙はそのまま union にする。** 定数から導出できる場合は `as const satisfies` で導出し、二重管理しない
- 単位や基数が決まっている値は、それが型に出る形にする。合成順が決まっている値は並びを型に出す
- ただし、キーごとに値域が違うなど**対で縛るコストが釣り合わない場合は無理に縛らない**。縛らなかった理由をコメントに残す
- **前提をコメントで書くのは、型で閉じたことにならない。** 「呼び出し側が保証する」と書いた時点で、それは型ではなく規律に頼っている。引数の説明が「〜であること」の形になったら、その「〜」を型にできないかを先に考える
- **既にある型エイリアスへ付け替えるだけでは閉じられない。** 構造が `number` のままの型に付け替えても、素の `number` がそのまま代入できる
- 閉じたことの確認は**実際に弾かれるか**で行う。素の `string` / `number` を渡すコードを一時的に書いて `tsc` が落ちることを見て、`expectTypeOf` で固定する

### 値の集合から union を導出する

自前で値の集合を定義して union を作る場合は、**定数のオブジェクト + `ValueOf`**(`packages/core/src/utils/types/utility-type.ts`)で書く。値を名前で指せるため、消費側が綴りを直接書かずに済む。走査が必要なときは `Object.values()` で並びにする。

**名前は定数オブジェクトもプロパティも PascalCase にする。** SCREAMING_SNAKE_CASE は使わない。

```typescript
const Mode = { Fill: 0, Stroke: 1, FillStroke: 2 } as const;
type TextRenderingModeValue = ValueOf<typeof Mode>;
```

- **union の型名は単数、定数オブジェクトは複数形**にして両方を同じファイルから export する
- 仕様の数値コードなど**既にある定数から導出する**場合はこの限りではない(出どころの形に従う)

## 不正な状態を型で表現できなくする(型による境界)

**バグは直すのではなく、表現できなくする。** 型は不正な状態をコードの世界に存在させないための境界として設計する。実行時チェックやテストで「見つける」前に、そもそも書けなくすることを考える。

### 正しい状態だけを列挙する

boolean や `Option` の組み合わせで矛盾した状態が作れてしまうなら、**取りうる状態を判別可能な union で列挙**し、状態に応じて持つフィールドを変える。

```typescript
// NG: 「free なのにオフセットがある」「圧縮エントリなのに世代番号がある」が表現できてしまう
type XRefEntry = { type: 0 | 1 | 2; offset?: ByteOffset; generationNumber?: GenerationNumber };

// OK: どの型がどのフィールドを持つかが構造に出る（実際の XRefEntry はこの形）
export type XRefEntry = XRefFreeEntry | XRefUsedEntry | XRefCompressedEntry;
```

判別子は仕様が番号で決めているならその番号でよい（`type: 0 | 1 | 2` は ISO 32000 Table 18 の型番号）。**判別子の綴りを仕様から離して付け替えない。**

### 列挙した状態の網羅を型で強制する

直和で列挙しても、**出し分けの側が網羅していなければ意味がない**。`if` の連なりで書くと最後の枝がラベルの無い受け皿になり、状態を1つ足したときに黙ってそこへ落ちる。

`switch` に `default` を置かずに書き、**戻り値の型を `undefined` を含まないものにする**。case が抜けると「返さない経路がある」(TS2366)としてコンパイルエラーになる。

- 文字列や数値を返す関数は、戻り値を素の `string` / `number` にしておけば同じ効果が得られる
- `default` の追加・`never` への代入・状態をキーにした対応表は要らない

### 生成時に検証し、不正な値を存在させない

制約を持つ値は、コンパニオンオブジェクトの `create` が**検証込みで生成**する(Smart Constructor)。検証に失敗しうるなら `Result` / `Option` を返し、「生成された = 制約を満たしている」を成立させる。生成後に呼び出し側が検証する設計にしない。

### 処理の通過を型に刻む

「ある処理を通過したこと」(解決済みの間接参照・検証済みのオフセット・展開済みのストリーム)が後続処理の前提になる場合、その事実を**構造の違いを持つ型**として表現し、未処理の値を処理済みとして受け渡せない**境界**を作る(Parse, don't validate: 検証は boolean を返すのではなく、検証済みを表す型への変換として書く)。

### ルール

- 消費側の関数は、自分が前提とする状態の型を**引数で要求する**。呼び出し側の規律ではなく型で誤用を防ぐ
- **構造が変わらない型エイリアスの新設は禁止**(`type ResolvedEntry = Entry` 等)。構造的型付けでは何も防がないのに「別の型がある」と誤読させる
- 状態の違いは可能な限り**実在する構造の違い**として表現する(必須キーの追加、値域の狭窄など)
- 狭い型への `as` は、**実行時にその事実を成立させる処理の戻り値1箇所のみ**許可する。境界以外での `as` によるすり抜けは禁止
- ブランド型は構造で表現できない場合の最終手段。防ぎたい誤用が実際にコード上へ現れてから導入する。**綴りは自前で書かず `utils/brand` の `Brand<T, B>` を使う**(目印の `unique symbol` は使う側で宣言する / 同じ制約を持つ値を1つの型にまとめない / 同じ制約の型が2つ以上あるなら互いに代入できないことを `expectTypeOf` で固定する)
- 型レベルの保証が仕様の一部であるときは、`expectTypeOf` によるテストで退行を検知する

## コメントは doc と Why / Why not に絞る

書いてよいのは次の3つだけ。**それ以外は消す。**

1. **doc としての説明** — その関数・型・定数が何か、引数、戻り値、例外的な扱い
2. **その形にした理由** — なぜそう書いたか。型・テストで守れないものだけ
3. **採らなかった理由** — なぜ他の選択肢を採らなかったか(同じ条件)

**呼び名をコメントに書かない。** `Why:` / `Why not:` をラベルとして頭に置かず、理由の文だけを書く。

### doc に書く項目

**doc は「何をするか」を 1〜2 文で書いて終わり。** 2 文を超えたら、下の「消すのは」に当たるものが混ざっているか、理由を概要へ畳んでいるか(理由は段落を分ける)、その関数が2つの役割を持っている。**挙動が及ぶ対象の列挙は概要ではなく仕様**なので、例示と混ぜて削らない。概要と列挙に加えて、**持っている項目だけ**を次の形で書く。

| 持っているもの | 書くこと |
|---|---|
| 引数 | `@param <名前>` — その引数が何を表すか |
| 戻り値(`void` 以外) | `@returns` — 何を返すか。不在・失敗を返すなら**どんなときにそうなるか** |
| 型引数 | `@typeParam <名前>` — 何を表す型か |

- **型の再掲は書かない。** 書くのは**その引数が何を表すか**・**満たしている前提**・**取りうる値の意味**
- `@returns` は「返り値の型」ではなく**中身**を書く。`Option` / `Result` を返すなら、`none` / `err` になる条件を書く
- **仕様の参照は残す。** `docs/specs/` の節番号や ISO 32000 の節番号は拠り所なので、doc に書いてよい

### Why と Why not は別物として書く

**理由は原則書かない。型・テスト・lint が守っているものは、そこが答えなのでコメントへ写さない**(「`default` を置かないので case の抜けがコンパイルエラーになる」「一致は `xxx.test.ts` が固定する」は、どちらもコードとテストを読めば分かる)。素直に書いてそうなった実装・自明な分岐も同じ。

書くのは**消したら次に読む人が同じ間違いをするもの**だけで、型やテストで表現できず外すと壊れるのに壊れたことに気づけない事情がそれに当たる。それを書くときは、実際に検討して捨てた案の Why not も 1〜2 行で添えて検討を一度で終わらせる。

- **理由の根拠に、いま直されつつある一時的な事実を置かない。** 直った瞬間に理由が嘘になる
- **理由は1つにつき1〜2行**に収める。3行以上要るなら、それは Issue に書くべき経緯が紛れ込んでいる

消すのは **型・テストが守っている理由** / **What の言い換え** / **コード内の値の再掲** / **1 つ挙げれば足りる例示** / **経緯・実行履歴** / **Issue 番号**(判断の履歴は Issue が、変更の理由はコミットが持つ) / **一般論**。判断軸は「これを消したら、次に読む人が同じ間違いをするか」。しないなら消す。

## 外部の挙動は動かして確かめる

シェル・CLI・外部フォーマット・Web 標準 API の挙動を前提にしたコード(CI スクリプト・lint 設定を含む)は、**正しく動くはずという想定だけで書かない。** 依存する挙動を小さく再現して確かめてから使う。**PDF の実ファイルが相手なら特に**、仕様の読みだけで分岐を決めず、実バイト列で確かめる。

## 規約の適用範囲

**この規約は `packages/*/src/` の TypeScript だけでなく、`.claude/` `.github/` などツール側のコード・doc にも及ぶ。** 「TypeScript 前提の書き方だから対象外」と読み違えない。

- ブロックのネスト制限・条件式に名前を付ける、は対象言語を問わず適用する
- 「同じ処理が2箇所に現れたら共通化する」は、コードだけでなく**同じ判断根拠を説明する doc・README の重複**にも適用する。片方だけを直せる状態を作らない

## 禁止事項

- `any` の使用
- `@pdfmod/core` での I/O(console, fs, fetch, DOM 等)
- **同じ処理が2箇所に現れたまま放置する**(実装・テストとも)。汎用操作なら `ext/`、値の規則ならコンパニオンオブジェクトへ
- 長い配列の結合をインラインのスプレッドで書く(中身に名前を付けた変数へ入れてから結合する)
- ブロックのネストが `max-depth`(現在 4 段)を超える書き方
- 実装と食い違ったままのコメント(実装を変えたらコメントも同時に直す)
