カタログにある。

文書全体の設定を束ねる「ドキュメントカタログ」を、PDFの記述と今回のRust実装から読み解きます。

01

カタログは、文書全体の入口

PDFでは、ページ・フォント・しおりなどをオブジェクトとして保存し、参照でつなぎます。その中で、文書全体のルートに当たる辞書が Document Catalog（ドキュメントカタログ）です。

トレイラ辞書の /Root は、そのカタログを指します。カタログの /Pages を辿ると、各ページにつながるページツリーの根へ進めます。

今回：子の参照を保持するところまで。参照先の解析は後続処理です。

図は参照関係を示します。ファイル内の物理的な並び順ではありません。ページツリーの途中には複数のPagesノードが入ることもあります。

PHYSICAL INDEX

xref：どこにあるか

オブジェクト番号から、ファイル中の位置やオブジェクトストリーム内の格納先を調べます。

LOGICAL ROOT

Catalog：何につながるか

ページツリーやしおりなど、文書を構成する要素への入口と、文書全体の設定を持ちます。

02

PDF記述を、ひとつずつ読む

次は構造を説明するための抜粋です。実ファイルには、これに加えてxref・ヘッダ・ページオブジェクトなどが必要です。

% カタログ本体
1 0 obj
<<
  /Type       /Catalog
  /Pages      2 0 R
  /Version    /1.7
  /PageLayout /OneColumn
  /PageMode   /UseOutlines
  /Outlines   10 0 R
>>
endobj

% トレイラの抜粋
trailer
<< /Size 11 /Root 1 0 R >>

記号の意味

1 0 obj … endobj
オブジェクト番号1・世代番号0の間接オブジェクトを定義します。

<< … >>
キーと値を持つ辞書です。

/Type /Catalog
キーが Type、値が Catalog という名前オブジェクトです。

/Pages 2 0 R
キーが Pages、値が別のオブジェクトへの間接参照です。

2 0 R の3要素

2オブジェクト番号
0世代番号
R間接参照を示す記号
「2ページ目」への参照ではありません2 0 R はオブジェクトを識別する値です。ページ番号でもバイト位置でもありません。実際の格納場所はxrefとObjectResolverが調べます。
名前と文字列は別の型/Catalog は名前、(Catalog) は文字列です。同じ文字に見えても、/Type に文字列を渡すと今回の検証ではエラーになります。
03

必須なのは、TypeとPages

カタログとして構築できるのは、/Type /Catalog と /Pages の間接参照を持つ辞書です。Rustの Catalog は、これらの条件を検証してから生成されます。

キー必須 / 任意今回の取り扱い
/Type必須名前 /Catalog に一致すること。
/Pages必須間接参照であること。直接辞書や整数は不可。
/Version任意対応する版を示す名前。省略時はヘッダの版。
/PageLayout
/PageMode		任意名前をenumに変換。省略・未知の名前には既定値。
その他のキーキーによる値を保持。この段階では個別に解釈・検証しない。
TRY IT — 入力例を切り替えて検証結果を見る
<< /Type /Catalog /Pages 2 0 R >>

成功：カタログとして構築できる

Pagesの参照を保持します。PageLayoutはSinglePage、PageModeはUseNoneです。Pagesの参照先はまだ読み込みません。

この切り替えは実装に対応した説明用の例です。ブラウザ上でRustパーサを実行しているわけではありません。

「参照の形が正しい」と「参照先が正しい」は別の確認/Pages 2 0 R があれば、この段階の型検証は通ります。オブジェクト2が実在するか、ページツリーとして正しいかは、参照先を読む後続処理で確認します。

辞書中の null は不在として扱われます。たとえば /Pages null は必須キー欠落になります。任意キーの /PageMode null なら既定値を使います。

04

新しいバージョンを優先する

PDFの版は、ファイルヘッダの %PDF-1.4 などで宣言されます。カタログに /Version がある場合、ヘッダより新しければ、その版を有効バージョンとして採用します。古い値によって版を下げることはありません。

effective = max(header, catalog)
TRY IT — ヘッダとカタログの版を比較する
1.7
有効バージョン

カタログの1.7がヘッダの1.4より新しいため、1.7を採用します。

ヘッダカタログ有効な版理由
1.41.71.7カタログ側が新しい。
1.71.41.7ヘッダ側が新しい。
1.7省略1.7ヘッダの宣言を使う。
1.71.71.7同じ版なので変更なし。
今回の実装で受け付ける値は？

PdfVersion が表現する1.0〜1.7と2.0です。/Version /1.8 や /Version /garbage は InvalidVersion。/Version (1.7) は名前ではないため InvalidKeyType になります。

declared_version() はカタログに書かれた版、version() は比較後の有効バージョンを返します。両方を区別して保持します。

版の宣言は、機能実装の保証ではありません2.0という版を読み取れることと、PDF 2.0の全機能を処理・描画できることは別です。

06

読まない情報も、失わずに残す

カタログには、今回扱う項目以外にも多くの情報があります。それを削除せず、元の辞書を保持したまま、必要な値だけ型として取り出す方針です。

<< /Type /Catalog
   /Pages 2 0 R
   /Names 3 0 R
   /Outlines 4 0 R
   /AcroForm 5 0 R
   /VendorKey [6 0 R (data)]
>>

今回ここでは行わないこと

名前辞書の解析、しおりの列挙、フォームフィールドの解析、独自キーの解釈。

たとえば /Names 3 0 R は、その参照を保存します。この時点でオブジェクト3を読み込むことはありません。

元の辞書はそのまま

既知キー・未知キーの両方を保持します。設定値の正規化で元の辞書を書き換えません。

必要な部分だけ型にする

Pagesの参照、宣言された版・有効な版、配置・表示モードを取り出します。

後続処理が必要な情報を取得

entry(b"Names") などで生の値を取得し、必要になった段階で参照先を解決します。

NamesやAcroFormが直接辞書でも保持できます/Names << /Dests 3 0 R >> のような値も、その形のまま保持します。「未解釈のまま保持する」とは、全項目を間接参照に変換することではありません。

Rustでは Rc<PdfObject> によってObjectResolverと所有を共有します。大きな辞書を丸ごと複製せず、カタログ側からも元のオブジェクトを読み取れます。

07

Rootの解決と、位置付きエラー

ObjectResolver::catalog() は次の順に動作します。カタログを取得しても、PagesやNamesの参照先はまだ読み込みません。

トレイラからRootと位置を取得

Trailer::root() と Trailer::position() を読み取ります。

ObjectResolverでRootを解決

xrefを使って参照を辿ります。参照チェーンやオブジェクトストリーム内の格納にも対応します。

解決結果をCatalogとして検証

辞書・必須キー・各設定値を検証し、有効なバージョンを決めます。

状況今回返すエラー意味
Rootが未定義・解放済みNotADictionary { actual: Null }Resolverがnullを返すため、辞書の検証で失敗。
Rootの先が整数などNotADictionary参照は解決できても、カタログの形ではない。
参照循環・構文不正などRootResolutionFailed下位の ResolveError を保持。
TypeやPagesがないMissingRequiredKeyどの必須キーが欠けたかを保持。
型が不正 / Typeの値が違うInvalidKeyType / InvalidType型の誤りと名前の不一致を区別。
トレイラを持たないResolverMissingTrailerObjectResolver::new() はトレイラを保持しない。
エラーのpositionは、何の位置？catalog() から返すエラーは、参照元トレイラの位置を持ちます。問題のあるキーそのものや、カタログ本体の開始位置を示すわけではありません。従来形式ではトレイラ辞書の開始位置です。トレイラがない場合はヘッダの開始位置を使います。

Catalog::from_object() を直接呼ぶ場合は、呼び出し側が位置を渡します。エラーの種類を示す kind() と、文脈の位置を示す position() を分けて取得できます。

08

Rust APIにつなげて理解する

PDFバイト列からの利用例です。open() でヘッダとxrefを解析した後、catalog() でRootの先を取得します。

use pdfmod_core::resolver::ObjectResolver;

fn inspect(pdf_bytes: &[u8]) {
    let mut resolver = match ObjectResolver::open(pdf_bytes) {
        Ok(resolver) => resolver,
        Err(error) => {
            eprintln!("open failed: {error:?}");
            return;
        }
    };

    let catalog = match resolver.catalog() {
        Ok(catalog) => catalog,
        Err(error) => {
            eprintln!("catalog failed: {:?}", error.kind());
            eprintln!("context position: {:?}", error.position());
            return;
        }
    };

    // Pagesはまだ参照のまま
    println!("pages: {:?}", catalog.pages());
    println!("effective version: {}", catalog.version());
    println!("layout: {:?}", catalog.page_layout());
    println!("mode: {:?}", catalog.page_mode());

    // 未解釈エントリも読み取れる
    println!("names: {:?}", catalog.entry(b"Names"));
}
API返す内容
pages()ページツリーのルートへの IndirectRef。
declared_version()カタログで宣言された Option<PdfVersion>。
version()ヘッダとの優先比較を適用した PdfVersion。
page_layout() / page_mode()既定値を適用した PageLayout / PageMode。
entry(key)辞書の値を借用。キーがなければ None。
object()元の辞書オブジェクトへの &PdfObject。
