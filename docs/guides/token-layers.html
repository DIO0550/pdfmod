字句トークンと
描画命令の境界

同じ m でも、字句解析では「キーワード」、ページの描画命令では「演算子」です。文字を読み取る処理と、その意味を判断する処理を分けると、型も自然に分かれます。

字句解析 / LexicalToken命令の分類 / ContentStreamToken
01

「読めたもの」と「命令」を分ける

字句解析（lexical analysis）は、PDFのバイト列を数値・名前・文字列・区切りなどの小さな単位へ分ける処理です。この単位をトークン（token）と呼びます。

文字の形を読む

Tokenizer

10 を整数、/F1 を名前、(Hello) を文字列として読みます。m のような一般の綴りは Keyword になります。

結果：LexicalToken

描画命令の文脈で読む

ContentStreamTokenizer

ページのコンテンツストリーム（content stream）は描画命令の列です。字句解析の結果を使い、キーワードを演算子へ分類し直します。

結果：ContentStreamToken

トークンは、まだ完全なPDFオブジェクトではない[10 20] は、字句解析では配列開始・整数・整数・配列終了の列です。配列という1つの値へまとめるのは、その後のオブジェクト解析です。
02

同じ入力を、2つの層で読む

次はコンテンツストリームの抜粋です。完全なPDFファイルではありません。

10 20 m

オペランド（operand）は命令の引数、演算子（operator）は実行する命令です。PDFは引数を先に書く後置記法を使うので、この例は「座標 (10, 20) へ移動して新しいサブパスを始める」という命令になります。

字句解析の結果

Integer  value: 10  offset: 0
Integer  value: 20  offset: 3
Keyword  value: "m" offset: 6
EOF      value: null offset: 7

数値と綴りを読んだだけです。m を命令として実行しません。

コンテンツストリームの結果

Integer  value: 10  offset: 0
Integer  value: 20  offset: 3
Operator value: "m" offset: 6
EOF      value: null offset: 7

m の種類だけが変わります。綴りと元の位置は引き継ぎます。

offset は入力の先頭から数えたバイト位置です。実装では ByteOffset 型を使います。上の結果は読みやすさのために数値で表記しています。

分類と実行は別の処理Operator にできても、引数の数や種類が正しいとは限りません。引数を検証して命令を実行するのはインタプリタと演算子ハンドラです。
03

型には、その層が扱うものだけを入れる

union型（直和型）は、列挙した型のどれか1つを表します。LexicalToken は字句解析が生成する13種類、ContentStreamToken はそれに2種類を加えた型です。

type ContentStreamToken =
  | LexicalToken
  | Operator
  | TokenInlineImage;
「起こらない可能性」を利用側に背負わせない以前の全体型 Token を字句解析の戻り値にすると、演算子や画像が返る可能性まで表します。LexicalToken に狭めれば、オブジェクト解析がその可能性を考える必要がなくなります。

ContentStreamToken は型として LexicalToken 全体を含みます。ただし、このトークナイザが実際に読む Keyword は演算子へ再分類され、BI はインライン画像の読み取りへ進みます。

04

同じ字句解析を、用途ごとに使う

次の図は、字句トークンを使う2つの処理経路です。

戻す入口も、字句トークンに限定する

BufferedTokenizer は先読みしたトークンを戻せる機構です。戻り値だけを狭めても、戻す入口が広いままでは演算子を混ぜられるため、pushBack の引数も狭めます。

next(): LexicalToken
pushBack(token: LexicalToken): void
このコードはコンパイルエラーになるコンテンツストリームの演算子を、一般の字句トークンのバッファへ戻すことはできません。
const operator = Operator.of("m", ByteOffset.of(6));

buffered.pushBack(operator);
// エラー：Operator は LexicalToken に代入できない
05

演算子の綴りも value へ揃える

キーワードが演算子に変わっても、綴りそのものは変わりません。どちらも value に保存すれば、分類だけを変えたことが構造にも表れます。

分類する前

{
  type: TokenType.Keyword,
  value: "m",
  offset: ByteOffset.of(6)
}

分類した後

{
  type: TokenType.Operator,
  value: "m",
  offset: ByteOffset.of(6)
}
参照する場所変更前変更後
演算子の綴りoperator.nameoperator.value
表示用の文字列演算子だけ name を読む専用分岐他の値トークンと同じく value を文字列化
インライン画像dict と data を保持同じ構造を維持。表示は BI ... ID ... EI

Operator.of(value, offset) が演算子を生成します。インタプリタは token.value でハンドラを検索し、未知の命令の警告にも同じ値を使います。

画像まで1つの value に揃えるわけではない画像は「辞書」と「バイト列」という複合情報を持つため、dict と data に分けます。画像の辞書値は ReadonlyArray<LexicalToken> とし、演算子や画像トークンを混ぜません。
06

具体例で境界を確認する

以下は説明用のPDF記述の抜粋です。結果は実装・テストに基づく例で、HTML内でパーサーを実行しているものではありません。

① スラッシュと括弧で種類が変わる

/m (m) m
入力字句解析コンテンツストリームの分類
/mNameName を維持。演算子にしない
(m)LiteralStringLiteralString を維持
mKeywordOperator
true false nullBoolean / Boolean / Null字句解析の時点で値に分類されるため、種類を維持

/m (m) m は分類を比較する例です。移動命令の引数が数値ではないため、そのまま正常に描画できる命令列ではありません。

② インライン画像は1トークンにまとめる

BI /W 1 /H 1 /BPC 8 /CS /G
ID A EI

BI は画像の開始、ID は辞書と画像データの境界、EI は終了です。/W・/H は幅・高さ、/BPC は成分あたりのビット数、/CS /G はグレースケールの指定です。1バイトの A を説明用の画素データにしています。

字句解析器だけの場合

BI や ID は一般のキーワードです。画像領域の開始を理解しないため、生の画像バイト列を安全に区切る役割は持ちません。

コンテンツストリームの場合

BI から専用の読み取りへ進み、辞書と生バイト列を1つの TokenInlineImage にまとめます。画像内部のバイト列は描画命令として再分類しません。

③ 空入力・未知の命令・壊れた画像

入力読み取り結果意味の判定
空のバイト列どちらも EOF のみ。コンテンツ側は Result.ok で返す終端は value: null。PDFの Null とは type で区別
1 2 xyzxyz は字句解析ではキーワード、コンテンツ側では演算子未登録ならインタプリタが UNKNOWN_OPERATOR を記録し、引数スタックを空にして継続する実装方針
BI /W 1コンテンツ側で Result.errID がないため CONTENT_STREAM_INLINE_IMAGE_INVALID。失敗の位置もエラーに含む
分類できたことは、命令の妥当性を保証しないOperator.of は未知の綴りや空文字も受け取れます。既知の命令か、引数が妥当か、実行できるかは後続処理の責務です。

戻り値の読み方

Tokenizer.nextToken(): LexicalToken
Tokenizer.tokenize(): LexicalToken[]

ContentStreamTokenizer.nextToken():
  Result<ContentStreamToken, PdfError>

ContentStreamTokenizer.tokenize():
  Result<ContentStreamToken[], PdfError>

一括読み取りの成功結果は、末尾のEOFも含みます。既存の Token 型は ContentStreamToken の非推奨エイリアスとして残しています。新しい利用箇所では層に合う型を使います。

この変更で学ぶ3つのこと① 字句を読むことと命令の意味を決めることを分ける。
② 本当に扱う値を、引数・戻り値の型に表す。
③ 分類を変えても、綴りと元の位置は保持する。

型の分離は、PDFの字句規則や描画命令の動作を変更するものではありません。コンテンツストリームを渡す前の圧縮解除、画像データのデコード、画面への描画はそれぞれ別の処理です。
