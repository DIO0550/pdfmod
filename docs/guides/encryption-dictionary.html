PDF INTERNALS / ENCRYPTION DICTIONARY

暗号化辞書を読む

PDFの /Encrypt は、暗号化の方式と鍵の材料を記述します。アルゴリズムの版、crypt filter、権限を、解釈できる型へ変換する仕組みを見ていきます。

01

暗号化の起点

トレイラの /Encrypt が暗号化辞書を指します。直接辞書でも間接参照でも書けます。暗号化辞書自体は復号前に読む必要があるため、オブジェクトストリームには格納できません。

セキュリティハンドラ

Security handler はパスワードなどからアクセスを認証する方式です。/Filter /Standard はパスワードベースの標準ハンドラを表します。

暗号化される値

対象は文字列とストリームです。辞書のキー名、名前オブジェクト、数値は暗号化されません。暗号化文書のトレイラには /ID が必要です。リビジョン2〜4では、その第1要素を鍵導出に使います。

辞書から読み取れること辞書の型変換では方式と鍵の材料が得られます。Rustでは、リビジョンに応じた鍵導出とパスワード認証にその材料を渡します。
02

辞書を読む

以下は説明用の抜粋です。暗号鍵の材料は短縮しており、完全なPDFや復号可能な鍵の例ではありません。

trailer
<< /Root 1 0 R /Size 20 /Encrypt 8 0 R
   /ID [<00112233> <00112233>] >>

8 0 obj
<< /Filter /Standard /V 4 /R 4 /Length 128
   /O <00FF> /U (user) /P -4 /EncryptMetadata false
   /CF << /StdCF << /CFM /AESV2 /Length 16 >> >>
   /StmF /StdCF /StrF /StdCF >>
endobj

8 0 R はオブジェクト番号8・世代番号0への間接参照です。<< >> は辞書、<00FF> は16進形式のバイト列、(user) はリテラル文字列です。/O と /U はテキストとして復号せず、元のバイト列を保持します。

キー意味保持・検証
/Filter /V /Rハンドラ名・アルゴリズム版・リビジョンStandard では必須。版の組を型へ変換
/Lengthファイル暗号鍵のビット数V2・V4 は40..128の8の倍数。省略時40
/O /U所有者・利用者パスワード由来の値必須のバイト列。長さは検証しない
/OE /UE /Perms暗号化ファイル鍵と権限のコピーR5・R6で必須のバイト列
/EncryptMetadataメタデータを暗号化するか省略時 true。指定時は真偽値が必要
/V の必須扱いはpdfmodの方針PDF仕様には /V の既定値0がありますが、pdfmodは省略を構造不正として返します。明示された /V 0 は未対応として保持します。省略と未対応は別の結果になります。
03

/V × /R の有効な6組

版とリビジョンを独立した任意の数値にすると、仕様にない組を作れてしまいます。StandardAlgorithm は有効な組だけを判別可能な union として表します。

型の種別/V/Rファイル鍵長と付随する値
V1R212RC4・40ビット固定
V1R313RC4・40ビット固定
V2R323RC4・/Length による可変長
V4R444/Length と crypt filter
V5R555AES-256・crypt filter と /OE /UE /Perms
V5R656AES-256・crypt filter と /OE /UE /Perms

V1とV5の鍵長は版から確定するため、直下の /Length を使用しません。V5R5はISO 32000-2で非推奨のリビジョンですが、辞書の構造は読み取れます。

未対応は構造不正と区別するV0は未文書化、V3は非公開の方式です。表にない組や /Adobe.PubSec などのハンドラは Unsupported として、元の辞書を欠損なく保持します。
04

crypt filter と鍵長の単位

Crypt filter は暗号方式の名前付き設定です。/CF が名前と設定の対応表になり、/StmF がストリーム、/StrF が文字列、/EFF が埋め込みファイルへの割り当てを表します。

暗号方式 /CFM

/None は暗号化なし、/V2 はRC4、/AESV2 はAES-128、/AESV3 はAES-256です。省略時は /None。未知の方式はエラーです。

組み込み /Identity

暗号化しない指定で、/CF 内の定義は不要です。StmF・StrFの省略時もIdentityになります。EFFの省略は None として保持します。

/Identity 以外のセレクタは /CF に定義されていなければなりません。pdfmod はV4・V5で /CF を必須にする実装上の制限を持ち、空辞書は受理します。

/CF 内の /Length入力の解釈正規化結果
5 / 16バイト表記40 / 128 ビット
40 / 128ビット表記40 / 128 ビット
17 / 44 / 256受理する鍵長に該当しない無視して None
名前・実数・間接参照整数の直接値ではない解決せず None
直下の /Length と /CF 内は別の規則ISOは /CF 内の鍵長をバイト単位としますが、ビット表記のPDFも存在します。RustとTypeScriptは5..16を8倍し、それ以外をビット数として扱い、40..128の8の倍数だけを保持します。これはpdfmodの正規化規則です。AESV3自体は表現できますが、/CF の32・256はこの規則では保持しません。V5のファイル鍵長は256ビット固定です。

TypeScriptの CryptFilter も方式で分岐するunionです。AESV2の keyLength は128、AESV3は256という固定値の型です。一方、length は入力辞書の /Length を正規化して保持する値であり、AESの固定鍵長を上書きしません。V2（RC4）の指定長は length で読み、省略はNoneのまま扱います。

/AuthEvent は認証の時点です。/DocOpen は文書を開くとき、/EFOpen は埋め込みファイルを開くときです。pdfmodは省略・未知名・型不一致をDocOpenへ戻します。

05

/P のビット表現

Permissions は印刷・変更・抽出などのアクセス権限をビットで表します。例えば第3ビットは印刷、第5ビットは抽出、第12ビットは高解像度の印刷です。ビットが1なら許可を表します。

4294967292 と -4 は同じ32ビット

仕様の符号付き表記は /P -4 ですが、符号なし表記の /P 4294967292 を書くPDFもあります。どちらも permissions.bits = -4 に正規化します。

受理範囲は -2147483648..4294967295 の整数です。範囲外は INVALID_PERMISSIONS になります。権限を実際に強制する処理は今回の対象外です。

06

正常・未対応・不正を比べる

以下は暗号化辞書の抜粋です。短い /O・/U は辞書解析の例で、鍵導出に必要な長さは表していません。

正常：最小のV1R2

<< /Filter /Standard /V 1 /R 2 /O () /U () /P -4 >>

Standard。40ビット固定、EncryptMetadataはtrue。空の鍵材料も長さ検証なしで保持します。

未対応：有効な型へ変換しない組

<< /Filter /Standard /V 1 /R 6 /Custom (keep) >>

Unsupported。後続の必須キーは要求せず、Customを含めて元の辞書を保持します。

未対応：公開鍵ハンドラ

<< /Filter /Adobe.PubSec /Recipients [(opaque)] >>

Unsupported。V・Rやハンドラ固有のキーを解釈しません。

不正：直接値が必要なキーの間接参照

<< /Filter /Standard /V 2 /R 3 /Length 5 0 R
   /O () /U () /P -4 >>

/Length 自体は省略可能ですが、V2・V4で指定する場合は整数の直接値が必要です。この例は INVALID_KEY_TYPE、キーは /Length になります。辞書内部の参照は解決しません。エラーには呼び出し側が渡した辞書のバイト位置を付けます。

07

解析の境界と対応範囲

  1. 解決済みの暗号化辞書を EncryptDictionary.fromDictionary(dictionary, offset) へ渡す。
  2. Filterを検証する。未知のハンドラならUnsupportedとして保持する。
  3. StandardではV・Rを必須の整数として読む。対応外の組ならUnsupportedとして保持する。
  4. 対応する組に必要な鍵長・crypt filter・追加鍵を読む。
  5. 共通のO・U・P・EncryptMetadataを読み、Standardを返す。
位置は辞書単位エラーの offset は渡された辞書の開始位置です。/CF/StdCF/CFMのようなキーのパスは報告しますが、個々の値の物理位置は取得しません。

キーと期待型を表す PdfDictionaryField と直接値の取得・型チェックは、PDF共通の PdfDictionaryReader が担当します。暗号化側はそのエラーを EncryptError に変換し、暗号化固有の制約を検証します。

入力辞書からキーを削除したりバイト列を書き換えたりしません。必須キー欠落、型不一致、不正なファイル鍵長、未定義セレクタはResultのエラーで返します。

TypeScriptの PdfDocument.load は引き続き暗号化PDFを ENCRYPTED_PDF_UNSUPPORTED として拒否します。Rustではパスワード認証済みの ObjectResolver::open_authenticated から文字列・ストリームの遅延復号を利用できますが、Rust PdfDocument のパスワード受付はまだ公開していません。

TypeScriptで解析結果を読む

次の例は公開APIを使い、辞書の抜粋をバイト列から読み取ります。ObjectParser はPDFの構文を辞書へ変換し、EncryptDictionary はその辞書を暗号化方式の型へ変換します。トレイラから /Encrypt を探す処理は含みません。

import {
  ByteOffset,
  EncryptDictionary,
  ObjectParser,
  StandardAlgorithm,
} from "@pdfmod/core";

function inspectEncryption(bytes: Uint8Array, offset: ByteOffset): string {
  const parsed = ObjectParser.parse(bytes, offset);
  if (!parsed.ok) {
    return parsed.error.message;
  }

  if (parsed.value.type !== "dictionary") {
    return "暗号化辞書が必要です";
  }

  const result = EncryptDictionary.fromDictionary(parsed.value, offset);
  if (!result.ok) {
    return `${result.error.key}: ${result.error.message}`;
  }

  if (result.value.type === "Unsupported") {
    return `未対応: ${result.value.filter}`;
  }

  const { algorithm, permissions } = result.value.handler;
  const bits = StandardAlgorithm.keyLength(algorithm);
  return `${algorithm.kind} / ${bits} bits / P=${permissions.bits}`;
}

const bytes = new TextEncoder().encode(
  "<< /Filter /Standard /V 1 /R 2 /O () /U () /P 4294967292 >>",
);
const summary = inspectEncryption(bytes, ByteOffset.of(0));
// summary は "V1R2 / 40 bits / P=-4"
  • ByteOffset はバイト位置を表す型です。この例の辞書は入力の先頭にあるので、位置が確定した定数0に of(0) を使います。外部入力の数値には、検証する create を使います。
  • Result は成功と失敗を値で表す型です。ok がfalseなら error、trueなら value を読みます。Unsupported は失敗ではなく、解釈せず保持できた成功です。
  • 判別可能なunionは、type や kind の値で中身の型が決まる仕組みです。未対応の分岐を抜けるとStandardだけが残り、handler を安全に読めます。
  • 鍵長は algorithm.keyLength または StandardAlgorithm.keyLength から読みます。V1の型は40、V5の型は256に限定され、異なる鍵長を代入すると型エラーになります。V2・V4も40〜128の8刻みだけを許します。
08

方式ごとの型に生成を任せる

/V と /R を読むと、どの方式として辞書を解釈するかが決まります。その先の読み取りは、選ばれた方式の型が担当します。例えば V2R3 は可変鍵長、V4R4 は可変鍵長とcrypt filter、V5R6 はAES-256用のパラメーターを読み取ります。

TypeScriptの type は実行時には消えるため、型の宣言だけでは処理を実行できません。そこで同じ名前の const に生成関数を置きます。この組をコンパニオンオブジェクトと呼びます。型注釈の V5R6 は値の形を表し、V5R6.fromDictionary(reader) は実際の読み取り処理を呼びます。

型生成入口担当する内容
V1R2 / V1R3create()40ビット固定の値を生成。追加の辞書項目は不要
V2R3fromDictionary(reader)直下の /Length。省略時40ビット、不正値はエラー
V4R4fromDictionary(reader)直下の /Length とcrypt filterの定義・割り当て
V5R5 / V5R6fromDictionary(reader)256ビット固定、crypt filter、/OE・/UE・/Perms

全方式の入口は、選択して委譲する

次は実装の抜粋です。StandardAlgorithm は6つの名前付き型をまとめたunionです。入口が /V 5 /R 6 を選ぶと V5R6 へ委譲します。map は成功値だけを some で包み、失敗はエラーのまま返します。未対応の組は none として、生辞書を保持する処理へ戻ります。

export type StandardAlgorithm =
  | V1R2 | V1R3 | V2R3
  | V4R4 | V5R5 | V5R6;

// StandardAlgorithm.fromDictionary の分岐の抜粋
case "5:6":
  return map(V5R6.fromDictionary(reader), some);

共通の材料を使っても、生成結果はその方式だけ

V5R5 と V5R6 は、辞書から読む項目が共通です。これを内部の Aes256Parameters にまとめ、両方式から利用します。& は型の交差で、共通項目に kind: "V5R6" を加えます。同じ項目を持っていても kind が違うため、V5R5の値をV5R6の値として渡すことはできません。

// importを省略した実装の抜粋
export type V5R6 = Aes256Parameters & {
  readonly kind: "V5R6";
};

export const V5R6 = {
  fromDictionary(reader: PdfDictionaryReader): Result<V5R6, EncryptError> {
    return map(Aes256Parameters.fromDictionary(reader), (parameters) => ({
      ...parameters,
      kind: "V5R6",
    }));
  },
} as const;

成功した戻り値は StandardAlgorithm 全体ではなく V5R6 です。呼び出し側は、もう一度方式を調べずに keys や固定値256の keyLength を扱えます。可変鍵長の読み取りは KeyLength.fromEncryptionDictionary、AESの追加鍵の読み取りは AesKeyMaterial.fromDictionary が共有します。

  1. PDFの辞書を読む入口

    外部入力には EncryptDictionary.fromDictionary を使います。ハンドラ名と /V・/R の判定、方式の生成、共通キーの読み取りをつなぎます。

  2. 選択された方式の項目を読む

    各方式の fromDictionary は方式固有の項目を読みます。/V・/R 自体の再判定や、共通の /O・/U・/P の検証は担当しません。

  3. 正常・省略・不正を値として返す

    V2R3で /Length 128 は128ビット、省略は40ビット、/Length 44 はキー /Length と辞書開始位置を持つエラーになります。生成処理を分けても、この解析方針は変わりません。

辞書の解析が担当する範囲V4R4ではcrypt filterから暗号方式を選びます。辞書解析は鍵材料のバイト列をそのまま保持します。Rustのバイト列変換は RC4の解説 で扱います。
09

旧リビジョンの鍵導出とMD5

標準セキュリティハンドラのリビジョン2〜4では、パスワードとPDFに記録された値からファイル暗号鍵を導出します。この手順で使うMD5は、任意長のバイト列を16バイトのダイジェストに変換するハッシュ関数です。

PDFから取り出す鍵の材料

qpdfで生成したリビジョン4のPDFから、暗号化辞書とトレイラを抜粋します。トレイラはPDF末尾にある辞書です。/Encrypt 5 0 R は、オブジェクト番号5・世代番号0の暗号化辞書を参照します。

% 利用者パスワード user で開けるテスト用 PDF の抜粋
5 0 obj
<< /Filter /Standard /V 4 /R 4 /Length 128
   /O <0ba3835f88f90388e74e54584125ce142be0de24c6b0d37746e075b891756671>
   /U <3250600e32dc6a8eae7dc501b5ba8e520122456a91bae5134273a6db134c87c4>
   /P -3392 /EncryptMetadata false
   /CF << /StdCF << /AuthEvent /DocOpen /CFM /AESV2 /Length 16 >> >>
   /StmF /StdCF /StrF /StdCF >>
endobj
trailer
<< /Root 1 0 R /Size 6 /Encrypt 5 0 R
   /ID [<31415926535897932384626433832795> <31415926535897932384626433832795>] >>

<0ba3…> は2桁で1バイトを表す16進文字列です。/ID の第1要素はPDFを更新しても変わらない永続IDで、鍵の材料に使います。第2要素は更新に合わせて変わるIDです。

Algorithm 2 で鍵を導出する

  1. パスワードを32バイトにそろえます。user の4バイト 75 73 65 72 の後ろに、規定のバイト列の先頭28バイトを付けます。入力が32バイト以上なら先頭32バイトを使います。
  2. 整えたパスワード、/O の32バイト、/P の4バイト、永続IDを順にMD5へ渡します。リトルエンディアンは数値の下位バイトから並べる方式で、/P -3392 は C0 F2 FF FF になります。pdfmodが受理する符号なし表記 4294963904 も同じ4バイトになります。
  3. リビジョン4で /EncryptMetadata false の場合は、FF FF FF FF を加えてから最初のダイジェストを得ます。
  4. リビジョン3と4では、直前のダイジェストの先頭 n バイトをMD5に掛け直す処理を50回繰り返します。例えば /Length 64 の場合、n は8です。
  5. 最後のダイジェストの先頭 n バイトがファイル暗号鍵です。この例では16バイトの 2d3657bf2eed39f71c700423877a4e15 が得られます。テストでは、鍵を使って計算した値を辞書の /U と照合します。
辞書の指定鍵長 n最初の MD5 の後に繰り返す回数
/V 1 /R 25バイト固定0回
/V 1 /R 35バイト固定50回
/V 2 /R 3、/V 4 /R 4辞書直下の /Length を8で割る。省略時は5バイト50回

Rustでファイル暗号鍵を導出する

let key = handler.derive_legacy_file_key(b"user", trailer.id())?;
let key_bytes = key.as_bytes();

b"user" は文字列の内容をバイトで表すRustの書き方です。trailer.id() は Option<&FileId> を返します。Option は値がある Some と欠けている None を表し、& は値を借りる記号です。ここでの ? は、成功時に鍵を取り出し、失敗時に呼び出し元へ理由を返します。

導出処理は、トレイラに /ID がなければ MissingFileId、/O が32バイトでなければ InvalidOwnerEntryLength を返します。/ID [<> <>] は2つの要素を持つので、長さ0の永続IDとして扱います。導出した鍵を /U や /O と照合する手順は パスワード認証 で扱います。

分割しても同じダイジェストを得る

MD5は64バイトがそろうたびに、4バイトずつ16個の整数へ読み替えます。各ブロックでビット演算、32ビットの加算、左回転を繰り返し、4個の32ビット整数からなる状態を更新します。update は64バイトに満たない末尾を保持するため、下の2通りの渡し方で同じダイジェストが得られます。

let mut md5 = Md5::new();
md5.update(b"a");
md5.update(b"bc");
let digest = md5.finalize();
assert_eq!(digest, Md5::digest(b"abc"));

finalize は末尾に 80（16進数）と必要な数の 00 を加え、最後の8バイトに元の入力のビット長をリトルエンディアンで置きます。端数が56バイト以上なら、終端と長さが1ブロックに収まらないため、長さは次のブロックに入ります。

入力のバイト数最後に残るバイト数確定時に処理するブロック数
001
55551
56562
6401
120562

Rust実装では内部の Md5 がブロック処理を担当します。状態、バッファー、出力は固定長なので、50回の反復で前のダイジェストの一部を渡すたびにヒープを確保する必要はありません。

既存PDFとの互換性に限って使用MD5の衝突耐性は失われています。旧形式の読み取りに限って使い、新規用途には使いません。
10

旧形式の暗号化とRC4

RC4は、鍵から生成したバイト列を入力に1バイトずつ重ねるストリーム暗号です。暗号化辞書で /V 1 または /V 2 を指定した旧形式ではRC4を使います。/V 4 ではcrypt filterの /CFM /V2 がRC4を選びます。

辞書から対象の方式を読む

以下は暗号化辞書と文字列オブジェクトの抜粋です。/StrF が指す /StdCF の /CFM は /V2 なので、通常の文字列にRC4を使います。/StmF /Identity は通常のストリームを暗号化しない指定です。

% 暗号化辞書と文字列の抜粋
8 0 obj
<< /Filter /Standard /V 4 /R 4 /Length 128
   /CF << /StdCF << /CFM /V2 /Length 16 >> >>
   /StrF /StdCF /StmF /Identity >>
endobj

9 0 obj
<< /Subject <A1076C> >>
endobj

辞書直下の /Length 128 はビット、crypt filter内の /Length 16 はバイト単位です。<A1076C> は暗号化された文字列を表す例です。この文字列を読むときは、ファイル暗号鍵とオブジェクト番号 9・世代番号 0 から求めた鍵を使います。

同じXORで暗号化と復号を行う

  1. 鍵スケジューリング（KSA） 0から255までの値を並べた置換表を作り、鍵のバイトを順に繰り返し使って表の要素を交換します。
  2. 疑似乱数生成（PRGA） 2つの添字を0から進め、置換表の要素を交換しながら入力1バイトごとに鍵ストリームを1バイト取り出します。添字の加算結果が256以上なら256を引きます。
  3. XOR（排他的論理和） 入力と鍵ストリームの各ビットを比較し、異なる位置を1にします。同じ鍵から初期化して同じ位置の鍵ストリームをもう一度XORすると、元の値に戻ります。
% 1バイトで見るXORの例（16進数）
暗号化  41 XOR 1F = 5E
復号    5E XOR 1F = 41

Rustの内部型 Rc4 は5〜16バイトの鍵を受け取ります。例えば4バイトや17バイトを渡すと None が返ります。apply は渡したデータをその場で書き換え、同じ状態で続けて呼ぶと次のバイトから処理します。空のデータでは鍵ストリームは進みません。

Rustで使える処理RC4はR2〜R4の パスワード認証 に使います。認証後は オブジェクトの復号鍵 を導出できます。

リビジョン6の鍵導出とSHA-2

標準セキュリティハンドラのリビジョン6では、パスワードとソルト（PDFに保存するランダムなバイト列）から、ファイル暗号鍵を取り出すための中間値を求めます。この処理で使うSHA-2は、バイト列から固定長のダイジェストを求めるハッシュ関数の系列です。

暗号化辞書からリビジョン6を判定する

以下は暗号化辞書とトレイラから方式の選択に関わる項目を抜き出した例です。/Encrypt 8 0 R は暗号化辞書への参照です。/R 6 はリビジョン6のパスワード処理を選び、/CFM /AESV3 は通常の文字列とストリームに使うAES-256を指定します。

% 暗号化辞書とトレイラの抜粋
8 0 obj
<< /Filter /Standard /V 5 /R 6
   /CF << /StdCF << /CFM /AESV3 >> >>
   /StrF /StdCF /StmF /StdCF >>
endobj
trailer
<< /Encrypt 8 0 R >>

鍵を取り出す手順で3種類を使い分ける

ファイル暗号鍵を取り出す Algorithm 2.A は、中間値を求めるために Algorithm 2.B を呼び出します。最初の2ステップが Algorithm 2.B のハッシュ計算です。

  1. パスワードとソルトをSHA-256に掛け、最初の中間値を得ます。所有者のパスワードを使う場合は、入力に /U の全48バイトも含めます。
  2. 中間値を使ったAES-128-CBC処理の結果から、次に使うSHA-256・SHA-384・SHA-512のいずれかを選びます。AESの出力全体を選んだハッシュに掛けて、次の中間値を更新します。この手順を少なくとも64回繰り返します。
  3. 鍵導出に使うソルトで得た中間値の先頭32バイトを使い、利用者なら /UE、所有者なら /OE を復号して、ファイル暗号鍵を取り出します。

入力の切れ目とパディング

ハッシュは入力を固定長のブロックに切り、ブロックごとに状態を更新します。update はブロックに満たない末尾だけを保持します。入力が完了すると、finalize が終端の 80（16進数）、必要なゼロ、元のビット長を順に補います。

方式ブロック長ビット長の欄ダイジェスト
SHA-25664バイト8バイト32バイト
SHA-384128バイト16バイト48バイト
SHA-512128バイト16バイト64バイト

SHA-256では末尾が55バイトなら同じブロックに終端と長さが収まり、56バイトなら長さを次のブロックに置きます。SHA-384とSHA-512では境界が111バイトと112バイトです。SHA-384はSHA-512と同じ圧縮処理を専用の初期値から実行し、最終状態の先頭6ワードを出力します。

次は分けて渡した abc のハッシュを返すRustの例です。一括入力の Sha256::digest(b"abc") と同じ32バイトになります。

fn hash_abc() -> Option<[u8; 32]> {
    let mut sha = Sha256::new();
    sha.update(b"a")?;
    sha.update(b"bc")?;
    Some(sha.finalize())
}
Rustで使える処理3種類のSHA-2は固定長の配列だけで計算するため、ハッシュを繰り返すたびにヒープを確保する必要はありません。ファイル暗号鍵の取り出しでは、検証用と鍵用のソルトを使い分けます。
12

AESのCBC・ECB復号

AESはデータを16バイトずつのブロックに分けて処理します。AES-128とAES-256の数字は鍵のビット数です。鍵の長さはそれぞれ16バイトと32バイトで、どちらもデータのブロック長は16バイトです。

文字列の方式を辞書から読む

以下は暗号化辞書と暗号化された文字列の抜粋です。/StrF と /StmF は文字列とストリームに適用するフィルタ名です。どちらも /CF 内の /StdCF を指すため、/CFM /AESV3 が選ばれます。/CFM /AESV2 を選ぶ形式では同じブロック構造をAES-128で処理します。

% 暗号化辞書の抜粋
8 0 obj
<< /Filter /Standard /V 5 /R 6
   /CF << /StdCF << /CFM /AESV3 >> >>
   /StrF /StdCF /StmF /StdCF
   /P -4 /Perms <D2FFE8BC214EBC01DFF5AF20C2B755C8> >>
endobj

% 暗号化文字列の抜粋。各行が16バイト
9 0 obj
<< /Subject <A0A1A2A3A4A5A6A7A8A9AAABACADAEAF
                AA21CE5618972CF6990C87A0B04065EB
                1DA720B04E5DDED942A216C5B4F681DF> >>
endobj

CBCで先頭の16バイトを使う

16進文字列の2桁が1バイトです。上の /Subject をバイト列として読むと48バイトになります。先頭の A0 から AF までの16バイトがIV（初期化ベクトル）で、続く32バイトが暗号文です。IVは最初のブロックを復号するときのXORに使う値です。

  1. 1ブロック目 AESで1ブロック復号し、その結果とIVを位置ごとにXORします。
  2. 2ブロック目以降 AESで復号した結果と、直前の暗号文のブロックをXORします。この連鎖をCBC（Cipher Block Chaining）と呼びます。
  3. パディングを外す 追加したバイト数を末尾の1バイトで読み取り、末尾にその値が同じ回数だけ並んでいることを確認して取り除きます。この例は末尾の 0F が15個なので、32バイトから15バイトを除き、PDF stream block! の17バイトが残ります。
IVと暗号文復号・検証の結果
16バイトのIVと1ブロック。復号後の末尾16バイトがすべて 10（16進数）空の平文を返す。元データの長さが16の倍数なら、16バイト分のパディングを追加する。
空、IVだけ、または暗号文が16バイト単位の途中で終わる長さのエラーを返す。IVに加え、16バイトの暗号文が1ブロック以上必要。
復号後の末尾が 00、11 以上、または 01 02 で終わるパディングのエラーを返す。02 で終わる場合は末尾が 02 02 で揃う必要がある。

権限の /Perms は1ブロックのECB

リビジョン5・6の /Perms は、ファイル暗号鍵を使ってAES-256のECB（Electronic Codebook）で復号します。ECBは各ブロックに直接AESを適用します。/Perms はIVもパディングも付かない16バイトで、復号後の全16バイトを権限の検証側に渡します。上の例では復号した先頭4バイト FC FF FF FF がリトルエンディアンの /P -4 です。

Rustで16バイトを切り出す

let Some((iv, ciphertext)) = input.split_first_chunk::<BLOCK_LEN>() else {
    return Err(AesCbcError::InvalidLength);
};

::<BLOCK_LEN> は切り出す個数をコンパイル時に指定する書き方で、ここでは16です。成功を表す Some((iv, ciphertext)) から2つの値を取り出します。iv は &[u8; 16]（16バイトちょうどの配列への参照）、ciphertext は &[u8]（残りのバイト列への参照）です。例えば b"abcde".split_first_chunk::<2>() なら、同じ元データから ab と cde を借ります。指定した長さに満たない場合は None となり、else の処理に進みます。

Rustで使える処理同じ鍵から作ったラウンド鍵をCBCとECBで共有します。次の節では、暗号化されたファイル鍵にCBCを、権限のコピーにECBを適用します。
13

2つのパスワードから同じファイル暗号鍵を取り出す

リビジョン5・6のPDFを作るとき、作成ソフトは文書用に32バイトの鍵を1つ用意します。その鍵を利用者用、所有者用の中間鍵でそれぞれ暗号化して辞書に保存します。開く人が使うパスワードが違っても、取り出す文書の鍵は同じです。

空パスワードで開けるPDFの辞書を読む

次はテストに使った1ページのPDFからの抜粋です。16進文字列の途中の改行は読みやすくするための空白です。/U の3行は、順に32バイトの検証値、8バイトの検証用ソルト、8バイトの鍵用ソルトです。

% トレイラが /Encrypt 6 0 R で参照する辞書の抜粋
6 0 obj
<< /Filter /Standard /V 5 /R 6
   /U <9c5dcd0995ef2b1ad7dae7144b6739ab9a6d8e445d13dae58a17b2cbf5e0ce7a
       6eddfcaa734bd957
       e33b9b10decee021>
   /UE <cb5e761235424db4edc8969c2b38c0a3e4159502e5a5e3cb09269b026eb6cad3>
   /P -4 /Perms <69dba27236cca1287cf8fc3c155f6b58> >>
endobj
役割検証値とソルト各ハッシュの追加データ暗号化された文書の鍵
利用者/U空のバイト列/UE
所有者/O/U の全48バイト/OE
  1. 候補のパスワードを照合する。 この例の利用者パスワードは空です。検証用ソルトを加えてR6のハッシュを計算すると、72ラウンドで /U の1行目と一致します。違うパスワードならここでエラーを返します。
  2. 文書の鍵を取り出す。 同じ空パスワードに3行目の鍵用ソルトを加えると、69ラウンドで別の32バイトの値が得られます。これを中間鍵にして /UE をAES-256-CBCで復号します。IVは16個のゼロ、入力は2ブロックちょうどです。末尾も鍵の一部として残します。
  3. 権限を照合する。 取り出した鍵で /Perms をECB復号すると、先頭から FC FF FF FF（/P -4）、FF FF FF FF（固定値）、T（メタデータ暗号化あり）、adb（固定文字列）が並びます。残りの4バイトは乱数です。固定部分も辞書の値も合うと、検証済みの鍵が返ります。

R6はどのラウンドで止まるか

R5はパスワード、ソルト、役割に応じた追加データをSHA-256で1回処理します。R6はこの値を出発点にします。各ラウンドで「パスワード・直前のハッシュ全体・追加データ」を64回並べてAES-128-CBCで暗号化します。その暗号文の先頭16バイトを整数として3で割った余りが0、1、2の順に、SHA-256、SHA-384、SHA-512を選び、暗号文全体を次のハッシュに渡します。

64ラウンド以降で、暗号文の末尾1バイトが「完了ラウンド数 − 32」以下になると終了します。例えば64ラウンド目で末尾が32なら終了、33なら継続です。最終ハッシュの先頭32バイトを使います。

Rustの &str と127バイトの境界

let bytes = prepared_password.as_bytes();
let password = bytes.get(..MAX_PASSWORD_BYTES).unwrap_or(bytes);

&str はUTF-8文字列を借りる型です。as_bytes() で同じメモリをバイト列として読み、..127 で先頭から127番目までを選びます。短ければ get が None を返し、unwrap_or(bytes) が元の全体を選びます。たとえばASCIIの a 125個に3バイトの「界」を続けると、「界」の先頭2バイトまでがハッシュに入ります。

文字を整える段階SASLprepは、空白の置換、Unicode正規化、禁止文字の検査など、パスワードの表記を整える手順です。pdfmodのRust APIでは呼び出し側でこの処理を済ませます。準備済みの空文字列は derive_aes256_file_key(PasswordRole::User, "") と渡せます。役割を自動判定する認証入口は パスワード認証 で扱います。

パスワードを認証して鍵と役割を確定する

ファイル暗号鍵を導出できても、入力されたパスワードが正しいか、利用者か所有者のどちらに該当するかはまだ確定していません。パスワード認証（password authentication）は、暗号化辞書の /U・/O と突き合わせて、検証済みのファイル暗号鍵と役割を同時に確定する手順です。

利用者パスワード（user password）

文書を開くためのパスワードです。空パスワード（長さ0）が設定されているPDFは入力なしで開けますが、/P の権限制限が適用されます。

所有者パスワード（owner password）

印刷や編集など /P の権限制限を解除して扱うためのパスワードです。利用者と所有者に同じパスワードを設定したPDFも存在します。

パスワードの有無で変わる試行順序

PDFを開くとき、パスワードが省略された場合と明示的に渡された場合で、役割を試す順番が異なります。以下の図は StandardSecurityHandler::authenticate の判定分岐です。

リビジョン別の4つの認証アルゴリズム

標準セキュリティハンドラでは、リビジョンと役割の組み合わせに応じて Algorithm 6・7・11・12 を使い分けます。

リビジョン役割アルゴリズム検証に使う項目と手順の要点
R2（/V 1 /R 2）利用者Algorithm 6Algorithm 2 の5バイト鍵で標準パディングをRC4暗号化し、/U の全32バイトと比較
R3・R4利用者Algorithm 6MD5(標準パディング || /ID[0]) を鍵 XOR ラウンド 0..20 で20回RC4し、/U の先頭16バイトと比較
R2所有者Algorithm 7MD5(32B整え済み所有者パスワード) の先頭5バイトで /O を1回RC4復号し、復元した32バイトを Algorithm 6 へ渡す
R3・R4所有者Algorithm 7Algorithm 3 手順1〜4（16バイト全体を50回MD5）の先頭 n バイトで /O を逆順 19..=0 の20回RC4復号し、復元した32バイトを Algorithm 6 へ渡す
R5・R6利用者Algorithm 11UTF-8（最大127バイト）と /U の検証用ソルトでハッシュ照合 → 鍵用ソルトで /UE 復号 → /Perms 検証
R5・R6所有者Algorithm 12UTF-8（最大127バイト）・/O のソルト・/U 全48バイトでハッシュ照合 → /OE 復号 → /Perms 検証

R2〜R4 の /O 復元と /U 照合（Algorithm 6 / 7）

R2〜R4 では、所有者パスワードから直接ファイル暗号鍵を作るのではなく、/O を復号して32バイトのパディング済み利用者パスワードを取り出し、利用者側と同じ Algorithm 6 に通します。

Algorithm 2 と Algorithm 3 の50回MD5は対象の長さが違うファイル暗号鍵を求める Algorithm 2 では、直前のダイジェストの先頭 n バイトだけを50回再ハッシュします（例：/Length 64 は8バイト）。これに対し、所有者RC4鍵を求める Algorithm 3（手順3）では16バイトのダイジェスト全体を50回再ハッシュし、完了後に先頭 n バイトを切り出します。

正常・省略例：空パスワードで自動オープンする R2 辞書

次はテスト用PDFからの抜粋です（完全なPDFではなく暗号化辞書とトレイラの部分）。利用者パスワードが空のR2暗号化辞書です。

% 空の利用者パスワードで開ける R2 暗号化辞書とトレイラの抜粋
<< /Filter /Standard /V 1 /R 2 /Length 40 /P -4
   /O <c92422687facee686e373f10b5c7d04738053152f7e2ee30e11c69ec442576ab>
   /U <b3d9fa366906ef42f354c6deb74c59075eaf334eb7c04356ba0d7f3dd8b51d0a> >>
trailer

   /ID [<31415926535897932384626433832795> <31415926535897932384626433832795>] >>

handler.authenticate(None, trailer.id()) を呼ぶと、空パスワード b"" を利用者 → 所有者の順に試し、Algorithm 6 で導出した5バイト鍵 0e7b66938a が /U の全32バイトと一致します。結果は PasswordRole::User 付きの AuthenticatedFileKey になります。

正常例：明示パスワードで所有者として認証する（R5・R6）

エラー例：パスワード不一致と構造不正の区別

誤ったパスワードや、R5・R6 に対して UTF-8 として解釈できないバイト列を渡した場合は AuthError::IncorrectPassword を返します。一方、R2〜R4 で /ID が欠けていれば MissingFileId、/U や /O が規定長（R2〜R4 は32バイト、R5・R6 は48バイト）と異なれば InvalidEntryLength、R5・R6 で /Perms が辞書と矛盾すれば InvalidPermissions となり、誤パスワードと辞書の破損・改ざんを明確に区別できます。

Rust API と型による安全境界

authenticate と authenticate_as は、検証済みの鍵と役割を AuthenticatedFileKey に包んで返します。認証結果は認証に使った暗号化辞書への参照も保持するため、復号方式と鍵を同じ辞書から選べます。

use pdfmod_core::encrypt::auth::{AuthError, PasswordRole};

match handler.authenticate(password, trailer.id()) {
    Ok(authenticated) => {
        let role: PasswordRole = authenticated.role();
        // role に応じて /P の権限制限を判定する
    }
    Err(AuthError::IncorrectPassword) => {
        // パスワード不一致：再入力を求めるなど
    }
    Err(structural_error) => {
        // /ID 欠落、/U・/O の長さ不正、/Perms 不一致など
    }
}
型・メソッド役割と制約
StandardSecurityHandler::authenticate(password, file_id)None は空パスワードを利用者 → 所有者、Some(bytes) は所有者 → 利用者の順に認証
StandardSecurityHandler::authenticate_as(role, password, file_id)指定した単一の PasswordRole で Algorithm 6 / 7 / 11 / 12 を適用
AuthenticatedFileKey認証に使った暗号化辞書を借用。role()・key()・as_bytes() で認証結果を参照。Debug は鍵バイト列を秘匿
FileEncryptionKeyLegacy(LegacyFileKey) と Aes256(Aes256FileKey) の列挙型。鍵種別のみを表し単独では認証済みを保証しない（認証が必要な境界では AuthenticatedFileKey を要求する）。as_bytes()・as_legacy()・as_aes256() を提供
AuthErrorIncorrectPassword と MissingFileId・InvalidEntryLength・InvalidKeyLength・InvalidPermissions・InvalidHashInput・UnsupportedRevision を区別
定数時間比較と鍵の秘匿/U や検証ハッシュの照合には、先頭で不一致を見つけても打ち切らず全バイトを XOR で畳み込む定数時間比較（constant-time comparison）を使います。また AuthenticatedFileKey と内包する鍵型は Debug フォーマットで鍵バイト列を出力しません。

オブジェクトの復号鍵

ファイル暗号鍵はパスワード認証で得られます。文字列やストリームを読む段階では、まず暗号化に使われた方式を探し、その方式に必要な鍵を用意します。

文字列とストリーム本体の既定の方式

次は暗号化辞書と間接オブジェクトの抜粋です。/StrF /ForStrings から /CF の /ForStrings を引くと、/CFM /V2 が見つかります。したがって /Subject に続く16進文字列は RC4 で復号します。ストリーム本体の既定方式は、/StmF /ForStreams が選ぶ AES-128 です。

% /Encrypt が指す暗号化辞書の抜粋
<< /V 4 /R 4 /Length 128
   /CF << /ForStreams << /CFM /AESV2 /Length 16 >>
          /ForStrings << /CFM /V2 /Length 16 >> >>
   /StmF /ForStreams /StrF /ForStrings >>

7 4660 obj
<< /Subject <5A2277> >>
endobj
指定処理
/V 1・/V 2、または /CFM /V2RC4。Algorithm 1 でオブジェクト鍵を導出します。
/CFM /AESV2AES-128。Algorithm 1 の MD5 入力に sAlT を加えます。
/CFM /AESV3AES-256。Algorithm 1.A に従って32バイトのファイル暗号鍵を使います。
/Identity、/CFM /None復号を省略します。/V 4 以降で /StmF や /StrF を省略すると、その対象は /Identity です。/CFM の省略は /None になります。
/CF に名前が見つからない場合たとえば /StrF /Missing を指定した文書は、暗号化辞書の解析時に UndefinedCryptFilter を返します。/Identity は組み込みの名前として解決されます。

Algorithm 1 の入力をバイトで読む

  1. ファイル暗号鍵を置く。 例の /Length 128 は16バイト鍵を表します。
  2. 番号をリトルエンディアンで足す。 リトルエンディアンは小さい桁のバイトから並べる方式です。7 4660 obj のオブジェクト番号 7 は 07 00 00、世代番号 4660（16進数で 1234）は 34 12 です。
  3. AES-128 の場合は sAlT を足す。 4文字を ASCII の4バイト 73 41 6C 54 にした固定値です。
  4. MD5 の先頭を取る。 16バイトの出力から、ファイル鍵の長さに5を足した長さまで取り出します。取り出すのは最大16バイトです。たとえばファイル鍵が5バイトなら、RC4 のオブジェクト鍵は10バイトになります。

例のオブジェクトでテスト用ファイル鍵 2d3657bf2eed39f71c700423877a4e15 を使うと、RC4 鍵は a81abbe4025116ebda01d9652639ddee です。この鍵で <5A2277> を復号したバイトを ASCII で読むと PDF になります。同じ番号と世代で AES-128 を選ぶと、sAlT が加わって鍵は 1b66d7e5ffda93e9bb90892ab0e05027 になります。

3バイトを超えるオブジェクト番号16進数で ff ff ff の次の番号 01 00 00 00 は、下位3バイトだけを取り出すと 00 00 00 になります。上位バイトだけが異なる場合は、同じ世代から同じ鍵が導出されます。

オブジェクトストリームを一度復号する

/Type /ObjStm は、複数のオブジェクトを一つのストリーム本体に格納します。コンテナの本体に /StmF とコンテナ自身の番号・世代を使います。そこから取り出したオブジェクトの文字列は、コンテナ本体を復号した時点で平文になっています。

let ObjectDecryptionTarget::Indirect { id, kind } = target else {
    return Ok(ObjectDecryption::None);
};

Rust の let … else は、右辺の値が左側の形に一致したときに中身を取り出す構文です。target が通常の間接オブジェクトなら、波括弧の id と kind を後続の処理で使えます。格納形態が InObjectStream なら else の中へ進み、復号不要を表す Ok(ObjectDecryption::None) を返します。

authenticated.object_decryption(target) と呼ぶと、認証結果に結び付いた辞書とファイル鍵から、対象の復号方式と鍵を選びます。選んだ方式がファイル鍵の種別や長さと両立しない場合は IncompatibleFileKey になります。

RC4 と AES-128 の戻り値は、その場で導出した鍵を持ちます。AES-256 では Algorithm 1.A が指定するファイル暗号鍵の32バイトをコピーして、ObjectDecryption::Aes256 に入れます。どの方式でも戻り値が自分で鍵を持つため、呼び出し側は認証結果を破棄したあとも復号方式と鍵を保持できます。

AuthenticatedFileKey<'handler> の 'handler は、暗号化辞書への参照を使える期間（ライフタイム）を表します。認証結果を使っている間は、元の辞書も参照できることを Rust のコンパイラが確認します。

認証済みResolverで遅延復号する

通常の ObjectResolver::open は暗号化文書を EncryptedDocument で拒否します。パスワード認証を済ませた場合は open_authenticated に認証結果を渡し、AuthenticatedObjectResolver が要求された間接オブジェクトだけを復号します。入力の /Encrypt と永続 /ID が認証元に一致することを入口で確認するため、別文書の鍵を渡すことはできません。

let authenticated = handler.authenticate(password, file_id)?;
let mut resolver = ObjectResolver::open_authenticated(input, authenticated)?;
let value = resolver.resolve(reference)?;
  1. 構造を先に読む。 xref、間接オブジェクトの番号、ストリーム辞書、暗号文の /Length は復号前の構造情報です。
  2. 対象を選ぶ。 文字列・配列・辞書内の文字列は /StrF、ストリーム本体は /StmF を使います。AESでは先頭16バイトをIV、末尾をPKCS#7パディングとして処理します。
  3. 平文長へ更新する。 ストリーム復号後は、暗号文と異なり得る実データ長を辞書の /Length へ書き戻します。
  4. 除外と一度だけの復号を守る。 /Encrypt、/ID、xrefストリーム、/Identity は無変更です。ObjStmはコンテナだけを復号し、内包オブジェクトは再復号しません。
  5. 署名と未対応フィルタを区別する。 /Type /Sig の /Contents は平文のまま保ち、同じ辞書の他の文字列は復号します。明示的な /Crypt や埋め込みファイルは /StmF へ勝手にフォールバックせず、型付きエラーにします。
メタデータの例外/EncryptMetadata false の /Type /Metadata ストリーム本体は平文として保ちます。通常ストリーム辞書に含まれる文字列は別物なので、/StrF の対象かどうかを辞書の値ごとに判定します。
失敗とキャッシュ認証元の不一致、復号方式と鍵の不一致、AESの長さ・パディング不正、未対応crypt filterは AuthenticatedResolveError の別バリアントで分岐できます。既存の ResolveError は変えないため、通常のResolverを使う既存呼び出しの網羅的matchは壊れません。復号済み PdfObject は認証済みResolverのキャッシュに保存されるため、同じ参照を再解決しても再度復号しません。Debug も平文オブジェクトではなく入力長とキャッシュ件数だけを出します。

crypt filter を使う文書では、ストリーム本体の既定の方式を /StmF から選びます。明示的な /Crypt や埋め込みファイル用の /EFF が適用される場合は、呼び出し側で扱います。これらのフィルタ固有経路は今回のResolver統合の対象外です。
