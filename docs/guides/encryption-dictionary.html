PDF INTERNALS / ENCRYPTION DICTIONARY

暗号化辞書を読む

PDFの /Encrypt は、暗号化の方式と鍵の材料を記述します。アルゴリズムの版、crypt filter、権限を、解釈できる型へ変換する仕組みを見ていきます。

01

暗号化の起点

トレイラの /Encrypt が暗号化辞書を指します。直接辞書でも間接参照でも書けます。暗号化辞書自体は復号前に読む必要があるため、オブジェクトストリームには格納できません。

セキュリティハンドラ

Security handler はパスワードなどからアクセスを認証する方式です。/Filter /Standard はパスワードベースの標準ハンドラを表します。

暗号化される値

対象は文字列とストリームです。辞書のキー名、名前オブジェクト、数値は暗号化されません。暗号化文書のトレイラには鍵導出に使用する /ID が必要です。

今回扱うのは辞書の構造辞書から方式と鍵の材料を読み取ります。文字列やストリームの復号、鍵導出、パスワード認証はこの型変換に含まれません。
02

辞書を読む

以下は説明用の抜粋です。暗号鍵の材料は短縮しており、完全なPDFや復号可能な鍵の例ではありません。

trailer
<< /Root 1 0 R /Size 20 /Encrypt 8 0 R
   /ID [<00112233> <00112233>] >>

8 0 obj
<< /Filter /Standard /V 4 /R 4 /Length 128
   /O <00FF> /U (user) /P -4 /EncryptMetadata false
   /CF << /StdCF << /CFM /AESV2 /Length 16 >> >>
   /StmF /StdCF /StrF /StdCF >>
endobj

8 0 R はオブジェクト番号8・世代番号0への間接参照です。<< >> は辞書、<00FF> は16進形式のバイト列、(user) はリテラル文字列です。/O と /U はテキストとして復号せず、元のバイト列を保持します。

キー意味保持・検証
/Filter /V /Rハンドラ名・アルゴリズム版・リビジョンStandard では必須。版の組を型へ変換
/Lengthファイル暗号鍵のビット数V2・V4 は40..128の8の倍数。省略時40
/O /U所有者・利用者パスワード由来の値必須のバイト列。長さは検証しない
/OE /UE /Perms暗号化ファイル鍵と権限のコピーR5・R6で必須のバイト列
/EncryptMetadataメタデータを暗号化するか省略時 true。指定時は真偽値が必要
/V の必須扱いはpdfmodの方針PDF仕様には /V の既定値0がありますが、pdfmodは省略を構造不正として返します。明示された /V 0 は未対応として保持します。省略と未対応は別の結果になります。
03

/V × /R の有効な6組

版とリビジョンを独立した任意の数値にすると、仕様にない組を作れてしまいます。StandardAlgorithm は有効な組だけを判別可能な union として表します。

型の種別/V/Rファイル鍵長と付随する値
V1R212RC4・40ビット固定
V1R313RC4・40ビット固定
V2R323RC4・/Length による可変長
V4R444/Length と crypt filter
V5R555AES-256・crypt filter と /OE /UE /Perms
V5R656AES-256・crypt filter と /OE /UE /Perms

V1とV5の鍵長は版から確定するため、直下の /Length を使用しません。V5R5はISO 32000-2で非推奨のリビジョンですが、辞書の構造は読み取れます。

未対応は構造不正と区別するV0は未文書化、V3は非公開の方式です。表にない組や /Adobe.PubSec などのハンドラは Unsupported として、元の辞書を欠損なく保持します。
04

crypt filter と鍵長の単位

Crypt filter は暗号方式の名前付き設定です。/CF が名前と設定の対応表になり、/StmF がストリーム、/StrF が文字列、/EFF が埋め込みファイルへの割り当てを表します。

暗号方式 /CFM

/None は暗号化なし、/V2 はRC4、/AESV2 はAES-128、/AESV3 はAES-256です。省略時は /None。未知の方式はエラーです。

組み込み /Identity

暗号化しない指定で、/CF 内の定義は不要です。StmF・StrFの省略時もIdentityになります。EFFの省略は None として保持します。

/Identity 以外のセレクタは /CF に定義されていなければなりません。pdfmod はV4・V5で /CF を必須にする実装上の制限を持ち、空辞書は受理します。

/CF 内の /Length入力の解釈正規化結果
5 / 16バイト表記40 / 128 ビット
40 / 128ビット表記40 / 128 ビット
17 / 44 / 256受理する鍵長に該当しない無視して None
名前・実数・間接参照整数の直接値ではない解決せず None
直下の /Length と /CF 内は別の規則ISOは /CF 内の鍵長をバイト単位としますが、ビット表記のPDFも存在します。RustとTypeScriptは5..16を8倍し、それ以外をビット数として扱い、40..128の8の倍数だけを保持します。これはpdfmodの正規化規則です。AESV3自体は表現できますが、/CF の32・256はこの規則では保持しません。V5のファイル鍵長は256ビット固定です。

TypeScriptの CryptFilter も方式で分岐するunionです。AESV2の keyLength は128、AESV3は256という固定値の型です。一方、length は入力辞書の /Length を正規化して保持する値であり、AESの固定鍵長を上書きしません。V2（RC4）の指定長は length で読み、省略はNoneのまま扱います。

/AuthEvent は認証の時点です。/DocOpen は文書を開くとき、/EFOpen は埋め込みファイルを開くときです。pdfmodは省略・未知名・型不一致をDocOpenへ戻します。

05

/P のビット表現

Permissions は印刷・変更・抽出などのアクセス権限をビットで表します。例えば第3ビットは印刷、第5ビットは抽出、第12ビットは高解像度の印刷です。ビットが1なら許可を表します。

4294967292 と -4 は同じ32ビット

仕様の符号付き表記は /P -4 ですが、符号なし表記の /P 4294967292 を書くPDFもあります。どちらも permissions.bits = -4 に正規化します。

受理範囲は -2147483648..4294967295 の整数です。範囲外は INVALID_PERMISSIONS になります。権限を実際に強制する処理は今回の対象外です。

06

正常・未対応・不正を比べる

以下は暗号化辞書の抜粋です。短い /O・/U は辞書解析の例で、鍵導出に必要な長さは表していません。

正常：最小のV1R2

<< /Filter /Standard /V 1 /R 2 /O () /U () /P -4 >>

Standard。40ビット固定、EncryptMetadataはtrue。空の鍵材料も長さ検証なしで保持します。

未対応：有効な型へ変換しない組

<< /Filter /Standard /V 1 /R 6 /Custom (keep) >>

Unsupported。後続の必須キーは要求せず、Customを含めて元の辞書を保持します。

未対応：公開鍵ハンドラ

<< /Filter /Adobe.PubSec /Recipients [(opaque)] >>

Unsupported。V・Rやハンドラ固有のキーを解釈しません。

不正：直接値が必要なキーの間接参照

<< /Filter /Standard /V 2 /R 3 /Length 5 0 R
   /O () /U () /P -4 >>

/Length 自体は省略可能ですが、V2・V4で指定する場合は整数の直接値が必要です。この例は INVALID_KEY_TYPE、キーは /Length になります。辞書内部の参照は解決しません。エラーには呼び出し側が渡した辞書のバイト位置を付けます。

07

解析の境界と対応範囲

  1. 解決済みの暗号化辞書を EncryptDictionary.fromDictionary(dictionary, offset) へ渡す。
  2. Filterを検証する。未知のハンドラならUnsupportedとして保持する。
  3. StandardではV・Rを必須の整数として読む。対応外の組ならUnsupportedとして保持する。
  4. 対応する組に必要な鍵長・crypt filter・追加鍵を読む。
  5. 共通のO・U・P・EncryptMetadataを読み、Standardを返す。
位置は辞書単位エラーの offset は渡された辞書の開始位置です。/CF/StdCF/CFMのようなキーのパスは報告しますが、個々の値の物理位置は取得しません。

キーと期待型を表す PdfDictionaryField と直接値の取得・型チェックは、PDF共通の PdfDictionaryReader が担当します。暗号化側はそのエラーを EncryptError に変換し、暗号化固有の制約を検証します。

入力辞書からキーを削除したりバイト列を書き換えたりしません。必須キー欠落、型不一致、不正なファイル鍵長、未定義セレクタはResultのエラーで返します。

TypeScriptの PdfDocument.load は引き続き暗号化PDFを ENCRYPTED_PDF_UNSUPPORTED として拒否します。この型化は復号機能の基盤であり、ドキュメント読込の復号対応は後続の作業です。

TypeScriptで解析結果を読む

次の例は公開APIを使い、辞書の抜粋をバイト列から読み取ります。ObjectParser はPDFの構文を辞書へ変換し、EncryptDictionary はその辞書を暗号化方式の型へ変換します。トレイラから /Encrypt を探す処理は含みません。

import {
  ByteOffset,
  EncryptDictionary,
  ObjectParser,
  StandardAlgorithm,
} from "@pdfmod/core";

function inspectEncryption(bytes: Uint8Array, offset: ByteOffset): string {
  const parsed = ObjectParser.parse(bytes, offset);
  if (!parsed.ok) {
    return parsed.error.message;
  }

  if (parsed.value.type !== "dictionary") {
    return "暗号化辞書が必要です";
  }

  const result = EncryptDictionary.fromDictionary(parsed.value, offset);
  if (!result.ok) {
    return `${result.error.key}: ${result.error.message}`;
  }

  if (result.value.type === "Unsupported") {
    return `未対応: ${result.value.filter}`;
  }

  const { algorithm, permissions } = result.value.handler;
  const bits = StandardAlgorithm.keyLength(algorithm);
  return `${algorithm.kind} / ${bits} bits / P=${permissions.bits}`;
}

const bytes = new TextEncoder().encode(
  "<< /Filter /Standard /V 1 /R 2 /O () /U () /P 4294967292 >>",
);
const summary = inspectEncryption(bytes, ByteOffset.of(0));
// summary は "V1R2 / 40 bits / P=-4"
  • ByteOffset はバイト位置を表す型です。この例の辞書は入力の先頭にあるので、位置が確定した定数0に of(0) を使います。外部入力の数値には、検証する create を使います。
  • Result は成功と失敗を値で表す型です。ok がfalseなら error、trueなら value を読みます。Unsupported は失敗ではなく、解釈せず保持できた成功です。
  • 判別可能なunionは、type や kind の値で中身の型が決まる仕組みです。未対応の分岐を抜けるとStandardだけが残り、handler を安全に読めます。
  • 鍵長は algorithm.keyLength または StandardAlgorithm.keyLength から読みます。V1の型は40、V5の型は256に限定され、異なる鍵長を代入すると型エラーになります。V2・V4も40〜128の8刻みだけを許します。
08

方式ごとの型に生成を任せる

/V と /R を読むと、どの方式として辞書を解釈するかが決まります。その先の読み取りは、選ばれた方式の型が担当します。例えば V2R3 は可変鍵長、V4R4 は可変鍵長とcrypt filter、V5R6 はAES-256用のパラメーターを読み取ります。

TypeScriptの type は実行時には消えるため、型の宣言だけでは処理を実行できません。そこで同じ名前の const に生成関数を置きます。この組をコンパニオンオブジェクトと呼びます。型注釈の V5R6 は値の形を表し、V5R6.fromDictionary(reader) は実際の読み取り処理を呼びます。

型生成入口担当する内容
V1R2 / V1R3create()40ビット固定の値を生成。追加の辞書項目は不要
V2R3fromDictionary(reader)直下の /Length。省略時40ビット、不正値はエラー
V4R4fromDictionary(reader)直下の /Length とcrypt filterの定義・割り当て
V5R5 / V5R6fromDictionary(reader)256ビット固定、crypt filter、/OE・/UE・/Perms

全方式の入口は、選択して委譲する

次は実装の抜粋です。StandardAlgorithm は6つの名前付き型をまとめたunionです。入口が /V 5 /R 6 を選ぶと V5R6 へ委譲します。map は成功値だけを some で包み、失敗はエラーのまま返します。未対応の組は none として、生辞書を保持する処理へ戻ります。

export type StandardAlgorithm =
  | V1R2 | V1R3 | V2R3
  | V4R4 | V5R5 | V5R6;

// StandardAlgorithm.fromDictionary の分岐の抜粋
case "5:6":
  return map(V5R6.fromDictionary(reader), some);

共通の材料を使っても、生成結果はその方式だけ

V5R5 と V5R6 は、辞書から読む項目が共通です。これを内部の Aes256Parameters にまとめ、両方式から利用します。& は型の交差で、共通項目に kind: "V5R6" を加えます。同じ項目を持っていても kind が違うため、V5R5の値をV5R6の値として渡すことはできません。

// importを省略した実装の抜粋
export type V5R6 = Aes256Parameters & {
  readonly kind: "V5R6";
};

export const V5R6 = {
  fromDictionary(reader: PdfDictionaryReader): Result<V5R6, EncryptError> {
    return map(Aes256Parameters.fromDictionary(reader), (parameters) => ({
      ...parameters,
      kind: "V5R6",
    }));
  },
} as const;

成功した戻り値は StandardAlgorithm 全体ではなく V5R6 です。呼び出し側は、もう一度方式を調べずに keys や固定値256の keyLength を扱えます。可変鍵長の読み取りは KeyLength.fromEncryptionDictionary、AESの追加鍵の読み取りは AesKeyMaterial.fromDictionary が共有します。

  1. PDFの辞書を読む入口

    外部入力には EncryptDictionary.fromDictionary を使います。ハンドラ名と /V・/R の判定、方式の生成、共通キーの読み取りをつなぎます。

  2. 選択された方式の項目を読む

    各方式の fromDictionary は方式固有の項目を読みます。/V・/R 自体の再判定や、共通の /O・/U・/P の検証は担当しません。

  3. 正常・省略・不正を値として返す

    V2R3で /Length 128 は128ビット、省略は40ビット、/Length 44 はキー /Length と辞書開始位置を持つエラーになります。生成処理を分けても、この解析方針は変わりません。

版の選択と、バイト列の暗号処理は別の責務V4R4ではcrypt filterから暗号方式を選びます。ここで分離したのは辞書を解釈する型と生成処理です。パスワード認証・鍵導出・RC4やAESによる復号は未実装です。鍵材料のバイト列の長さも、この段階では検証しません。
