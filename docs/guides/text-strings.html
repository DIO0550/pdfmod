PDF INTERNALS / TEXT STRINGS

同じ「文字列」でも、
まだ文字とは限らない。

PDFのタイトルやしおり名は、まずバイト列として読み取られます。そこから先頭の目印を確認し、文字への対応規則を選ぶと、人が読めるテキストに戻せます。

01

バイトから文字へ

テキスト文字列（text string）は、文書情報辞書 /Info の /Title やアウトラインの名前などに使う、人が読むための文字列です。PDFの文字列オブジェクトはバイナリデータにも使われるため、文字列を見つけたという理由だけで文字に変換してはいけません。

RAW BYTES

PdfString

リテラル・16進表記を読み解いたあとのバイト列。00 や任意の高位バイトも保持します。文字として妥当かは、まだ問いません。

DECODED TEXT

PdfTextString

テキスト用途と分かった値を、選んだエラー方針で復元した文字列。Rustの String として使えるUnicodeテキストです。

ページに描く文字とは、復元経路が違うTj・TJ の文字列は、フォントのEncodingやCMapに基づく文字コード列です。ここで扱うBOMデコーダーを一律に適用しません。/ActualText のようにテキスト文字列と定義された属性は別です。
02

「書き方」と「符号化」を分ける

次は /Info の辞書に書く値の説明用抜粋です。完全なPDFではありません。タイトル「日本」を、2通りの表記で書いています。

% 16進表記。2桁で1バイト。
/Title <FEFF65E5672C>

% リテラル表記。バックスラッシュの後は8進数。
/Title (\376\377\145\345\147\054)
StringEncoding と文字コードは別物StringEncoding::Literal / Hex は元の表記形式です。UTF-8などの符号化方式は、この値ではなく実際の先頭バイトで判定します。
03

3つの符号化を読む

BOM（Byte Order Mark）は、文字列の先頭に置く符号化の目印です。PDFのテキスト文字列では、指定のBOMがなければPDFDocEncodingとして読みます。

先頭バイト選ぶ符号化読み方
EF BB BFUTF-8先頭3バイトを除き、UTF-8として復元。PDF 2.0で追加。
FE FFUTF-16BE先頭2バイトを除き、上位バイトが先の16ビット単位で読む。
どちらでもないPDFDocEncoding先頭から各バイトを専用の対応表で文字に変換。

PDFDocEncodingはLatin-1ではない

1バイトずつ対応表を引きます。英数字の多くは見慣れた並びですが、特殊記号や未割当の場所があります。例えば A0 は空白ではなく €（U+20AC）です。

バイト範囲対応・扱い
09 / 0A / 0DTAB・LF・CR。定義済みの制御文字。
00–08 / 0B–0C / 0E–17仕様表のNotesがU（未割当）。数値をそのままUnicodeへ渡さない。
18–1F˘ ˇ ˆ ˙ ˝ ˛ ˚ ˜ の8文字。
20–7EASCIIと一致。英数字・記号・空白。
80–9E•、†、…、ﬁ、Œ などの記号・合字。
A0€（EURO SIGN）。
A1–FF のうち AD 以外同じ数値のUnicode文字に対応。
7F / 9F / AD未割当。Strictならエラー、Replaceなら �。

UTF-16BEでは、2つの単位で1文字になることがある

基本多言語面の文字は通常1つの16ビット単位です。補助平面の文字はサロゲートペア（surrogate pair）として、上位 D800–DBFF と下位 DC00–DFFF の組で表します。

仕様と回復方針を区別するBOMや文字対応はPDF仕様、不正なUnicode列の判定はUnicodeの規則に基づきます。不正時に Err を返すか、U+FFFD（�）に置換して続けるかは、このライブラリで選べる方針です。
04

BOM判定の流れを辿る

判断するのは先頭だけです。UTF-8らしく見えるかどうかを推測したり、デコード失敗後に別の符号化へ切り替えたりはしません。

BOMなしUTF-8は推測しない

C3 A9 はUTF-8なら「é」ですが、このAPIではBOMなしなので「Ã©」。EF BB BF C3 A9 なら「é」です。

UTF-16LEも推測しない

FF FE はUTF-16BEのBOMではありません。指定のBOMに一致しないので、この2バイトはPDFDocEncodingの「ÿþ」になります。

05

正常・境界・不正を比べる

入力は、字句解析後のバイト列を16進数で表しています。位置はBOMを含む入力内のゼロ起点バイト位置です。ファイル上の位置や、出力文字数ではありません。

TRY IT — 例を切り替える

3つの表現から同じ「€」へ

A0                 → PDFDocEncoding → €
FE FF 20 AC        → UTF-16BE        → €
EF BB BF E2 82 AC   → UTF-8           → €
バイト列の長さと文字数は一致しない同じ1文字でも1・4・6バイトになります。先頭に付くBOM自体は、出力文字には含めません。

空文字列とBOMだけの入力

空のバイト列 → ""
FE FF        → ""
EF BB BF     → ""
EF BB        → "ï»"（完全なBOMではない）
16進数の桁数と、UTF-16のバイト数は別<FEFF004> は16進数の末尾に0を補い、FE FF 00 40 →「@」。<FEFF00> は桁数が偶数でも、BOMの後に1バイトしかなくUTF-16BEとして不正です。

同じ不正入力に2つの方針

入力バイト列StrictReplace
41 7F 42未割当：位置1A�B
FE FF D8 00 00 41孤立サロゲート：位置2�A
FE FF 00 41 42奇数長：位置4A�
EF BB BF 41 FF 42不正UTF-8：位置4A�B
不正な部分を、正常な文字に見せかけないStrictは最初のエラーで停止し、途中までの文字列を返しません。Replaceは不正部分を置換して続け、後続の正常な文字は残します。

実装テストと照合した説明用の例です。ブラウザ上でRustのデコーダーを実行するものではありません。

置換の単位は、PDFDocEncodingでは未割当バイトごと、UTF-16BEでは孤立コード単位ごとと末尾の余剰1バイトです。UTF-8はRust標準ライブラリの String::from_utf8_lossy に従うため、不正バイト数と置換文字数が常に一致するわけではありません。

06

型とAPIの境界

テキスト用途であることを判断した呼び出し側が、PdfString::as_bytes() を渡して変換を要求します。バイト列からテキストへの暗黙変換はありません。

use pdfmod_core::{
    object::PdfString,
    text_string::{DecodePolicy, PdfTextString},
};

let raw = PdfString::hex(b"\xFE\xFF\x65\xE5\x67\x2C");
let text = PdfTextString::decode(
    raw.as_bytes(), DecodePolicy::Strict,
)?;
assert_eq!(text.as_str(), "日本");
let value: String = text.into();
API・型役割
PdfTextString::decode借用したバイト列を、指定方針で復元。
DecodePolicy::Strict / Replace不正入力を拒否するか、U+FFFDへ置換。
as_str() / Into<String>復元結果の借用／所有権を移す取り出し。
TextDecodeError::kind()未割当バイト、UTF-8不正、孤立サロゲート、奇数長を分類。
offset().value()BOMを含む入力内のバイト位置。ファイルのByteOffsetとは別の型。

このモジュールの責務

3種類の符号化の復元と、不正入力への対応です。元の PdfString とリテラル／16進の表記情報は変更しません。

呼び出し側・後続の責務

暗号化の復号、/Infoなどの辞書の読取り、PDFバージョンとUTF-8使用の整合性、フォント経由の文字復元は含みません。

Unicodeの復元と、表示用の加工は別Unicode文字列内の言語指定エスケープは文字として保持します。言語区間の解釈・除去、Unicode正規化、表示向けの制御文字処理は行いません。既存TypeScript版とは独立しており、低位制御バイトの取り扱いも一致するとは限りません。
