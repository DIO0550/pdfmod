## 1. 概要

有効な PDF ファイルは、物理的に次の 4 つの主要セグメントで構成されます。

```text
+-----------------------------+
| ヘッダ (Header)              |  ← ファイル先頭（バージョン宣言）
+-----------------------------+
| ボディ (Body)                |  ← インダイレクトオブジェクト群
|   1 0 obj ... endobj        |
|   2 0 obj ... endobj        |
|   ...                       |
+-----------------------------+
| 相互参照テーブル (xref)       |  ← オブジェクト位置の索引
+-----------------------------+
| トレイラ (Trailer)           |  ← ドキュメントのエントリーポイント
+-----------------------------+
| startxref + %%EOF           |  ← xref の位置とファイル終端マーカー
+-----------------------------+
```

> **重要**: PDF は**ファイル末尾から逆方向に解析を開始**します。先頭から順に全オブジェクトを読む方式は、巨大なファイルでのパフォーマンスや増分更新（[08章](./08_incremental_update_linearization.md)）の扱いにおいて現実的ではありません。

## 2. ファイルヘッダ

### 2.1 バージョン宣言

ファイルの先頭に配置されるバージョン宣言行です。

```pdf
%PDF-1.7
```

| バージョン | 対応する ISO 規格 |
| :--- | :--- |
| `%PDF-1.0` 〜 `%PDF-1.7` | ISO 32000-1 |
| `%PDF-2.0` | ISO 32000-2 |

### 2.2 バージョンの上書きルール

ファイルヘッダのバージョン宣言は最終値ではありません。ドキュメントカタログ辞書内の `/Version` エントリが、ヘッダのバージョンを**上書き（オーバーライド）**できます。

**判定手順**:

1. ファイルヘッダから暫定バージョンを取得する。
2. ドキュメントカタログ辞書（[03章 §2](./03_document_architecture.md#2-ドキュメントカタログ)）の `/Version` エントリを確認する。
3. `/Version` が存在し、かつヘッダのバージョンより新しい場合は `/Version` を採用する。
4. それ以外（未設定、またはヘッダ以下）の場合はヘッダのバージョンを採用する。

### 2.3 バイナリファイルインジケータ

バイナリデータを含む PDF では、ヘッダの直後に高ビット文字を含むコメント行を配置します。

```pdf
%PDF-1.7
%âãÏÓ
```

- ASCII コード 127 を超えるバイト（`0x80`〜`0xFF`）を **4 バイト以上**含むコメント行（例: `%\xE2\xE3\xCF\xD3\n`）。
- ファイル転送プロトコルやツールに対し、テキストではなくバイナリファイルであることを伝えて改行コード変換による破損を防ぐ。
- **読み込み時**: 通常のコメントとして無視してよい（存在確認に使うことはできる）。
- **書き出し時**: ヘッダ直後に 4 バイト以上の高ビットバイトを含むコメント行を出力する。

## 3. ファイルボディ

ボディ部分にはインダイレクトオブジェクトが並びます。オブジェクトの物理的な配置順序に意味はなく、すべて xref テーブル経由のランダムアクセスで参照されます。

```pdf
1 0 obj
<< /Type /Catalog /Pages 2 0 R >>
endobj

2 0 obj
<< /Type /Pages /Kids [3 0 R] /Count 1 >>
endobj

3 0 obj
<< /Type /Page /Parent 2 0 R /MediaBox [0 0 612 792] /Contents 4 0 R >>
endobj

4 0 obj
<< /Length 44 >>
stream
BT /F1 24 Tf 72 720 Td (Hello World) Tj ET
endstream
endobj
```

## 4. 相互参照テーブル（Xrefテーブル）

相互参照テーブルは「オブジェクト番号 → ファイル内の格納位置」を引く索引です。従来の**テキスト形式**と、PDF 1.5 で導入された**XRef ストリーム形式**の 2 種類があります。

### 4.1 従来のテキストベースxrefテーブル

```pdf
xref
0 6
0000000000 65535 f
0000000009 00000 n
0000000058 00000 n
0000000115 00000 n
0000000206 00000 n
0000000300 00000 n
```

#### テーブル構造

| 行 | 説明 |
| :--- | :--- |
| `xref` | テーブル開始キーワード |
| `0 6` | サブセクションヘッダ（最初のオブジェクト番号とエントリ数） |
| 以降の行 | 各オブジェクトのエントリ（規格上は 20 バイト固定長） |

#### エントリフォーマット（20 バイト固定長）

```text
nnnnnnnnnn ggggg s EOL
|          |     |  |
|          |     |  +-- 行末 (2バイト: CR+LF / SP+LF / SP+CR)
|          |     +----- 状態フラグ (1バイト: 'n' または 'f')
|          +----------- 世代番号 (5桁、0埋め)
+---------------------- バイトオフセット または 次の空きオブジェクト番号 (10桁、0埋め)
```

| フィールド | バイト数 | 説明 |
| :--- | :--- | :--- |
| オフセット / 次空き番号 | 10 | `n` ならファイル先頭からの正確なバイトオフセット、`f` なら次の空きオブジェクト番号 |
| スペース | 1 | 区切り（`0x20`） |
| 世代番号 | 5 | オブジェクトの世代番号（通常 `00000`） |
| スペース | 1 | 区切り（`0x20`） |
| 状態フラグ | 1 | `n`（使用中: in-use） / `f`（空き: free） |
| EOL | 2 | 行末文字（実世界の PDF では 1 バイトの LF / CR のみの場合もあり寛容に扱う） |

#### 特殊ルール（オブジェクト番号 0 と空きリスト）

- **オブジェクト番号 0** は常に世代番号 `65535` の空き（`f`）エントリとして予約され、空きオブジェクト連結リストの先頭（ヘッド）を務める。
- 空き（`f`）エントリの先頭 10 桁フィールドは、オフセットではなく「次の空きオブジェクト番号」を指す（リスト末尾は `0`）。

#### 複数サブセクション

連続しないオブジェクト番号範囲を複数のサブセクションで表現できます。

```pdf
xref
0 3
0000000000 65535 f
0000000009 00000 n
0000000058 00000 n
10 2
0000000300 00000 n
0000000450 00000 n
```

上記の例では、オブジェクト `0`〜`2` と `10`〜`11` の計 5 エントリが定義されています。

#### pdfmod の実装方針（オブジェクト番号 0 の扱い）

xref テーブルのキーには正整数を表す `ObjectNumber`（[01章 §4.4](./01_lexical_conventions.md#44-オブジェクト識別子の構成)）を使うため、番号 `0` はキーとして登録できません。

- 標準的な PDF は `0 N` サブセクションや xref ストリームの `/Index` 既定値 `[0, size]` を通じて必ず 0 番エントリを含みます。
- そのため **0 番エントリの本体は読み進めたうえでエラーにはせず、テーブルへは登録せずに読み飛ばします**。
- `/Size` は 0 番を含めた元の値のまま保持するため、テーブルの登録エントリ数と `/Size` は一致しません。
- この読み飛ばしにより空きリストのヘッド情報は失われるため、将来空きリストの走査・再利用（ライター機能）を実装する際には 0 番エントリの保持方法を別途設計します。

### 4.2 XRefストリーム（PDF 1.5以降）

プレーンテキストの xref テーブルの代わりに、**ストリームオブジェクト内のバイナリデータ**として相互参照情報とトレイラ情報をまとめて格納する形式です。圧縮できるうえ、オブジェクトストリーム（ObjStm）内のオブジェクトも参照できます。

```pdf
15 0 obj
<< /Type /XRef
   /Size 20
   /W [1 3 1]
   /Root 1 0 R
   /Filter /FlateDecode
   /Length 120
>>
stream
... (Flate圧縮されたバイナリデータ) ...
endstream
endobj
```

#### XRef ストリーム辞書の必須・主要エントリ

| キー | 型 | 必須 | 説明 |
| :--- | :--- | :--- | :--- |
| `/Type` | 名前 | **必須** | 必ず `/XRef` |
| `/Size` | 整数 | **必須** | テーブル内の最大オブジェクト番号 + 1 |
| `/W` | 配列 | **必須** | 各フィールドのバイト幅 `[w1, w2, w3]` |
| `/Index` | 配列 | 任意 | サブセクション範囲 `[開始番号, 個数, ...]` のペア列。省略時は `[0, /Size]` |

#### `/W` 配列とバイナリレイアウト

`/W [w1 w2 w3]` は、1 エントリが `w1 + w2 + w3` バイトのビッグエンディアン符号なし整数 3 つで構成されることを示します。

```text
例: /W [1 3 1] → 1エントリ = 5バイト

+----------+--------------------+----------+
|  Type    |      Field2        |  Field3  |
| (w1=1B)  |      (w2=3B)       | (w3=1B)  |
+----------+--------------------+----------+
    01           00 00 09            00
  (通常)        (offset=9)         (gen=0)
```

幅が `0` のフィールドはストリームデータ上に存在せず、規定の既定値が補われます（`w1=0` なら `Type=1`、`w2=0` なら `0`、`w3=0` なら `0`）。

#### エントリタイプ（`Type` 値）別の意味

| `Type` | 種別 | `Field2` の意味 | `Field3` の意味 |
| :--- | :--- | :--- | :--- |
| `0` | 空き（Free） | 次の空きオブジェクト番号（`FreeObjectNumber`。リスト末尾の `0` を許容） | 再利用時の世代番号 |
| `1` | 通常（Used / In-Use） | ファイル先頭からのバイトオフセット | 世代番号 |
| `2` | 圧縮（Compressed） | 親オブジェクトストリームのオブジェクト番号（`ObjectNumber`。`0` は不正） | オブジェクトストリーム内の 0 起点インデックス（世代番号は常に `0`） |

#### デコード手順

1. ストリームを `/Filter`・`/DecodeParms` に従って展開する。
2. 1 エントリ長を `entry_size = w1 + w2 + w3` とし、展開後データを `entry_size` バイト単位で切り出す。
3. 各チャンクから `w1`・`w2`・`w3` バイトをビッグエンディアン符号なし整数として読み取り、`Type` に応じてエントリを構築する。

### 4.3 テキストxrefとXRefストリームの統合

適合リーダーは、テキスト形式とストリーム形式の違いを上位レイヤから隠蔽し、**両形式を単一の相互参照テーブル抽象として扱える**ように設計します。

| 格納場所の種類 | 保持する位置情報 | 対応する元形式 |
| :--- | :--- | :--- |
| ファイル内の直接位置（Direct Offset） | ファイル先頭からのバイトオフセット + 世代番号 | テキスト xref の `n` / XRef ストリームの `Type=1` |
| オブジェクトストリーム内（In Object Stream） | 親 ObjStm のオブジェクト番号 + ストリーム内インデックス | XRef ストリームの `Type=2` |
| 空き（Free） | 次の空き番号 + 世代番号 | テキスト xref の `f` / XRef ストリームの `Type=0` |

### 4.4 ハイブリッド参照ファイル（ISO 32000-1 §7.5.8.4）

XRef ストリーム非対応の古いリーダーとの互換性を保つため、**テキスト xref テーブルと XRef ストリームの両方**を持つファイル形式があります。従来形式のトレイラ辞書に `/XRefStm` キーが含まれ、相互参照ストリームのバイトオフセットを指します。

```text
テキスト形式 xref + trailer
  ├─ /XRefStm ──→ 相互参照ストリーム（ObjStm 内の Type=2 エントリを含む）
  │               ★ 同一更新内ではストリーム側を優先してマージ
  └─ /Prev    ──→ 一つ前の更新の xref セクション（/XRefStm 読込後に辿る）
```

- ObjStm 内オブジェクト（`Type=2`）は `/XRefStm` が指すストリーム側にのみ記録され、テキストテーブル側では `free` または未記載となる。
- XRef ストリーム対応リーダーは、`/Prev` を辿る前に `/XRefStm` のストリームを読み、**ストリーム側のエントリを優先**しなければならない。
- `/XRefStm` を無視すると ObjStm 内オブジェクトが未定義参照（`null`）扱いになり、ページやフォントが静かに欠落する。

## 5. トレイラ辞書（Trailer Dictionary）

### 5.1 解析の開始手順

```text
1. ファイル末尾の %%EOF マーカーを探す
2. %%EOF から上方向へスキャンして startxref キーワードを探す
3. startxref 直後の整数（xref セクションのバイトオフセット）を取得する
4. 指定オフセットの xref を読み込み、トレイラ辞書を取得する
   - テキスト形式: xref テーブル直後の trailer << ... >>
   - ストリーム形式: XRef ストリームオブジェクトの辞書自体
```

### 5.2 従来形式のトレイラ

```pdf
trailer
<< /Size 6
   /Root 1 0 R
   /Info 5 0 R
   /ID [<abc123> <def456>]
>>
startxref
408
%%EOF
```

### 5.3 トレイラ辞書の主要キー

| キー | 型 | 必須 | 説明 |
| :--- | :--- | :--- | :--- |
| `/Root` | 間接参照 | **必須** | ドキュメントカタログへの参照（ドキュメント全体のルート要素） |
| `/Size` | 整数 | **必須** | xref テーブルのエントリ総数（最大オブジェクト番号 + 1） |
| `/Info` | 間接参照 | 任意 | ドキュメント情報辞書への参照（タイトル、作成者、作成日時など） |
| `/ID` | 配列 | 条件付き必須 | 2 つのバイト文字列 `[永続ID, 変更ID]`。ファイルの一意識別や暗号化鍵導出に使用 |
| `/Prev` | 整数（バイトオフセット） | 条件付き | 一つ前の（古い）xref セクションのバイトオフセット（増分更新時） |
| `/Encrypt` | 辞書または間接参照 | 条件付き | 暗号化辞書（[02b章](./02b_encryption.md)） |
| `/XRefStm` | 整数（バイトオフセット） | 条件付き | ハイブリッド参照ファイルの相互参照ストリーム位置（従来形式トレイラのみ。§4.4 参照） |

### 5.4 `/ID` 配列の詳細

```pdf
/ID [<永続ID> <変更ID>]
```

| 要素 | 説明 |
| :--- | :--- |
| 第 1 要素（永続 ID） | ファイル作成時に生成され、以後の編集でも変更されない |
| 第 2 要素（変更 ID） | ファイルが変更されるたびに再生成される |

- PDF 2.0 では `/ID` の記述要件が厳格化されている。
- **暗号化された PDF では `/ID` が必須**であり、R2〜R4 のファイル暗号鍵導出では第 1 要素（永続 ID）を入力に使う（[02b章 §11](./02b_encryption.md#11-r2r4-のファイル暗号鍵を導出する)）。

### 5.5 解析フローの全体手順

PDF バイナリからドキュメント構造を構築する完全な流れは次のとおりです。

```text
[1] ファイル末尾から %%EOF を探索
        ↓
[2] %%EOF の手前から startxref キーワードと xref オフセットを取得
        ↓
[3] 指定オフセットで xref セクション（テキスト or ストリーム）とトレイラ辞書を解析
        ↓
[4] /XRefStm があれば相互参照ストリームを読み込んで優先マージ
        ↓
[5] /Prev チェーンを再帰的に辿り、新しいエントリ優先で全 xref を統合（循環・深度制限を確認）
        ↓
[6] 最新トレイラの /Root を解決してドキュメントカタログを取得
        ↓
[7] カタログからページツリー・メタデータを構築
```

## 6. %%EOF マーカー

- ファイルの論理的な終端を示すマーカー。
- 増分更新（[08章](./08_incremental_update_linearization.md)）が行われた PDF には**複数の `%%EOF` が存在する**ため、パーサは**最後の `%%EOF`** から解析を開始する。
- 実世界の PDF では `%%EOF` の後ろに余分なデータ（ゴミデータ）が付加されていることがあるため、寛容に処理すべきである。

#### 探索アルゴリズム

1. ファイル末尾から**最大 1024 バイト**の範囲で `"%%EOF"` を後方検索する（ISO 32000-1 §7.5.5 の規定）。
2. `%%EOF` の前後にあるホワイトスペースは許容する。
3. 1024 バイト以内に見つからない場合、厳格モードではエラーとし、寛容モードでは検索範囲を拡大して再探索する（pdfmod の解析パイプラインでは最大 4096 バイトまで拡大し警告を発行する）。
