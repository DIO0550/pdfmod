## 1. 概要

PDF 仕様は、ファイルの更新・最適化に関して 2 つの対照的な構造アプローチを備えています。

| アプローチ | 目的 | 構造の方向 |
| :--- | :--- | :--- |
| インクリメンタルアップデート | 高速な追記保存・履歴保持・デジタル署名の保全 | 既存データを触らずファイル末尾に追記 |
| リニアライズ（Fast Web View） | ネットワーク経由での 1 ページ目即座表示 | ファイル全体のオブジェクト配置を再構成 |

> **重要**: この 2 つは構造的に**相互排他**です。リニアライズ済み PDF に増分更新を追記すると、リニアライズの前提が崩れます（§4）。

## 2. インクリメンタルアップデート

### 2.1 基本原理

PDF に変更を加える際、元のファイルのバイト列には**一切手を加えず**、追加・変更されたオブジェクトと新しい xref・トレイラをファイル末尾へ追記します。

```text
+----------------------------------+
| 元のヘッダ                        |
| 元のボディ                        |
| 元の xref テーブル                |
| 元のトレイラ                       |
| 元の %%EOF                        |
+----------------------------------+  ← 元のファイル終端（ここまでは不変）
| 追加・変更されたオブジェクト群      |  ← 追記部分
| 新しい xref テーブル              |
| 新しいトレイラ (/Prev 付き)        |
| 新しい %%EOF                      |
+----------------------------------+
```

### 2.2 主な使用シーン

- フォーム入力データの保存
- 注釈（アノテーション）の追加・編集
- デジタル署名の適用（§5）
- ページの追加・削除・回転
- メタデータの更新

### 2.3 インクリメンタルアップデートの構造

追記されるトレイラ辞書には、直前の xref テーブルのバイトオフセットを指す `/Prev` キーを含めます。

```pdf
trailer
<< /Size 25
   /Root 1 0 R
   /Prev 408          % 一つ前の xref テーブルのバイトオフセット
   /Info 5 0 R
>>
startxref
1024                  % 今回の新しい xref テーブルのバイトオフセット
%%EOF
```

パーサは最新トレイラの `/Prev` を次々に辿ることで、過去すべての更新履歴（**xref テーブルの連鎖**）へ到達します。

### 2.4 解析アルゴリズム

```text
[1] 末尾の %%EOF → startxref から最新の xref とトレイラを読む
        ↓
[2] visited オフセット集合に開始オフセットを登録（循環参照防止）
        ↓
[3] トレイラに /Prev（およびハイブリッド時は /XRefStm）がある間、反復:
      - 訪問済みオフセットなら循環エラー / 深度上限超過ならエラー
      - 指定オフセットの xref とトレイラを読み込む
        ↓
[4] 全セクションをマージ
      - 同一オブジェクト番号は「新しいセクションのエントリ」を優先
      - 新しい側に無い番号だけ古いセクションから補完
```

### 2.5 オブジェクトの削除

増分更新でオブジェクトを削除するときは、元のオブジェクト実体を消さず、新しい xref テーブルでその番号に **`f`（free）** フラグを設定し、世代番号を +1 します。

```pdf
xref
0 1
0000000000 65535 f         % オブジェクト 0: 空きリストのヘッド
5 1
0000000000 00003 f         % オブジェクト 5 を削除（世代番号 2 → 3）
```

| フィールド | 値 | 説明 |
| :--- | :--- | :--- |
| オフセット欄 | 次の空きオブジェクト番号 | 空きオブジェクト連結リストの次要素（末尾は `0`） |
| 世代番号 | インクリメント後の値 | 将来再利用されるときの世代番号 |
| フラグ | `f` | 空き（free）状態 |

### 2.6 ネイティブなバージョン管理

元のバイト列がそのまま残るため、PDF はファイル自体にバージョン履歴を内包しています。

**直前の更新をロールバックする手順**:

1. ファイル末尾から最後の `%%EOF` を特定する。
2. それより前に存在する 1 つ前の `%%EOF` を特定する。
3. 1 つ前の `%%EOF`（直後の改行を含む）の位置でファイルを切り捨てることで、更新前の PDF を完全に復元できる。

### 2.7 適合ライターの実装要件

増分保存を行うライターは次の手順でファイル末尾へ追記します。

1. **変更オブジェクトの追記**: 変更・追加された各オブジェクトをファイル末尾へ書き出し、新しいバイトオフセットと世代番号を記録する（削除対象は本体を書かず `f` エントリのみ記録）。
2. **新 xref テーブルの書き出し**: 記録したエントリだけをサブセクションとして書き出し、その開始位置を `xref_offset` とする。
3. **新トレイラの書き出し**: 元の最新 xref オフセットを `/Prev` に設定し、更新後の `/Size`・`/Root` 等を含むトレイラを書き出す。
4. **終端マーカーの書き出し**: `startxref`、`xref_offset`、`%%EOF` を書き出す。

## 3. リニアライズ（Fast Web View）

### 3.1 基本原理

ファイル全体のダウンロード完了を待たずに**1 ページ目を即座にストリーミング表示**できるよう、オブジェクトと xref の物理配置を最適化・再構成する形式です。

### 3.2 標準 PDF の問題

```text
標準的な PDF:
  ヘッダ → ボディ（全ページのオブジェクト）→ xref → トレイラ → %%EOF
                                                    ↑
                                            解析の起点が末尾にある
→ 1 ページ目を表示するだけでもファイル全体のダウンロードが必要
```

### 3.3 リニアライズされた PDF の構造

```text
+-------------------------------------------+
| ヘッダ (%PDF-1.7)                          |
+-------------------------------------------+
| リニアライズ化パラメータ辞書               |  ← ファイル先頭付近の最初のオブジェクト
+-------------------------------------------+
| 1 ページ目用 xref テーブル (Part 1)        |
+-------------------------------------------+
| ドキュメントカタログ                       |
| ページツリーのルート                       |
| 1 ページ目のページ辞書・フォント・画像      |
| 1 ページ目のコンテンツストリーム            |
+-------------------------------------------+  ← ここまで届いた時点で 1 ページ目を表示可能
| 残りのページのオブジェクト群 + ヒント       |
+-------------------------------------------+
| 残りのページ用 xref テーブル (Part 2)      |
+-------------------------------------------+
| トレイラ + startxref + %%EOF               |
+-------------------------------------------+
```

### 3.4 リニアライズ化パラメータ辞書

ファイルヘッダの直後に配置される最初の間接オブジェクトです。

```pdf
1 0 obj
<< /Linearized 1.0
   /L 54321          % ファイル全体の総バイト数
   /H [200 50]       % ヒントストリームの [オフセット, 長さ]
   /O 5              % 1 ページ目のページオブジェクト番号
   /E 1024           % 1 ページ目セクションの終了オフセット
   /N 10             % ドキュメントの総ページ数
   /T 53000          % メイン xref テーブルのオフセット
>>
endobj
```

| キー | 型 | 説明 |
| :--- | :--- | :--- |
| `/Linearized` | 実数 | リニアライズ仕様バージョン（常に `1.0`） |
| `/L` | 整数 | ファイルの総バイト数（改変・増分更新の検出に利用） |
| `/H` | 配列 | ヒントストリームの `[オフセット, 長さ]`（オーバーフロー時は 4 要素） |
| `/O` | 整数 | 1 ページ目のページオブジェクト番号 |
| `/E` | 整数 | 1 ページ目セクションの終了バイトオフセット |
| `/N` | 整数 | ドキュメントの総ページ数 |
| `/T` | 整数 | メイン xref テーブル（または XRef ストリーム）のオフセット |

### 3.5 ヒントテーブル

2 ページ目以降をオンデマンド取得するための追加索引です。

**HTTP Range Request によるオンデマンド表示フロー**:

1. ページオフセットヒントテーブルから、目的のページ N に必要なオブジェクト群のバイト範囲を取得する。
2. 該当するバイト範囲だけをサーバーへリクエスト（HTTP Range Request）する。
3. 取得した部分データからページ N を描画する。

### 3.6 2 段階 xref 構造

| セクション | 配置場所 | 含まれる対象 |
| :--- | :--- | :--- |
| Part 1 xref | ファイル先頭付近 | カタログ、ページツリールート、1 ページ目関連の全オブジェクト |
| Part 2 xref | ファイル末尾付近 | 2 ページ目以降の全オブジェクト、ヒントテーブル |

### 3.7 リニアライズの検出と検証

| 確認ステップ | 結果 | 判定ステータス |
| :--- | :--- | :--- |
| 1. ファイル先頭オブジェクトに `/Linearized` キーがあるか | 存在しない | **NotLinearized**（非リニアライズ） |
| 2. ファイル内の `%%EOF` が複数あるか（増分更新の有無） | 2 個以上 | **LinearizedButModified**（リニアライズ後に増分更新済み） |
| 3. `/L` の値と実ファイルサイズが一致するか | 不一致 | **LinearizedButCorrupted**（リニアライズ情報破損） |
| すべて通過 | 一致 | **Valid**（有効なリニアライズ PDF） |

## 4. インクリメンタルアップデートとリニアライズの相互排他性

### 4.1 構造的な非互換性

リニアライズ済み PDF に対してインクリメンタルアップデートを行うと、新しいオブジェクトや更新後のトレイラが末尾に追記され、先頭の 1 ページ目配置・`/L` サイズ・2 段階 xref の整合性が崩壊するため、Fast Web View の恩恵は失われます。

### 4.2 パーサの判断ロジック

| 検出ステータス（§3.7） | 採用する解析戦略 |
| :--- | :--- |
| `Valid` | **ストリーミング最適化解析**（先頭から 1 ページ目を即時表示し、残りはヒントで取得） |
| `LinearizedButModified` | **通常の末尾からの解析**（最新の増分更新を反映するため） |
| `NotLinearized` / `LinearizedButCorrupted` | **通常の末尾からの解析** |

### 4.3 再リニアライズ

増分更新後に再び Fast Web View に対応させるには、ファイル全体を**完全再構築**します。

1. 全 xref チェーンをマージして最新のオブジェクトテーブルを確定する。
2. 削除済み・未参照の不要オブジェクトを除外（ガベージコレクション）する。
3. 1 ページ目描画に必要なオブジェクト群を特定し、先頭セクションへ集約する。
4. 残りページのオブジェクトを配置し、ヒントテーブルを生成する。
5. リニアライズパラメータ辞書と 2 段階 xref を再計算してファイル全体を書き出す。

## 5. デジタル署名とインクリメンタルアップデート

### 5.1 署名の保全

デジタル署名が含まれる PDF では、インクリメンタルアップデートが**既存署名を壊さずに追記できる唯一の変更方法**です。

- デジタル署名は、署名時点のファイルバイト列に対する暗号学的ハッシュに署名している。
- 元のバイト列を 1 バイトでも書き換えるとハッシュが変わり、署名が無効になる。
- 増分更新なら元のバイト列を保全したまま新しい注釈や 2 つ目の署名を追記でき、検証時には署名ごとの対象バイト範囲でハッシュを再計算できる。

### 5.2 署名のバイト範囲（`/ByteRange`）

```pdf
<< /Type /Sig
   /Filter /Adobe.PPKLite
   /SubFilter /adbe.pkcs7.detached
   /ByteRange [0 840 960 240]    % [offset1 length1 offset2 length2]
   /Contents <...署名データ...>
>>
```

```text
ファイル先頭                                                 署名時点の末尾
[ 0 ──────── 839 ][ 840 ─────── 959 ][ 960 ───────── 1199 ]
  ハッシュ対象 ①     /Contents 値本体      ハッシュ対象 ②
  (offset=0, len=840)  (計算から除外)     (offset=960, len=240)
```
