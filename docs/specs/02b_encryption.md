## 1. 暗号化辞書の位置づけ

暗号化された PDF では、トレイラの `/Encrypt` が**暗号化辞書**を指します（[02章 §5.3](./02_file_structure.md#53-トレイラ辞書の主要キー)）。この辞書は「どのセキュリティハンドラが、どの方式で、どの対象を暗号化しているか」を記述します。

- `/Encrypt` の値は**間接参照でも直接辞書でも**記述できる。
- 暗号化辞書自体はオブジェクトストリーム（ObjStm）に格納できない（復号の起点であり、復号前に平文で読める必要があるため）。
- 暗号化された文書ではトレイラの `/ID` が必須。R2〜R4 では第 1 要素（永続 ID）を鍵導出に使う。
- 暗号化の対象は**文字列とストリーム**に限られ、辞書のキー名・数値・名前オブジェクト・配列構造自体は暗号化されない。

セキュリティハンドラは `/Filter` で識別します。ISO が規定するのはパスワードベースの**標準セキュリティハンドラ**（`/Standard`）です。公開鍵ベースの `/Adobe.PubSec` などは、ハンドラ固有の追加キー（`/Recipients` など）を持ちます。

## 2. 標準セキュリティハンドラのキー

ISO 32000-1 表 20（共通）・表 21（標準ハンドラ）に基づく主要キーです。

| キー | 型 | 必須 | 既定値 | 意味 |
| :--- | :--- | :--- | :--- | :--- |
| `/Filter` | 名前 | **必須** | — | セキュリティハンドラ名。標準は `/Standard` |
| `/SubFilter` | 名前 | 任意 | — | ハンドラ固有のサブ形式（公開鍵ハンドラなどで使用） |
| `/V` | 整数 | **必須** | — | アルゴリズム版（§3）。ISO は既定値 `0`（未文書化アルゴリズム）を定めるが、**pdfmod では欠落を構造不正として扱う** |
| `/R` | 整数 | **必須** | — | ハンドラのリビジョン（§3） |
| `/Length` | 整数 | 任意 | `40` | ファイル暗号鍵の長さ（ビット）。`40..=128` かつ 8 の倍数 |
| `/O` | 文字列 | **必須** | — | 所有者パスワードから導出した値（R2〜R4 は 32 バイト、R5・R6 は 48 バイト） |
| `/U` | 文字列 | **必須** | — | 利用者パスワードから導出した値（長さは `/O` と同じ） |
| `/OE` | 文字列 | R5・R6 で必須 | — | 所有者用の暗号化ファイル鍵（32 バイト） |
| `/UE` | 文字列 | R5・R6 で必須 | — | 利用者用の暗号化ファイル鍵（32 バイト） |
| `/P` | 整数 | **必須** | — | アクセス権限フラグ。符号付き 32 ビット整数（§5） |
| `/Perms` | 文字列 | R5・R6 で必須 | — | 権限の暗号化コピー（16 バイト） |
| `/EncryptMetadata` | 真偽値 | 任意 | `true` | 文書メタデータを暗号化するか（`/V 4` 以降） |
| `/CF`, `/StmF`, `/StrF`, `/EFF` | — | `/V 4` 以降 | — | crypt filter 定義と適用先（§4） |

## 3. `/V` と `/R` の組み合わせ

`/V`（アルゴリズム版）と `/R`（ハンドラのリビジョン）の有効な組み合わせは、仕様上次の **6 種** に限られます。

```text
   /V \ /R │  2        3        4        5        6      その他
  ─────────┼────────────────────────────────────────────────────
      0    │  ✗        ✗        ✗        ✗        ✗        ✗     ← 未文書化アルゴリズム
      1    │ V1R2     V1R3      ✗        ✗        ✗        ✗
      2    │  ✗       V2R3      ✗        ✗        ✗        ✗
      3    │  ✗        ✗        ✗        ✗        ✗        ✗     ← 非公開アルゴリズム
      4    │  ✗        ✗       V4R4      ✗        ✗        ✗
      5    │  ✗        ✗        ✗       V5R5     V5R6      ✗
    その他  │  ✗        ✗        ✗        ✗        ✗        ✗
```

| 組み合わせ | 暗号方式 | 鍵長 | 備考 |
| :--- | :--- | :--- | :--- |
| `/V 1` `/R 2` | RC4 | 40 ビット固定 | 最初期の暗号化 |
| `/V 1` `/R 3` | RC4 | 40 ビット固定 | リビジョン 3 固有の権限ビットを使う場合 |
| `/V 2` `/R 3` | RC4 | `/Length`（40..=128） | 可変長 RC4 |
| `/V 4` `/R 4` | crypt filter で選択 | `/Length` | `/CF` で方式を指定（RC4 / AES-128 など） |
| `/V 5` `/R 5` | AES-256 | 256 ビット固定 | Adobe ExtensionLevel 3（ISO 32000-2 で非推奨） |
| `/V 5` `/R 6` | AES-256 | 256 ビット固定 | ISO 32000-2 §7.6.4.3（現行推奨） |

> `/V 0`（未文書化）および `/V 3`（非公開）はアルゴリズム内容が仕様に規定されていません。

## 4. crypt filter

`/V 4` 以降では、暗号化辞書直下で単一方式を決める代わりに **crypt filter** で対象ごとに暗号方式を切り替えます。

### 4.1 適用先の指定キー（暗号化辞書直下）

| キー | 型 | 既定値 | 意味 |
| :--- | :--- | :--- | :--- |
| `/CF` | 辞書 | — | crypt filter 名 → crypt filter 辞書の対応表 |
| `/StmF` | 名前 | `/Identity` | ストリームに適用する crypt filter 名 |
| `/StrF` | 名前 | `/Identity` | 文字列に適用する crypt filter 名 |
| `/EFF` | 名前 | — | 埋め込みファイルストリームに適用する crypt filter 名 |

`/Identity` は `/CF` に定義されない**組み込みの名前**で「暗号化しない」を意味します。`/StmF`・`/StrF`・`/EFF` に `/Identity` 以外の名前を指定する場合、その名前は `/CF` 辞書に定義されていなければなりません。

### 4.2 `/CF` の各エントリ（crypt filter 辞書、ISO 32000-1 表 25）

| キー | 型 | 既定値 | 意味 |
| :--- | :--- | :--- | :--- |
| `/CFM` | 名前 | `/None` | 暗号方式: `/None`（無暗号）/ `/V2`（RC4）/ `/AESV2`（AES-128）/ `/AESV3`（AES-256） |
| `/AuthEvent` | 名前 | `/DocOpen` | 認証タイミング: `/DocOpen`（文書オープン時）/ `/EFOpen`（添付ファイルオープン時） |
| `/Length` | 整数 | — | 鍵長（ISO は**バイト単位**と規定するが、ビット単位で出力する実装も存在する） |

#### pdfmod の実装方針（`/CF` 内 `/Length` の単位正規化）

バイト表記（`5..=16`）とビット表記（`40..=128` かつ 8 の倍数）は定義域が重ならないため、一意に判別できます。

| 入力値の範囲 | 解釈 |
| :--- | :--- |
| `5..=16` | バイト表記とみなして 8 倍する（`40..=128` ビット） |
| `40..=128` かつ 8 の倍数 | ビット表記としてそのまま受理する |
| 上記以外（`32`・`256`・型不一致・間接参照など） | エラーにせず**無視**する（`/V 5` の AES-256 鍵長は版から 256 ビットと確定するため） |

## 5. アクセス権限フラグ `/P`

`/P` は符号付き 32 ビット整数のビットフラグです（ISO 32000-1 表 22）。ビット位置は **1 起点（LSB = ビット 1）** で数え、`1` が許可、`0` が禁止を表します。ビット 1–2 と 7–8 は予約（常に `1`）です。

| ビット | 意味 |
| :--- | :--- |
| 3 | 印刷（`/R 3` 以上では低解像度印刷） |
| 4 | 内容の変更 |
| 5 | テキスト・グラフィックスの抽出 |
| 6 | 注釈の追加・変更、フォームフィールドの記入 |
| 9 | フォームフィールドの記入（`/R 3` 以上） |
| 10 | アクセシビリティ目的の抽出（ISO 32000-2 で非推奨） |
| 11 | 文書の組み立て（ページの挿入・回転・削除） |
| 12 | 高解像度での印刷（`/R 3` 以上） |

> **実ファイル上の注意**: `/P` を符号なし 32 ビット表記（例: `4294967292` = `-4` と同一ビットパターン）で書き出す PDF ライタが存在します。

## 6. pdfmod での扱い

### 6.1 現在の実装範囲と境界

| 領域 | 現状の扱い |
| :--- | :--- |
| 暗号化辞書の型化 | Rust（`crate::encrypt::EncryptDictionary`）と TypeScript（`EncryptDictionary.fromDictionary(dictionary, offset)`）の両方で提供 |
| `/V` × `/R` の型制約 | §3 の 6 種だけを `StandardAlgorithm` として表現し、不正な組み合わせを構築不可にする |
| 未対応ハンドラ・未対応版 | `/Adobe.PubSec` や未対応の `/V`×`/R` は `EncryptDictionary::Unsupported` に生辞書を保持して**解析を止めない** |
| 構造不正エラー | `/Filter`・`/V`・`/R` の欠落や Standard 辞書の構造不正は `EncryptError` として位置情報付きで報告する |
| 鍵導出・パスワード認証（Rust） | R2〜R4 の鍵導出は §11、R5・R6 の鍵導出・権限検証は §12、全リビジョンのパスワード認証と役割判定の入口は §13 で実装済み |
| オブジェクトの復号鍵（Rust） | `AuthenticatedFileKey` と対象から方式を選び、Algorithm 1 / 1.A に従って鍵を返す（§14） |
| TypeScript `PdfDocument.load` | 復号未対応のため、暗号化 PDF は引き続き拒否する（暗号化辞書の型化 API は独立提供） |
| 今後の対応範囲 | 文字列・ストリームへの復号の適用と、`ObjectResolver`・`PdfDocument` への統合（#683） |

### 6.2 TypeScript と Rust の共通解析方針

| 項目 | 共通の検証・正規化ルール |
| :--- | :--- |
| 直下の `/Length` | `/V 1` は 40 ビット固定、`/V 5` は 256 ビット固定（直下の `/Length` は使用しない）。`/V 2`・`/V 4` では直下の `/Length` を検証し、省略時は 40 ビット |
| `/CF` の必須性 | `/V 4`・`/V 5` では `/CF` を必須とし、空辞書は受理する |
| `/CF` 内の `/AuthEvent` | 省略・未知名・型不一致は `/DocOpen` として扱う |
| `/CF` 内の `/Length` | §4.2 の単位正規化で解釈できる直接整数だけを保持し、それ以外は無視する |
| `/P` の受理範囲 | `-2147483648..=4294967295` の整数を受理し、符号付き 32 ビットの同一ビットパターンへ正規化する |
| `/O`, `/U`, `/OE`, `/UE`, `/Perms` | 辞書解析時にはバイト長を検証せず生のバイト列のまま保持する（長さ検証は鍵導出側の責務） |
| 辞書内の間接参照 | 暗号化辞書の中に書かれた間接参照（`/Length 5 0 R` など）は解決しない |
| 未対応時の検証範囲 | 未対応の `/V`×`/R` は `/V`・`/R` の型を検証したうえで生辞書を保持する。未対応ハンドラは `/Filter` のみ検証する |
| TS 版のエラー位置情報 | `EncryptError` はキーのパスと呼び出し側が渡した辞書の開始位置を保持する（個々の値の位置は取得しない） |

## 7. 旧リビジョンの鍵導出に使う MD5

ISO 32000-1 §7.6.3.3 の **Algorithm 2** は、R2〜R4 のファイル暗号鍵導出に MD5 を使用します。

### 仕様と仕組み（RFC 1321 §3）

- 入力を **64 バイトブロック**単位で処理し、**16 バイト**のダイジェストを出力する。
- パディング: 入力末尾に `0x80` を 1 バイト追加し、ブロック長 56 バイト（mod 64）になるまで `0x00` で埋めた後、元のビット長の下位 64 ビットを**リトルエンディアン**で 8 バイト付加する。

### pdfmod（Rust）での提供機能

- 内部モジュール `encrypt::md5` が逐次入力（`update` / `finalize`）と一括計算（`digest`）を提供する。
- `digest` はヒープ確保を行わないため、R3・R4 の鍵導出で行う「先頭 `n` バイトの 50 回再ハッシュ」にそのまま利用できる。
- **用途制限**: 既存 PDF との互換性に限って使用し、新規のセキュリティ用途には使わない。

## 8. 旧形式の暗号化に使う RC4

ISO 32000-1:2008 §7.6.2 の旧形式では、`/V 1`・`/V 2`、または `/V 4` で `/CFM /V2` が選ばれた場合にストリーム暗号 **RC4** を使います。文字列・ストリームごとに、Algorithm 1 でファイル暗号鍵とオブジェクト番号・世代番号から導出した鍵を適用します。

### アルゴリズムの流れ

```text
鍵 (5〜16バイト)
  │
  ▼
[1] KSA (鍵スケジューリング)
    0〜255 の置換表 S を初期化し、鍵バイトを繰り返し使って要素を交換する
  │
  ▼
[2] PRGA (疑似乱数生成)
    2つの添字 (i, j) を 0 から始め、mod 256 で加算・交換しながら
    入力 1 バイトごとに鍵ストリームを 1 バイト生成する
  │
  ▼
[3] XOR 適用
    入力バイト ^ 鍵ストリーム = 出力バイト
    ※ 同じ鍵で再度 XOR すると元に戻るため、暗号化と復号は同一処理になる
```

### pdfmod（Rust）での提供機能

- 内部型 `encrypt::rc4::Rc4` は **5〜16 バイト**の鍵を受理し、範囲外は `None` を返す。
- `apply` はスライスをインプレース更新し、分割入力に対しても同一の鍵ストリーム状態を継続する（空スライスでは状態を進めない）。
- R2〜R4 のパスワード認証では §13 のとおり `/U` の照合と `/O` の復号に使う。PDF 読み込み時の文字列・ストリーム復号への接続は #683 で扱う。

## 9. リビジョン6の鍵導出に使う SHA-2

ISO 32000-2:2020 §7.6.4.3 の **Algorithm 2.A** は、ファイル暗号鍵導出の途中で **Algorithm 2.B** を呼び出します。Algorithm 2.B では SHA-256 で初期値を作り、AES の出力に応じて **SHA-256 / SHA-384 / SHA-512** を切り替えながら反復計算します（詳細は §12）。

### 3 方式の比較（FIPS 180-4 §5.1–5.3, §6.2, §6.4–6.5）

| 方式 | ブロック長 | 元のビット長欄（ビッグエンディアン） | ダイジェスト長 |
| :--- | :--- | :--- | :--- |
| SHA-256 | 64 バイト | 8 バイト | 32 バイト |
| SHA-384 | 128 バイト | 16 バイト | 48 バイト |
| SHA-512 | 128 バイト | 16 バイト | 64 バイト |

- SHA-384 は SHA-512 と圧縮関数を共有し、専用の初期値から計算した最終状態の先頭 6 ワード（48 バイト）を出力する。
- パディングは終端 `0x80`、`0x00` 埋め、元のビット長の**ビッグエンディアン**表現を補う。

### pdfmod（Rust）での提供機能

- 内部モジュール `encrypt::sha2` が上記 3 方式の逐次入力（`update` / `finalize`）とヒープ確保なしの一括計算（`digest`）を提供する。
- `update` は元のビット長が長さ欄に収まらない場合、内部状態を壊さず `None` を返す。`finalize` は固定長配列でダイジェストを返す。

## 10. AES-128 / AES-256 の復号

PDF の crypt filter では `/CFM /AESV2` が **AES-128**（ISO 32000-1:2008 §7.6）、`/CFM /AESV3` が **AES-256**（R5 は Adobe ExtensionLevel 3、R6 は ISO 32000-2:2020 §7.6.4.3）を表します。鍵長はそれぞれ 16 / 32 バイト、ブロック長はいずれも 16 バイトです（FIPS 197 §5.2–5.3）。

### 対象ごとの暗号利用モード

| 対象 | 方式 | 初期化ベクトル（IV） | パディング（PKCS#7） |
| :--- | :--- | :--- | :--- |
| `/AESV2` の文字列・ストリーム | AES-128-CBC | データの先頭 16 バイト | 末尾 1〜16 バイトを検証して除去 |
| `/AESV3` の文字列・ストリーム | AES-256-CBC | データの先頭 16 バイト | 末尾 1〜16 バイトを検証して除去 |
| `/Perms`（R5・R6 の権限コピー） | AES-256-ECB | なし | なし（16 バイトすべて保持） |

### PDF における AES-CBC データのレイアウト

```text
|<--- 16 バイト --->|<--- 16 バイト × N ブロック（N ≥ 1）--->|
+-------------------+------------------+--------------------+
|        IV         |   暗号文ブロック 1  |   暗号文ブロック N   |
+-------------------+------------------+--------------------+
                                                 │ 復号後の末尾に
                                                 ▼ パディング n バイト（値 = n）
                      例: 平文が空でも 0x10 が 16 個並ぶため、IV 含め最小 32 バイト
```

- **CBC 復号**（NIST SP 800-38A §6.2）: 各ブロックを AES 逆変換し、1 ブロック目は IV と、2 ブロック目以降は直前の暗号文ブロックと XOR する。
- **パディング検証**: 末尾バイトの値 `n`（`1..=16`）に対し、末尾 `n` バイトすべてが `n` であることを確認して除去する。

### pdfmod（Rust）での提供機能

内部型 `encrypt::aes::Aes` は固定長鍵からラウンド鍵（AES-128 は 11 個、AES-256 は 15 個）を生成し、次の操作を提供します。

| 操作 | 用途 | 主なエラー |
| :--- | :--- | :--- |
| `decrypt_pdf_cbc` | 文字列・ストリームの CBC 復号 + パディング除去 | `InvalidLength`（IV 不足・暗号文が空・16 バイトの倍数でない） / `InvalidPadding`（パディング不正） |
| `decrypt_ecb_block` | `/Perms` 用の 16 バイト固定長 ECB 復号 | — |

## 11. R2〜R4 のファイル暗号鍵を導出する

ISO 32000-1:2008 §7.6.3.3 の **Algorithm 2** に基づき、パスワードと暗号化辞書からファイル暗号鍵を求めます（Rust では `StandardSecurityHandler::derive_legacy_file_key`）。

### 鍵長 `n`（バイト数）の決定

| 組み合わせ | 鍵長 `n` |
| :--- | :--- |
| `/V 1 /R 2` または `/V 1 /R 3` | 5 バイト（40 ビット固定） |
| `/V 2 /R 3` または `/V 4 /R 4` | 辞書直下の `/Length ÷ 8`（省略時は 5 バイト） |

### 導出手順

```text
[Step 1] パスワードを 32 バイトに整える
         - 32 バイト未満: 規定パディング列の先頭から補う
         - 32 バイト超過: 先頭 32 バイトへ切り詰める
                │
                ▼
[Step 2] 以下を順に連結して MD5 へ入力
         ① 32 バイト化したパスワード
         ② /O（32 バイト）
         ③ /P（符号付き 32 ビット整数のリトルエンディアン 4 バイト）
         ④ トレイラ /ID の第 1 要素（永続 ID）
         ⑤ [R4 かつ /EncryptMetadata = false のみ] FF FF FF FF
                │
                ▼
[Step 3] R3・R4 のみ: 直前のダイジェスト先頭 n バイトに対し MD5 を 50 回反復
                │
                ▼
[Step 4] 最終ダイジェストの先頭 n バイト ＝ ファイル暗号鍵
```

> `/P` が pdfmod で受理する符号なし表記で書かれていた場合も、同一の 32 ビットパターンから 4 バイトへ変換します。

### pdfmod のエラー条件

| 条件 | 返すエラー |
| :--- | :--- |
| トレイラの `/ID` が欠けている（空の永続 ID を含む 2 要素の `/ID` は受理） | `MissingFileId` |
| `/O` が 32 バイトでない | `InvalidOwnerEntryLength` |

> `/U`・`/O` によるパスワード認証は §13 で扱います。

## 12. R5・R6 の AES-256 ファイル暗号鍵と権限の検証

ISO 32000-2:2020 §7.6.4.3 の **Algorithm 2.A / 2.B** に基づき、利用者または所有者のパスワード検証、中間鍵の導出、ファイル暗号鍵の復号、権限ブロック `/Perms` の照合を行います（Rust では `StandardSecurityHandler::derive_aes256_file_key(role, prepared_password)`）。

### 12.1 パスワードの準備（呼び出し側の責務）

- **SASLprep 非実装**: pdfmod は SASLprep（RFC 4013 の文字マッピング・NFKC 正規化・禁止文字/双方向性検査）を実装しないため、必要に応じて呼び出し側で正規化する。
- **127 バイト切り詰め**: 受け取った UTF-8 文字列の**先頭 127 バイト**を使用する（末尾がマルチバイト文字の途中であっても 127 バイト位置で切る）。空文字列は 0 バイトの入力となる。

### 12.2 役割ごとの参照項目と `/U`・`/O` のバイト構造

| 役割 | 検証値とソルトを読む項目（48 バイト） | ハッシュ末尾に加える利用者情報 | 復号する暗号化鍵（32 バイト） |
| :--- | :--- | :--- | :--- |
| 利用者（User） | `/U` | 空（0 バイト） | `/UE` |
| 所有者（Owner） | `/O` | `/U` の全 48 バイト | `/OE` |

```text
/U または /O（計 48 バイト）:
+----------------------------------------+-------------------+-------------------+
|        期待する検証ハッシュ (32B)        |  検証用ソルト (8B) |   鍵用ソルト (8B)  |
+----------------------------------------+-------------------+-------------------+
 0                                     31 32               39 40               47
```

### 12.3 導出と検証の全体手順（Algorithm 2.A）

1. **長さ確認**: 役割に対応する `/U`・`/O`（48 バイト）、`/UE`・`/OE`（32 バイト）、`/Perms`（16 バイト）の長さを確認する。
2. **パスワード検証**: `パスワード || 検証用ソルト || 利用者情報` をハッシュし、先頭 32 バイトの期待値と比較する（不一致なら失敗）。
3. **中間鍵の導出**: ソルトを**鍵用ソルト**に差し替えて同様に再計算し、32 バイトの中間鍵を得る。
   - **R5**: 手順 2・3 ともに単発の SHA-256 を使用。
   - **R6**: 手順 2・3 ともに次の **Algorithm 2.B（反復ハッシュ）** を使用。
4. **ファイル暗号鍵の復号**: 中間鍵で `/UE` または `/OE`（32 バイト）を **AES-256-CBC**（IV = 全ゼロ 16 バイト、パディングなし）で復号し、32 バイトのファイル暗号鍵を得る。
5. **権限ブロック `/Perms` の検証**: 得たファイル暗号鍵で `/Perms`（16 バイト）を **AES-256-ECB** で復号し、次のレイアウトと一致する場合にのみファイル暗号鍵を返す。

```text
復号後の /Perms（計 16 バイト）:
+------------------+------------------+-----+-----------+--------------+
| /P (LE 4B)       | FF FF FF FF (4B) | T/F |  "adb"    |   乱数 (4B)  |
+------------------+------------------+-----+-----------+--------------+
 0                3 4                7   8   9        11 12          15
                                         │
                                         └─ /EncryptMetadata が true なら ASCII 'T'、false なら 'F'
```

### 12.4 R6 の反復ハッシュ（Algorithm 2.B）

```text
初期値: K = SHA-256(パスワード || ソルト || 利用者情報)   [32 バイト]

ラウンド r = 0, 1, 2, ... を反復:
  1. K1 = (パスワード || K 全体 || 利用者情報) を 64 回繰り返したバイト列
  2. E  = AES-128-CBC 暗号化(データ = K1, 鍵 = K[0..16], IV = K[16..32], パディングなし)
  3. E の先頭 16 バイトをビッグエンディアン整数とみなし、3 で割った余りで次ハッシュを選択:
       - 余り 0 → K = SHA-256(E)  [32 バイト]
       - 余り 1 → K = SHA-384(E)  [48 バイト]
       - 余り 2 → K = SHA-512(E)  [64 バイト]
  4. 終了条件: 完了したラウンド数 ≥ 64  かつ  完了したラウンド数 ≥ (E の末尾バイト + 32)
               を満たしたら終了し、最終 K の先頭 32 バイトを出力する
```

### 12.5 pdfmod のエラー種別

| エラー | 発生条件 |
| :--- | :--- |
| `IncorrectPassword` | 検証ハッシュが `/U` または `/O` の先頭 32 バイトと一致しない |
| `InvalidPermissions` | 復号した `/Perms` の `/P`・`FF FF FF FF`・`T`/`F`・`adb` のいずれかが一致しない |
| `InvalidEntryLength` | 必要な辞書項目のバイト長が規定と異なる（キー名と実際の長さを保持） |

> R2〜R4 の鍵導出は §11、全リビジョンのパスワード認証と役割判定は §13 の入口を使います。

## 13. パスワード認証（Algorithm 6 / 7 / 11 / 12）

ISO 32000-1:2008 §7.6.3.4（Algorithm 6・7）および ISO 32000-2:2020 §7.6.4.4（Algorithm 11・12）に従い、暗号化辞書の `/U`・`/O` と照合してファイル暗号鍵と役割（利用者 / 所有者）を確定します。

Rust の `pdfmod_core::encrypt::auth` モジュールは、検証済みの鍵と役割を表す `AuthenticatedFileKey`、鍵本体を版別に包む `FileEncryptionKey`（`Legacy(LegacyFileKey)` / `Aes256(Aes256FileKey)`）、認証エラー `AuthError`、および `PasswordRole`（`encrypt::aes256_key::PasswordRole` の再公開）を提供します。入口は `StandardSecurityHandler` の次の 2 メソッドです。

- `authenticate(password: Option<&[u8]>, file_id: Option<&FileId>) -> Result<AuthenticatedFileKey<'_>, AuthError>` — 役割を自動判定して認証する
- `authenticate_as(role: PasswordRole, password: &[u8], file_id: Option<&FileId>) -> Result<AuthenticatedFileKey<'_>, AuthError>` — 指定した単一の役割で認証する

### 13.1 役割の試行順序と未指定時の既定動作

| `password` の指定 | 入力バイト列 | 試行順序 | 意図 |
| :--- | :--- | :--- | :--- |
| `None`（未指定） | `b""`（空パスワード） | `User` → `Owner` | 利用者・所有者ともに空パスワードの文書でも利用者として開き、`/P` の権限制限を尊重する |
| `Some(bytes)`（明示指定） | `bytes` | `Owner` → `User` | ISO 32000-1 §7.6.3.1 / ISO 32000-2 §7.6.4.1 に従い、利用者・所有者が同一パスワードの文書でも所有者権限を付与する |

1 つ目の役割が `AuthError::IncorrectPassword` を返した場合のみ 2 つ目の役割を試します。`/ID` 欠落や辞書項目の長さ不正、`/Perms` 不一致などの構造エラーはフォールバックせず即座に返します。

### 13.2 R2〜R4 の利用者パスワード認証（Algorithm 6）

R2〜R4 はパスワードを生のバイト列（PDFDocEncoding 等）として扱い、トレイラの `/ID` と 32 バイトちょうどの `/O`・`/U` を必須とします。Algorithm 2（§11）でファイル暗号鍵を導出した後、`/U` の期待値を計算して定数時間比較（全バイトの XOR 畳み込み）で照合します。

1. **R2（`/V 1 /R 2`）**: 32 バイトの標準パディング列をファイル暗号鍵（5 バイト）で RC4 暗号化し、`/U` の**全 32 バイト**と比較する（Algorithm 4）。
2. **R3・R4（`/V 1 /R 3`・`/V 2 /R 3`・`/V 4 /R 4`）**: `MD5(標準パディング列 || /ID[0])` の 16 バイトに対し、`i = 0..20` の 20 ラウンドで「ファイル暗号鍵の各バイトと `i` を XOR した鍵」を使って RC4 暗号化し、`/U` の**先頭 16 バイト**と比較する（Algorithm 5）。後半 16 バイトは任意のパディングであり比較しないが、辞書項目 `/U` 自体の長さは 32 バイトであることを検証する。

### 13.3 R2〜R4 の所有者パスワード認証（Algorithm 7）

1. **所有者 RC4 鍵の導出（Algorithm 3 手順 1〜4）**: 所有者パスワードを 32 バイトにパディングして MD5 に掛ける。R3・R4 では、得られた **16 バイトのダイジェスト全体**に MD5 をさらに 50 回適用する（Algorithm 2 の先頭 `n` バイト再ハッシュとは異なる）。ダイジェストの先頭 `n` バイト（R2・`/V 1 /R 3` は 5 バイト、`/V 2 /R 3`・`/V 4 /R 4` は `/Length / 8` バイト）を所有者 RC4 鍵とする。
2. **`/O` の復号**: `/O` の 32 バイトを復号してパディング済み利用者パスワードを復元する。R2 は所有者 RC4 鍵で 1 回 RC4 復号する。R3・R4 は `i = 19..=0` の**逆順** 20 ラウンドで「所有者 RC4 鍵の各バイトと `i` を XOR した鍵」を使って RC4 復号する。
3. **利用者側アルゴリズムでの検証**: 復元した 32 バイトのパディング済み利用者パスワードを**再パディングせずに** Algorithm 2 へ渡し、Algorithm 6 で `/U` と照合する。照合できれば `PasswordRole::Owner` と検証済みファイル暗号鍵を返す。

### 13.4 R5・R6 のパスワード認証（Algorithm 11 / 12）

R5・R6 はトレイラの `/ID` を参照しません。パスワードバイト列は鍵導出に使う先頭 127 バイトを覆う最小の UTF-8 文字境界まで（最大 130 バイト）を認証 1 回につき一度だけ UTF-8 として検証し、その範囲内に不正な UTF-8 があればどの検証ハッシュとも一致しないため `AuthError::IncorrectPassword` を返します（その文字境界より後ろの未使用バイトは走査せず無視します）。有効なプレフィックスは先頭 127 バイトで切り詰め（127 バイト目が多バイト文字の途中であってもそのまま切る。SASLprep は呼び出し側の責務）、`StandardSecurityHandler::derive_aes256_file_key`（§12）へ委譲します。

- **Algorithm 11（利用者）**: `/U`（48 バイト）の検証用ソルトでハッシュ照合（定数時間比較）し、鍵用ソルトで `/UE`（32 バイト）を復号して `/Perms`（16 バイト）を検証する。
- **Algorithm 12（所有者）**: `/O`（48 バイト）のソルトと追加データ `/U`（全 48 バイト）でハッシュ照合し、鍵用ソルトで `/OE`（32 バイト）を復号して `/Perms` を検証する。

### 13.5 型による安全境界とエラー分類

- `AuthenticatedFileKey<'handler>` は、認証に使った暗号化辞書の参照と検証済みの鍵・役割を保持する。フィールドは非公開で、`authenticate` / `authenticate_as` から構築する。`role()`・`key()`・`as_bytes()` で結果を参照できる。
- `FileEncryptionKey` は `Legacy(LegacyFileKey)` / `Aes256(Aes256FileKey)` の鍵種別を表す列挙型であり、単独では鍵の認証済みを保証しない（`Legacy` は `/U` 未照合の `derive_legacy_file_key` の結果も包める）。認証済みの鍵を要求する境界では `AuthenticatedFileKey` を受け取る。`FileEncryptionKey` は `as_bytes()`・`as_legacy()`・`as_aes256()` を提供し、`AuthenticatedFileKey`・`FileEncryptionKey` とも `Clone` / `Copy` を実装せず、`Debug` 出力は `finish_non_exhaustive()`（内包鍵型の秘匿実装を含む）で鍵バイト列を出力しない。
- `AuthError` はパスワード不一致と暗号化辞書・トレイラの構造不正や改ざんをバリアントで区別する。

| バリアント | 意味 |
| :--- | :--- |
| `IncorrectPassword` | 指定パスワード（未指定時は空パスワード）が認証に一致しない（R5・R6 の不正 UTF-8 を含む） |
| `MissingFileId` | R2〜R4 の認証に必要なトレイラの `/ID` が欠けている |
| `InvalidEntryLength { key, actual }` | `/O` `/U` `/OE` `/UE` `/Perms` の長さが仕様と異なる |
| `InvalidKeyLength { length }` | R2〜R4 の鍵長が 5〜16 バイトの範囲に収まらない |
| `InvalidPermissions` | R5・R6 で復号した `/Perms` の固定値・権限・メタデータフラグが辞書と一致しない |
| `InvalidHashInput` | R5・R6 の SHA-2 入力長または反復ブロック長を扱えない |
| `UnsupportedRevision` | 対応外のアルゴリズム版・リビジョンが渡された |

認証に成功したら、返された `AuthenticatedFileKey` を §14 のオブジェクト復号鍵の選択に使います。

## 14. オブジェクトの復号鍵

### 14.1 暗号方式の選択

`/V 1`・`/V 2` の文字列とストリームは RC4 を使います。`/V 4` 以降の既定方式は、文字列なら `/StrF`、ストリーム本体なら `/StmF` で選び、指定名を `/CF` で引きます。ストリーム辞書内の文字列にも `/StrF` が適用されます。

| 選択結果 | 鍵の扱い |
| :--- | :--- |
| `/Identity`、`/CFM /None` | 復号を省略。`/StmF`・`/StrF` の既定は `/Identity`、`/CFM` の既定は `/None` |
| `/CFM /V2` | Algorithm 1 で RC4 鍵を導出 |
| `/CFM /AESV2` | Algorithm 1 の入力末尾に `sAlT` を加え、16 バイトの AES-128 鍵を導出 |
| `/CFM /AESV3` | Algorithm 1.A に従い 32 バイトのファイル暗号鍵を使用 |

### 14.2 Algorithm 1 と 1.A

ISO 32000-1:2008 §7.6.2 の **Algorithm 1** では、認証済みのファイル暗号鍵、間接オブジェクト番号の下位 3 バイト、世代番号の下位 2 バイトを順に連結します。番号は下位バイトから並べます（リトルエンディアン）。AES-128 ではその末尾に ASCII `sAlT`（`73 41 6C 54`）を追加します。連結したバイト列を MD5 にかけ、先頭 `min(ファイル暗号鍵のバイト数 + 5, 16)` バイトを鍵にします。

例えば `7 4660 obj` の番号は `07 00 00`、世代 `4660 = 0x1234` は `34 12` です。オブジェクト番号が `0x01000000` のときは `00 00 00` が入力になります。番号の上位バイトだけが異なり世代が同じオブジェクトは、同じ鍵を導出します。AES-256 の **Algorithm 1.A** はオブジェクト番号・世代番号に関わらず 32 バイトのファイル暗号鍵を使用します。

### 14.3 オブジェクトストリームと Rust API

`/Type /ObjStm` のストリーム本体は、コンテナ自身の番号・世代とストリームの方式で復号します。取り出した内包オブジェクトの文字列は、コンテナの復号ですでに平文になっています。

`AuthenticatedFileKey::object_decryption` は、`ObjectDecryptionTarget` を受け取り、認証結果が保持する暗号化辞書とファイル鍵から方式と鍵を選びます。

- 通常の間接オブジェクトでは値の種類から既定の方式を選びます。RC4 と AES-128 は `ObjectId` を使って鍵を導出し、`/AESV3` は認証済みの 32 バイトの鍵をコピーします。戻り値は鍵を所有するため、認証結果より長く保持できます。
- ストリーム側の明示的な `/Crypt` や埋め込みファイル用の `/EFF` が適用される場合は、呼び出し側で扱います。
- `InObjectStream` ではフィルター選択と鍵導出を省略し、`ObjectDecryption::None` を返します。
- `/CF` に未定義の名前は暗号化辞書の解析時に `UndefinedCryptFilter` になります。選ばれた方式とファイル鍵が両立しない場合は `IncompatibleFileKey` を返します。

実際のデータへの復号の適用と文書読込への統合は #683 で扱います。
