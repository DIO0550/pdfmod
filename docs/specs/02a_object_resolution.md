## 1. 概要

PDF ファイル内のオブジェクトは、他のオブジェクトを**間接参照（Indirect Reference: `N G R`）**で指し示します（`N` はオブジェクト番号、`G` は世代番号）。

この間接参照から実体の PDF オブジェクトを取り出す処理を**オブジェクト解決（Object Resolution）**と呼びます。適合リーダーは相互参照テーブル（xref）を引いて物理位置を特定し、該当箇所からオブジェクトを読み込みます。

```text
間接参照: 5 0 R
    ↓ xref テーブルで番号 5 の位置を特定
    ↓ 該当オフセット（または ObjStm 内）からオブジェクトを読み込み
実体: << /Type /Page /MediaBox [0 0 612 792] >>
```

## 2. xrefテーブルによるオブジェクト位置の特定

相互参照テーブルのエントリは、次の 3 種類に分類されます。

### 2.1 Free Entry (type=0)

削除されたオブジェクトを示し、空きオブジェクトの連結リスト（フリーリスト）を形成します。

```pdf
xref
0 3
0000000000 65535 f    % オブジェクト 0: フリーリストの先頭
0000000010 00000 n
0000000000 00001 f    % オブジェクト 2: 削除済み（世代番号 +1）
```

適合リーダーは、Free Entry に対する間接参照を解決したときに **`null` オブジェクト** を返します。

### 2.2 Used Entry (type=1)

ファイルボディ内に直接置かれた通常のオブジェクトです。ファイル先頭からのバイトオフセットで位置が指定されます。

```pdf
xref
0 3
0000000000 65535 f
0000000010 00000 n    % オブジェクト 1: オフセット 10、世代 0
0000000512 00000 n    % オブジェクト 2: オフセット 512、世代 0
```

適合リーダーは指定オフセットへシークし、`N G obj ... endobj` 構文を解析してオブジェクトを読み込みます。

### 2.3 Compressed Entry (type=2)

オブジェクトストリーム（ObjStm）内に格納されたオブジェクトです。XRef ストリーム形式でのみ現れます。

| フィールド | 内容 |
| :--- | :--- |
| `type` | `2` |
| `streamObject` | 親オブジェクトストリームのオブジェクト番号 |
| `indexInStream` | ストリーム内での 0 起点インデックス |

Compressed Entry の世代番号は**常に `0`** です。

### 2.4 解決フロー

```text
間接参照 (N G R) を受け取る
    ↓
xref テーブルでオブジェクト番号 N を検索
    ↓
┌─ 未登録 ────────────→ null を返却
├─ type=0 (Free) ─────→ null を返却
├─ type=1 (Used) ─────→ 世代照合 → オフセットにシーク → obj ... endobj を解析
└─ type=2 (Compressed)→ 世代=0 確認 → 親 ObjStm を解決 → 対象インデックスを抽出
```

#### pdfmod の実装方針（オブジェクト番号 0 の扱い）

番号 `0` は ISO 32000-1 §7.5.4 の空きリスト先頭として予約されており、実在オブジェクトにはなりえません。

| 構文 | pdfmod の扱い | 理由 |
| :--- | :--- | :--- |
| `0 G R`（間接参照） | **パース時点で `null` オブジェクトに畳む**（参照ノードを作らない。構文エラーにしない） | xref を引くまでもなく常に `null` へ解決されるため。構文エラーにしないのは Postel の法則による |
| `0 G obj`（間接オブジェクト定義） | **エラー** | ISO 32000-1 §7.3.10（オブジェクト番号は正整数）に違反するため |

> **TS / Rust 間の既存差分**: 辞書の値が `null`（`0 G R` を畳んだ結果を含む）になったときの扱いは実装間で異なります。Rust は ISO 32000-1 §7.3.7 の正規化に従いキーごと削除し、TypeScript はキーを残して `null` 値を保持します。

## 3. 間接オブジェクト定義の構文

`type=1`（Used Entry）で参照されるオブジェクトは、次の構文で定義されます。

```pdf
N G obj
  <オブジェクト本体>
endobj
```

- **N**: オブジェクト番号（1 以上の正整数）
- **G**: 世代番号（非負整数、通常は `0`）
- **`obj` / `endobj`**: 定義の開始・終了キーワード

### 3.1 ヘッダ検証

適合リーダーは、xref エントリの指すオフセットに期待どおりの `N G obj` ヘッダが存在することを検証すべきです。番号や世代が一致しない場合、ファイルが破損しているかオフセットがずれている可能性があります（§8 参照）。

---

## 4. 世代番号の役割

世代番号は、オブジェクト番号の削除と再利用を安全に区別するための仕組みです。

### 4.1 ライフサイクル

1. 新規に割り当てられたオブジェクトは **世代番号 `0`** で始まる。
2. 増分更新で削除されるとフリーリストに入り、**世代番号が +1** される。
3. 同じオブジェクト番号が再利用されるとき、その新しい世代番号で `in-use` になる。

### 4.2 世代番号の不一致

間接参照 `N G R` の世代番号 `G` と xref エントリの世代番号が一致しない場合、その参照は古い世代を指す無効な参照とみなされます。適合リーダーは **`null` オブジェクト** を返すべきです。

世代番号の最大値は **`65535`** です（ISO 32000-1 §7.5.4）。

## 5. オブジェクトストリーム内のオブジェクト

### 5.1 ObjStm の構造

オブジェクトストリーム（`/Type /ObjStm`）は、複数のオブジェクトを 1 つのストリーム内にまとめて圧縮格納するコンテナです。

```pdf
10 0 obj
<< /Type /ObjStm /N 3 /First 24 >>
stream
11 0 12 100 13 200    % ヘッダ: (オブジェクト番号, 相対オフセット) のペア列
<< /Key1 /Value1 >>   % オブジェクト 11 のデータ
<< /Key2 /Value2 >>   % オブジェクト 12 のデータ
<< /Key3 /Value3 >>   % オブジェクト 13 のデータ
endstream
endobj
```

| キー | 必須 | 内容 |
| :--- | :--- | :--- |
| `/Type` | **必須** | `/ObjStm` |
| `/N` | **必須** | 格納されているオブジェクト数 |
| `/First` | **必須** | 最初のオブジェクトデータが始まる展開後バイトオフセット |

### 5.2 世代番号の制約

ObjStm 内に格納されたオブジェクトの世代番号は**常に `0`** です。世代番号が `0` でないオブジェクトは ObjStm へ格納できません。

### 5.3 格納制限

ISO 32000-1 §7.5.7 により、次のオブジェクトは ObjStm 内に格納できません。

- ストリームオブジェクト自身（ObjStm の入れ子も含む）
- 世代番号が `0` でないオブジェクト
- 暗号化辞書（`/Encrypt` の値となる辞書）
- **オブジェクトストリーム自身の辞書**の `/Length` エントリから間接参照されるオブジェクト（ストリーム本体より先に長さを確定する必要があるため。通常のコンテンツ/画像ストリームの `/Length` 参照先は対象外）

## 6. 循環参照

### 6.1 仕様上の扱い

PDF 仕様は間接参照による循環を明示禁止していませんが、適合ファイルにおいて意味のある循環参照は発生しません。一方で、破損ファイルや悪意あるファイルには循環参照が含まれることがあります。

### 6.2 適合リーダーの対応

適合リーダーは循環参照を検出し、無限ループを防止しなければなりません。

| 検出手法 | 内容 |
| :--- | :--- |
| **訪問済みセット** | 解決チェーン内で現在解決中のオブジェクト ID を記録し、再訪問を検出する |
| **深さ制限** | 解決チェーンの最大深度（例: 100 段）を設け、超過時に打ち切る |

循環参照を検出した場合は、エラーを返すか `null` オブジェクトとして処理します。

### 6.3 並行解決時の相互待ち

同一オブジェクトの解決結果を複数の解決チェーンで共有する実装（in-flight 共有）では、**チェーンごとの訪問済みセットだけでは循環を検出できません**。

```text
チェーン A: X を解決中 ──▶ Y の完了を待機
                                 │
                                 ▼ (相互待ちによるハング)
チェーン B: Y を解決中 ──▶ X の完了を待機

※ A の訪問済みセット = {X}、B の訪問済みセット = {Y} のため、
  単独セット上には循環が現れない。
```

#### 対策（待機グラフによる検出）

- 解決中の別チェーンの結果を待つ前に、**待機グラフ**（解決中オブジェクト → そのチェーンが待っているオブジェクト、の有向グラフ）を辿る。
- 辿った先が「自チェーンが現在解決中のオブジェクト」に到達する場合は、待たずに**循環参照エラー**として即座に打ち切る。
- 実時間タイムアウトによる打ち切りは、実行環境やファイルサイズに依存するため推奨されない。

## 7. 解決結果のキャッシュ

### 7.1 キャッシュの必要性

PDF ではフォント辞書やカラースペースなど、同一オブジェクトが多数箇所から繰り返し参照されます。解決結果をキャッシュすることで重複パースを避け、性能を大きく改善できます。

### 7.2 キャッシュキー

増分更新により同一オブジェクト番号でも異なる世代番号の参照が存在しうるため、キャッシュキーは **`(オブジェクト番号, 世代番号)` の組**（文字列表現なら `"N-G"`）にします。

### 7.3 LRU 戦略

メモリ使用量を抑えるため、LRU（Least Recently Used）キャッシュを推奨します。一般的な PDF では **1024 エントリ**程度の容量で十分なヒット率が得られます。

## 8. オフセットずれの寛容処理

### 8.1 問題

実世界の PDF では、xref テーブルに記録されたバイトオフセットと実際のオブジェクト位置がずれていることがあります。

- 増分更新時のオフセット計算ミス
- PDF 結合・変換ツールのバグ
- 改行コード変換（CR+LF → LF）による数バイトのずれ

### 8.2 対応戦略

段階的に回復を試みます。

| 段階 | 処理内容 |
| :--- | :--- |
| **1. 通常参照** | xref に記録されたオフセットに `N G obj` があるか確認する |
| **2. 近傍探索** | 見つからない場合、前後数十バイト（例: ±32 バイト）を探索する |
| **3. ファイル全体走査（再構築）** | それでも見つからない場合、ファイル全体を走査してオブジェクト位置を再構築する。元の xref で解決できるエントリ（free・世代番号・圧縮オブジェクトを含む）を優先し、走査結果は補助として使う |

#### 回復時の注意点

- 全体走査で同一オブジェクト番号が複数見つかった場合は、**後方の定義**を採用する。ただし、文字列・コメント・ストリームデータ本体の中に現れる見かけ上の `N G obj` を定義と誤認してはならない。
- 回復に成功した場合は「対象・元の位置・回復位置」を**警告として記録**し、回復不能な場合はエラーを返す。
- `startxref` や `%%EOF` が破損している場合も、有効なトレイラとオブジェクト境界を確認できれば回復を試みる。境界を確定できないストリームやトレイラ不在のファイルについて、内容を推測して成功扱いにしてはならない。
- PDF/A など厳格な適合性検証が求められる文脈では、寛容処理を無効化すべきである。
