# Lexer（字句解析）

PDFバイナリ（`Uint8Array`）をISO 32000-1:2008 §7.2 の字句規則に従ってトークン列に変換するモジュール。

---

## 前提: PDFファイルの全体構造

Lexerが何を切り出しているかを理解するため、まずPDFファイル全体の物理構造を示す。ISO 32000-1:2008 §7.5 "File Structure" の要約。

### 4つの物理セクション

PDFファイルは先頭から末尾に向けて次の4セクションで構成される。

```
┌────────────────────────────────────────┐
│ 1. Header     %PDF-1.7\n               │  §7.5.2
│               %âãÏÓ\n   (バイナリマーカ)  │
├────────────────────────────────────────┤
│ 2. Body                                │  §7.5.3
│                                        │
│    1 0 obj                             │  ← インダイレクトオブジェクト
│    << /Type /Catalog /Pages 2 0 R >>   │
│    endobj                              │
│                                        │
│    2 0 obj                             │
│    << /Type /Pages /Kids [3 0 R]       │
│       /Count 1 >>                      │
│    endobj                              │
│                                        │
│    3 0 obj                             │
│    << /Type /Page /Parent 2 0 R        │
│       /MediaBox [0 0 612 792]          │
│       /Contents 4 0 R >>               │
│    endobj                              │
│                                        │
│    4 0 obj                             │
│    << /Length 44 >>                    │
│    stream                              │  ← ストリームオブジェクト
│    BT /F1 24 Tf 72 720 Td (Hi) Tj ET   │    （バイナリOK）
│    endstream                           │
│    endobj                              │
│                                        │
├────────────────────────────────────────┤
│ 3. Cross-Reference Table (xref)        │  §7.5.4
│                                        │
│    xref                                │
│    0 5                                 │
│    0000000000 65535 f                  │  ← オブジェクト0: 未使用
│    0000000015 00000 n                  │  ← オブジェクト1のバイトオフセット
│    0000000074 00000 n                  │
│    0000000120 00000 n                  │
│    0000000210 00000 n                  │
├────────────────────────────────────────┤
│ 4. Trailer                             │  §7.5.5
│                                        │
│    trailer                             │
│    << /Size 5 /Root 1 0 R >>           │  ← カタログ(1 0 R)への入口
│    startxref                           │
│    255                                 │  ← xrefセクションのバイトオフセット
│    %%EOF                               │  ← ファイル終端マーカ
└────────────────────────────────────────┘
```

### 各セクションの役割

| セクション | 役割 | Lexerとの関係 |
|:-----------|:-----|:--------------|
| **Header** (§7.5.2) | `%PDF-M.m` でPDF版、続くバイナリ4バイト以上のコメントで「これはバイナリファイル」宣言 | Lexer非依存（上位層がバイト比較で検出） |
| **Body** (§7.5.3) | インダイレクトオブジェクト（`N G obj ... endobj`）の並び。全オブジェクトの実体がここに格納 | **Lexerの主戦場**。この領域を上位パーサがトークン化して構文木にする |
| **xref** (§7.5.4) | 「オブジェクト番号 → Bodyのバイトオフセット」の索引。20バイト固定レコード | 基本的にバイト単位で直接パース。Lexerは使わない |
| **Trailer** (§7.5.5) | ルートカタログ参照、`startxref`、`%%EOF` | 辞書部分（`<< ... >>`）はLexerを通す |

### なぜ末尾から読むか

PDFは「ランダムアクセス・ファイル」として設計されている。

1. ファイル末尾の `%%EOF` を探す
2. その直前の `startxref` でxrefのバイトオフセットを得る
3. xrefから必要なオブジェクトのバイトオフセットを得る
4. **Bodyの該当位置に直接ジャンプ**して1オブジェクトだけパース

大きなPDFでもページ1枚を表示するのに全体を読む必要がない。Lexerが**任意のバイトオフセットから開始**できるように設計されているのはこのため（`Tokenizer` のコンストラクタは位置0始まりだが、上位層は必要な部分バイト列だけを切り出して `Tokenizer` に渡すことで部分パースを実現する）。

### インクリメンタルアップデート（§7.5.6）

既存PDFに変更を加える場合、ファイル末尾に**追記**する。

```
[元のHeader][元のBody][元のxref][元のTrailer][元の%%EOF]
                                             [新Body][新xref][新Trailer /Prev 元オフセット][新%%EOF]
```

- `%%EOF` はファイル内に複数出現しうる
- パーサは **最後の** `%%EOF` から読み始め、`/Prev` を辿って古いxrefをマージする

### オブジェクトストリーム（§7.5.7 / PDF 1.5+）

Body内のインダイレクトオブジェクトは、複数をまとめて1つのストリーム（`/Type /ObjStm`）に圧縮格納できる。この場合、内側のオブジェクト群は**FlateDecode展開後のバイト列**に対してLexerを再適用してパースする。すなわちLexerは「ファイル全体」だけでなく「任意の展開済みバイト列」にも適用される。

### Body内でのトークン例

Lexerが上記Bodyを流すと、以下のようなトークン列を出力する（オブジェクト1の例）。

```
Integer(1) Integer(0) Keyword("obj")
DictBegin Name("Type") Name("Catalog") Name("Pages") Integer(2) Integer(0) Keyword("R") DictEnd
Keyword("endobj")
```

このトークン列から **インダイレクトオブジェクト定義** `1 0 obj ... endobj` や **インダイレクト参照** `2 0 R` を組み立てるのは上位のObjectParserの責務。Lexerは「数値」「キーワード」「辞書の括弧」などの**最小単位**しか認識しない。

## bytes モジュール

### バイト分類（ISO 32000-1 Table 1 / Table 2）

PDF仕様はバイトを以下に分類する。

#### Whitespace（Table 1）— トークン区切りとしてのみ意味を持つ

| バイト | 文字 | 使われる場所 |
|:-------|:-----|:-------------|
| `0x00` | NUL | ほぼ使われない。歴史的理由で含まれる（PostScript互換） |
| `0x09` | HT（水平タブ） | インデントに使われる場合あり |
| `0x0A` | LF | EOLマーカ（Unix系）。`stream` キーワード直後、`endstream` 直前、xrefの20バイトレコード末尾など、**データ境界として多用** |
| `0x0C` | FF（改頁） | ほぼ使われない |
| `0x0D` | CR | EOLマーカ（旧Mac系）。`CR+LF` 単位で現れることが多い（Windows系出力） |
| `0x20` | SPACE | トークン間区切りの主役。インダイレクト参照 `5 0 R` などで必須 |

#### Delimiter（Table 2）— PDF構文を構築する特殊記号

| バイト | 文字 | 使われる場所 |
|:-------|:-----|:-------------|
| `0x28` `0x29` | `(` `)` | **リテラル文字列** `(Hello)`（§7.3.4.2） |
| `0x3C` `0x3E` | `<` `>` | **16進文字列** `<48656C6C6F>`（§7.3.4.3）、**二重時は辞書** `<< ... >>`（§7.3.7） |
| `0x5B` `0x5D` | `[` `]` | **配列** `[1 2 3]`（§7.3.6）。MediaBox、Kids、Contents 等で頻出 |
| `0x7B` `0x7D` | `{` `}` | **Type 4 Function**（PostScript Calculator Function §7.10.5）専用。通常のオブジェクト構文には現れない |
| `0x2F` | `/` | **名前オブジェクト** `/Type /Page`（§7.3.5）。辞書のキーとしてほぼ全箇所で登場 |
| `0x25` | `%` | **コメント** `% ...`（§7.2.4）、**ヘッダ** `%PDF-1.7`（§7.5.2）、**終端マーカ** `%%EOF`（§7.5.5） |

**Regular**: 上記以外のバイト。数値、キーワード（`obj` `endobj` `R` `stream` `endstream` `trailer` `xref` `startxref` `true` `false` `null`）、名前の本体、文字列本体などを構成する。

判定は `Set<number>` によるO(1)ルックアップで実装される。

### skipWhitespaceAndComments

`data[pos]` 以降から、以下が続く限り読み進めた最終位置を返す。

1. 空白バイト（Table 1）
2. `%` で始まるコメント（`LF` or `CR` まで／改行文字自体は空白扱いで次ループ以降に読み飛ばす）

`end` 引数は省略可（既定値 `data.length`）。

#### なぜスキップするのか

PDFの字句規則では **空白とコメントはトークンの一部ではない**（§7.2.3, §7.2.4）。上位のパーサは「次のトークンは何か」だけを知りたいので、Lexerが先に意味のないバイトを飛ばしてしまうのが自然。以下が具体的な理由。

**空白をスキップする理由**

- 空白は **トークンの区切りとしてのみ** 意味を持つ（例: `5 0 R` の空白は「整数・整数・キーワードという3トークンである」ことを示すだけ）
- 空白は連続可・種類混在可（`SP SP LF CR SP` のような並びも合法）。個別に意味を持たないので1つの処理でまとめて飛ばすのが効率的
- 改行コードはUnix/Mac/Windowsで異なる（LF / CR / CR+LF）が、PDFは3通りとも合法とする（§7.2.3）。Lexerで吸収することで上位層はEOL種別を意識せずに済む
- 辞書・配列・オブジェクト定義の**どこにでも挿入可能**なため、トークンを読むたびに先頭の空白を飛ばす共通処理が必要

**コメントをスキップする理由**

- コメントは人間向けのメタ情報で、**PDFの意味構造には影響しない**（§7.2.4 で「字句解析上は単一の白空白として扱う」と明記）
- コメントはオブジェクト定義の途中にも書ける（例: `<< /Type % ここはコメント\n/Page >>` は合法）。上位層がコメントを意識するのは煩雑なのでLexerで消す
- ただし `%PDF-1.7`（ヘッダ §7.5.2）と `%%EOF`（終端 §7.5.5）は**特殊コメント**で、上位層がバイト比較で検出する必要がある。これらはBody解析前後の**Lexerを通さない領域**なので、Lexerがスキップしても問題ない
- ストリーム本体（`stream ... endstream`）内の `%` はコメントとして解釈してはならない（§7.2.4）。これはLexerを `stream` ブロック内に入れないことで回避する（上位層が `/Length` バイトをそのまま切り出す）

**なぜ「空白」と「コメント」を1関数にまとめているか**

1つだけ飛ばしても直後に他方が来る可能性があるため（例: `SP SP % comment LF SP /Name`）。ループで両方を相互に処理しないと、1回の呼び出しで確実に「次の有効トークン先頭」に到達できない。

### matchesBytesAt

`data` の `offset` から `pattern` のバイト列と完全一致するかを判定する軽量ヘルパ。キーワード認識などで使用。

## tokenizer モジュール

### Tokenizer クラス

内部状態は `data: Uint8Array` と `pos: number` の2つのみ。

| メンバ | 役割 |
|:-------|:-----|
| `constructor(data)` | バイト列を受け取り `pos = 0` で初期化 |
| `get position` | 現在のバイトオフセットを取得 |
| `nextToken(): Token` | 次の1トークンを読み取る |
| `tokenize(): Token[]` | 末尾の `EOF` トークンまで全消費した配列を返す |

### トークン種別（TokenType）

`@pdfmod/core` の `TokenType` 列挙型に対応。

| TokenType | 由来バイト | 値の型 | 備考・使われる場所 |
|:----------|:-----------|:-------|:-------------------|
| `ArrayBegin` | `[` | `"["` | 配列の開始。`MediaBox [0 0 612 792]`、`Kids [3 0 R 4 0 R]` など |
| `ArrayEnd` | `]` | `"]"` | 配列の終了 |
| `DictBegin` | `<<` | `"<<"` | `<` を先読みして判定。辞書の開始。`<< /Type /Page >>` や `trailer << ... >>` など **PDF最重要データ構造** |
| `DictEnd` | `>>` | `">>"` | `>` を先読みして判定。辞書の終了 |
| `HexString` | `<hex>` | `string` | 空白は無視、`>` が終端。バイナリデータ（フォントCIDや暗号キーなど）を可読ASCII化して格納するときに使用 |
| `LiteralString` | `(...)` | `string` | 括弧ネスト対応、エスケープ処理。テキスト抽出 `(Hello World) Tj`、Info辞書の `/Title (...)` など |
| `Name` | `/...` | `string` | `#xx` 16進エスケープを復号。辞書のキー全般（`/Type` `/Length` `/Filter` ...）、フィルタ名（`/FlateDecode`）、フォント名など |
| `Integer` | 数字列 | `number` | 小数点なし。インダイレクトオブジェクト番号、世代番号、`/Length`、xrefオフセット、各種カウント値 |
| `Real` | 数字列 | `number` | 小数点を含む。座標、行列、色成分、フォントサイズなど |
| `Boolean` | `true` / `false` | `boolean` | `/Linearized true`、暗号辞書のフラグなど |
| `Null` | `null` | `null` | 辞書エントリの明示削除、未解決のインダイレクト参照の解決結果 |
| `Keyword` | それ以外のキーワード | `string` | `obj` / `endobj`（オブジェクト定義 §7.3.10）、`R`（インダイレクト参照）、`stream` / `endstream`（§7.3.8）、`xref` / `trailer` / `startxref`（§7.5.4-5）、コンテンツストリーム演算子（`BT` `ET` `Tj` `Tf` `Td` ...）。単独の `>` もここに落ちる |
| `EOF` | — | `null` | ストリーム末尾で常に1つ返す。上位層のループ終了判定用（PDFの `%%EOF` とは無関係） |

すべてのトークンは `offset: ByteOffset`（Branded型）を持ち、入力バイト列上の開始位置を保持する。

### 字句認識の処理フロー

`nextToken()` は次の順で動作する。

1. `skipWhitespaceAndComments` で先行空白と `%` コメントを読み飛ばす
2. 末尾に達していれば `EOF` トークンを返す
3. 現在位置を `offset` として記録し、1バイト先読み
4. `switch` で以下の分岐を行う
   - `[` / `]` → `ArrayBegin` / `ArrayEnd`
   - `<` → 次バイトが `<` なら `DictBegin`、そうでなければ `readHexString`
   - `>` → 次バイトが `>` なら `DictEnd`、そうでなければ単独の `Keyword(">")`
   - `(` → `readLiteralString`
   - `/` → `readName`
   - 数字 / `+` / `-` / `.` → `readNumber`
   - それ以外 → `readKeyword`

### 補足: `()` と `<>`（単独）は「文字列の2つの書き方」

まず大前提として、**PDFの文字列オブジェクトは「バイト列」**（§7.3.4）。その書き方に2種類あるだけで、**結果として生成されるオブジェクトの型は同じ**。

| 書き方 | 例 | デコード後のバイト列 | 正式名称 |
|:-------|:---|:---------------------|:---------|
| `(...)` | `(Hello)` | `48 65 6C 6C 6F`（"Hello"） | Literal String（§7.3.4.2） |
| `<...>` 単独 | `<48656C6C6F>` | `48 65 6C 6C 6F`（同じ "Hello"） | Hexadecimal String（§7.3.4.3） |

つまり `(Hello)` と `<48656C6C6F>` は**完全に同じ意味**。PDFライタがどちらで書いてもよい。

#### なぜ2種類あるか

- **`(...)` は人間が読める文字用** — 英数字や普通の記号で済むなら直接書ける。`(Hello World)` のように明快
- **`<...>` はバイナリやエスケープ地獄回避用** — `\0`、`\x7F`、日本語 UTF-16BE、制御文字などを含む場合、`(...)` だとエスケープが増えて読みにくい。16進表記なら全バイトを均一に2桁で表せる

#### 実例での使い分け

```
/Title (My Document)               % 普通の文字列は (...) が多い
/Author (Alice)
/Contents (BT /F1 12 Tf ...)       % コンテンツストリーム指示

/ID [ <A1B2C3D4E5F6...> <...> ]    % ID はバイナリハッシュ → 16進が自然
/O  <3A40CD...>                    % 暗号辞書の Owner password hash → 16進
/Title <FEFF30CF30ED30FC>          % UTF-16BE（先頭BOM FE FF）で日本語 "ハロー"
```

特に **日本語などの非ASCII** は `<FEFF...>` 形式（UTF-16BEのBOM付き）で書かれることが多い。

#### では `<<` `>>`（辞書）との違いは？

`<` が**1つか2つか**だけ。Lexerは `<` を読んだ瞬間に次の1バイトを先読みして判定している。

| 入力 | トークン |
|:-----|:---------|
| `<48656C6C6F>` | `HexString("48656C6C6F")` |
| `<< /Key 1 >>` | `DictBegin ... DictEnd` |

#### まとめ表

| 記号 | 意味 | 例 | 結果の型 |
|:-----|:-----|:---|:---------|
| `(...)` | リテラル文字列 | `(Hello)` | 文字列（バイト列） |
| `<...>`（単独） | 16進文字列 | `<48656C6C6F>` | **同じ**文字列（バイト列） |
| `<< ... >>`（二重） | **辞書** | `<< /Type /Page >>` | 辞書（キー値マップ） — 別物 |

#### PDFのどこで現れるか

文字列オブジェクトはPDF全体で幅広く使われる。典型的な登場箇所を**`()` が好まれる場面**と**`<>` が好まれる場面**に分けて示す。

##### `()` リテラル文字列が現れる主な場所

| 場所 | 仕様節 | 用途 | 例 |
|:-----|:-------|:-----|:---|
| **Info辞書** | §14.3.3 | ドキュメントメタデータ | `/Title (My Document)` `/Author (Alice)` `/Producer (pdfmod 1.0)` |
| **コンテンツストリーム** | §9.4.3 Table 107 | ページに描画するテキスト | `(Hello World) Tj` / `[(Hel) -20 (lo)] TJ`（Tj/TJ演算子のオペランド） |
| **注釈辞書** | §12.5.2 | 注釈の本文・ポップアップ | `/Contents (This is a comment)` |
| **URIアクション** | §12.6.4.7 | リンク先URL | `/URI (https://example.com)` |
| **アウトライン** | §12.3.3 | しおり・ブックマークのタイトル | `/Title (Chapter 1)` |
| **フォームフィールド値** | §12.7.3.3 | テキストフィールドの値 | `/V (user input)` |
| **JavaScript** | §12.6.4.16 | JavaScriptコード | `/JS (app.alert\("Hi"\);)` |
| **日付文字列** | §7.9.4 | 日時（ASCIIフォーマット） | `/CreationDate (D:20260419120000+09'00')` |

##### `<>` 16進文字列が現れる主な場所

| 場所 | 仕様節 | 用途 | 例 |
|:-----|:-------|:-----|:---|
| **ファイルID** | §14.4 | ファイル識別子（Trailer内） | `/ID [ <A1B2C3D4E5F6...> <78901234...> ]` |
| **暗号辞書** | §7.6.4 | パスワードハッシュ・暗号キー | `/O <3A40CD...>` `/U <EEEEEEEE...>` `/Perms <...>` |
| **非ASCII Info辞書** | §14.3.3 + §7.9.2.2 | 日本語・中国語等のメタデータ（UTF-16BE + BOM） | `/Title <FEFF30CF30ED30FC>`（"ハロー"） |
| **デジタル署名** | §12.8 | 署名値・証明書 | `/Contents <3082...>`（PKCS#7 DER） |
| **CMap/ToUnicode** | §9.10.3 | フォントのグリフ→Unicodeマッピング | `<0001> <0041>` `<00FB01> <0066 0069>` |
| **CID/Font** | §9.7 | CID配列、Differences配列 | `/Encoding << /Differences [ 1 /f_i <AD> ] >>` |
| **非ASCIIアウトライン** | §12.3.3 | しおりタイトルが日本語等 | `/Title <FEFF5BFE8C61>` |

##### 同じフィールドで両形式が現れる例

`/Title` は英語タイトルなら `(...)`、日本語タイトルなら `<...>` になる。同じ辞書エントリでもファイル次第で形式が変わる。

```
% 英語ドキュメント
<< /Title (Annual Report 2026)
   /Author (Alice Smith)
>>

% 日本語ドキュメント（UTF-16BE + BOM FE FF）
<< /Title <FEFF5E74510197D85831>           % "年次報告"
   /Author <FEFF30A230EA30B930B930DF30B9>  % "アリススミス"
>>
```

##### 実際のPDFボディでの出現例

Info辞書・Trailer・コンテンツストリームで、両形式が自然に混在する様子。

```
10 0 obj
<< /Title    (Report)                          ← リテラル（英語）
   /Subject  <FEFF30EC30DD30FC30C8>            ← 16進（UTF-16BE "レポート"）
   /Author   (Alice)                           ← リテラル
   /CreationDate (D:20260419120000+09'00')     ← リテラル（日付）
>>
endobj

20 0 obj                                       ← コンテンツストリーム
<< /Length 40 >>
stream
BT /F1 12 Tf 72 720 Td (Hello World) Tj ET    ← リテラル（描画テキスト）
endstream
endobj

trailer
<< /Size 21 /Root 1 0 R
   /ID [ <A1B2C3D4...> <E5F60718...> ]         ← 16進（ファイルID）
>>
```

##### 覚え方の目安

- **「人間が文章として書くもの」→ `(...)`**（タイトル、著者名、コメント、URL、本文テキスト）
- **「機械が計算で作るバイナリ」→ `<...>`**（ハッシュ、ID、暗号キー、署名）
- **「ASCIIで書けない言語」→ `<...>`**（UTF-16BE+BOMなので先頭が `FEFF` で始まる）

### リテラル文字列の規則（§7.3.4.2）

`readLiteralString` は以下を処理する。

- **括弧のネスト**: 外側の `(` を開いた状態から `depth = 1` で開始し、`(` で `depth++`、`)` で `depth--`。`depth === 0` になった `)` が終端
- **バックスラッシュエスケープ**: `\n`, `\r`, `\t`, `\b`, `\f`, `\(`, `\)`, `\\`
- **8進エスケープ**: `\ddd`（最大3桁、`0-7` のみ）を対応コードポイントに変換
- **未定義エスケープ**: 上記以外はバックスラッシュを剥がした文字そのまま（`\q` → `q`）

### 16進文字列の規則（§7.3.4.3）

`readHexString` は `>` が出るまで読み進め、途中の空白は無視する。値はデコードせず、生の16進文字列（大文字・小文字混在可）を保持する。奇数桁補正（末尾に `0` を補う）などのデコード処理は**上位のObjectParser層で行う**。

### Name の規則（§7.3.5）

`readName` は次の空白 or 区切り文字までをトークンとし、途中の `#xx` をASCII16進エスケープとして復号する（`#20` → スペースなど）。`#` 後の2バイトがデータ範囲外の場合はエスケープせずそのまま積む。

### 数値の規則（§7.3.3）

`readNumber` は整数・実数の両方を扱う。

- 先頭バイトが `.` のとき `hasDecimal = true` で開始（`.5` → `Real(0.5)`）
- 2つ目の `.` は拒否し、そこで停止
- 途中で空白/区切り以外の非数字が出た場合、**位置を `offset + 1` まで巻き戻して `readKeyword` にフォールバック**する。これにより `1a2` のような不正入力が数値ではなくキーワードとして消費される
- 変換は `parseInt(str, 10)` / `parseFloat(str)`

### キーワードとブール/null の特殊化

`readKeyword` は次の空白 or 区切り文字までを収集し、以下の文字列に限り特別扱いする。

| 文字列 | トークン |
|:-------|:---------|
| `true` | `Boolean(true)` |
| `false` | `Boolean(false)` |
| `null` | `Null` |

それ以外はすべて `Keyword` トークン（値は文字列）。`obj` / `endobj` / `R` / `stream` / `endstream` / `xref` / `trailer` / `startxref` の識別は**上位層（ObjectParser等）で文字列比較により行う**。

## 設計上の注意

### 責務の境界

Lexerが**行わない**処理は以下。

- インダイレクト参照 `N G R` の組立て（`Integer Integer Keyword("R")` の3トークン列を作るだけ）
- `stream ... endstream` のバイト範囲抽出（キーワードを返すのみ）
- 16進文字列のバイト列へのデコード
- リテラル文字列の PDFDocEncoding / UTF-16BE 解釈
- エラー検出（未閉じ括弧、不正な数値などを**寛容に通す**）

これらはすべて上位のパーサ層の責務。

### 寛容性（Postelの法則）

字句解析は入力を拒否しない。未閉じの `(...)` や `<...` は末尾までを値として持つトークンを返し、`EOF` に到達する。エラー報告は上位層が構文レベルで行う。

### パフォーマンス特性

- 状態は `pos` のみで、バックトラックは **数値→キーワードフォールバック1箇所のみ**（巻き戻し量は最大1バイト）
- トークン値は `String.fromCharCode` による逐次構築（長い文字列で配列結合に劣る可能性はあるが、現状PDFに出現する典型長では問題なし）
- `isPdfWhitespace` / `isPdfDelimiter` は `Set.has` でO(1)

## 使用例

```ts
import { Tokenizer, TokenType } from "@pdfmod/core";

const data = new TextEncoder().encode("5 0 obj\n<< /Type /Page >>\nendobj");
const tokenizer = new Tokenizer(data);

for (;;) {
  const token = tokenizer.nextToken();
  if (token.type === TokenType.EOF) break;
  console.log(token.type, token.value);
}
// Integer 5
// Integer 0
// Keyword "obj"
// DictBegin "<<"
// Name "Type"
// Name "Page"
// DictEnd ">>"
// Keyword "endobj"
```

## コード ↔ PDF仕様 対応表

Lexerで扱うバイト・制御構造ごとに、ISO 32000-1:2008（PDF 1.7）のどのセクションを根拠としているかを示す。セクション番号はISO 32000-1基準。ISO 32000-2:2020（PDF 2.0）でも同等条項が存在する（節番号がずれる場合あり）。

### 1. バイト分類

| コード箇所 | バイト | 仕様根拠 | 規定内容・使われる場所 |
|:-----------|:-------|:---------|:----------------------|
| `bytes/index.ts` `WHITESPACE` | `0x00` NUL | §7.2.3 Table 1 | 白空白の6種のうちのひとつ。ほぼ使われない（PostScript互換で含まれる） |
| 〃 | `0x09` HT | §7.2.3 Table 1 | 水平タブ。インデント用途 |
| 〃 | `0x0A` LF | §7.2.3 Table 1, §7.2.3 EOL | Unix系EOL。`stream` 直後・`endstream` 直前・xref 20バイトレコード末尾で必須 |
| 〃 | `0x0C` FF | §7.2.3 Table 1 | フォームフィード。ほぼ使われない |
| 〃 | `0x0D` CR | §7.2.3 Table 1, §7.2.3 EOL | 旧Mac系EOL。Windows系では `CR+LF` ペア |
| 〃 | `0x20` SP | §7.2.3 Table 1 | トークン区切りの主役（`5 0 R`、`[1 2 3]` など） |
| `bytes/index.ts` `DELIMITER` | `(` `)` | §7.2.3 Table 2 / §7.3.4.2 | リテラル文字列の開閉。テキスト `(Hello)`、Info辞書 `/Title (...)` |
| 〃 | `<` `>` | §7.2.3 Table 2 / §7.3.4.3, §7.3.7 | 単独: 16進文字列 `<48656C6C6F>` / 二重 `<<` `>>`: 辞書 |
| 〃 | `[` `]` | §7.2.3 Table 2 / §7.3.6 | 配列。`MediaBox`、`Kids`、行列、色値など |
| 〃 | `{` `}` | §7.2.3 Table 2 | Type 4 Function（PostScript Calculator §7.10.5）専用。通常のオブジェクト構文には現れない |
| 〃 | `/` | §7.2.3 Table 2 / §7.3.5 | 名前オブジェクト先頭。辞書キー全般・フィルタ名・フォント名 |
| 〃 | `%` | §7.2.3 Table 2 / §7.2.4 | コメント開始。ヘッダ `%PDF-1.7`、終端 `%%EOF` も同バイト起点の特殊コメント |

### 2. 空白・コメントのスキップ

| コード箇所 | 仕様根拠 | 規定内容 |
|:-----------|:---------|:---------|
| `skipWhitespaceAndComments`（空白ループ） | §7.2.3 | 「空白はトークン区切りであり複数連続可」 |
| `skipComment`（`%` → LF/CR） | §7.2.4 | 「`%` から最初のEOLマーカまでがコメント。字句解析上は単一の白空白として扱う」 |
| `skipComment` が LF/CR で停止（改行自体は残す） | §7.2.3 EOL | EOLマーカをループ本体の空白判定側で消費させるため（CR+LFを2個の空白として自然に処理） |

補足: ISO 32000-1 は EOL を「LF」「CR」「CR+LF」の3通りと定義（§7.2.3）。本実装は LF と CR をそれぞれ独立した空白とみなすことで3通りを統一的に処理する。

### 3. トークン認識（`Tokenizer.nextToken`）

`switch` 分岐と仕様節の対応。

| 分岐 | バイト | 仕様根拠 | トークン |
|:-----|:-------|:---------|:---------|
| `AsciiLeftBracket` / `AsciiRightBracket` | `[` `]` | §7.3.6 Array Objects | `ArrayBegin` / `ArrayEnd` |
| `AsciiLessThan` + 次も `<` | `<<` | §7.3.7 Dictionary Objects | `DictBegin` |
| `AsciiLessThan` 単独 | `<` | §7.3.4.3 Hexadecimal Strings | `HexString`（`readHexString`） |
| `AsciiGreaterThan` + 次も `>` | `>>` | §7.3.7 Dictionary Objects | `DictEnd` |
| `AsciiGreaterThan` 単独 | `>` | （仕様上は不正） | `Keyword(">")`（寛容処理） |
| `AsciiLeftParen` | `(` | §7.3.4.2 Literal Strings | `LiteralString`（`readLiteralString`） |
| `AsciiSlash` | `/` | §7.3.5 Name Objects | `Name`（`readName`） |
| 数字 / `+` / `-` / `.` | `0-9` `+` `-` `.` | §7.3.3 Numeric Objects | `Integer` / `Real`（`readNumber`） |
| それ以外 | — | §7.3.2, §7.3.9, §7.3.10, §7.5.x | `Boolean` / `Null` / `Keyword`（`readKeyword`） |

### 4. 各 `read*` メソッドの仕様根拠

#### `readHexString`（§7.3.4.3 Hexadecimal Strings）

| 処理 | 仕様根拠 | 規定内容 |
|:-----|:---------|:---------|
| `>` まで読む | §7.3.4.3 | `<` と `>` で区切られる |
| 空白を無視して格納 | §7.3.4.3 | 「16進数字間の空白は無視される」 |
| 奇数桁補正は**行わない** | §7.3.4.3 | 「奇数桁のとき末尾に `0` を補う」— **デコードは上位層** |
| 大小文字を混在保持 | §7.3.4.3 | 「`a-f` と `A-F` は等価」— デコード時に正規化 |

#### `readLiteralString`（§7.3.4.2 Literal Strings）

| 処理 | 仕様根拠 | 規定内容 |
|:-----|:---------|:---------|
| `depth` による `(` `)` ネスト追跡 | §7.3.4.2 | 「バランスした丸括弧はエスケープ不要」 |
| `\n` `\r` `\t` `\b` `\f` | §7.3.4.2 Table 3 | エスケープシーケンス一覧 |
| `\(` `\)` `\\` | §7.3.4.2 Table 3 | 特殊文字エスケープ |
| `\ddd`（最大3桁） | §7.3.4.2 | 8進数表記エスケープ。`0-7` のみ |
| 未定義エスケープ → 文字そのまま | §7.3.4.2 | 「認識されない `\x` はバックスラッシュを無視し `x` を残す」 |

補足: 本実装では §7.3.4.2 で規定される「行末バックスラッシュによる行継続」および「CR/LF/CR+LFを `\n` に正規化する」処理は **現時点で未実装**（生のバイトをそのまま格納）。必要になれば上位層または本モジュール内で対応予定。

#### `readName`（§7.3.5 Name Objects）

| 処理 | 仕様根拠 | 規定内容 |
|:-----|:---------|:---------|
| 白空白 or 区切り文字で停止 | §7.3.5 | 「名前は区切り文字 or 白空白で終了」 |
| `#xx` 2桁16進エスケープ | §7.3.5 | 「`#` の直後の2桁16進で任意バイトを表現」 |
| `#` の後にバイトが足りない場合は非エスケープ扱い | 仕様外（寛容処理） | `#` 末尾付近の壊れたPDFでも落ちないため |

#### `readNumber`（§7.3.3 Numeric Objects）

| 処理 | 仕様根拠 | 規定内容 |
|:-----|:---------|:---------|
| 先頭 `+` `-` を許可 | §7.3.3 | 「省略可能な符号」 |
| 先頭単独 `.` を `Real` として開始 | §7.3.3 | 「`.002` `4.` など整数部/小数部のいずれか省略可」 |
| 2つ目の `.` で停止 | §7.3.3 | 「1数値中に小数点は高々1個」 |
| 非数字出現で `readKeyword` に巻き戻し | 仕様外（寛容処理） | 数値→キーワードの境界が曖昧な場合の安全側フォールバック |
| 指数表記非対応 | §7.3.3 | 「指数表記は許可されない」 |

#### `readKeyword`（§7.3.2 / §7.3.9 / §7.3.10）

| 処理 | 仕様根拠 | 規定内容 |
|:-----|:---------|:---------|

| `false` → `Boolean(false)` | §7.3.2 | 〃 |
| `null` → `Null` | §7.3.9 Null Object | キーワード |

| `xref` / `trailer` / `startxref` | §7.5.4, §7.5.5 File Structure | 〃 |
